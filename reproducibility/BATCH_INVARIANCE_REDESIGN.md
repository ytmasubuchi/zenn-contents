# batch-invariance 実験の再設計と事前登録

記録日時: 2026-10-20
**本ファイルは実装・実測の前にコミットする。** 予測の事前性を git のタイムスタンプで担保する。

## 旧設計の何が間違っていたか

旧 `S9_greedy_batch1` / `S9_greedy_batch8` は、Thinking Machines Lab (TML)
「Defeating Nondeterminism in LLM Inference」が報告した batch-invariance の破れを
検出できる設計になっていなかった。欠陥は3つ。

### 欠陥1: バッチ構成が均質
```python
inputs = tokenizer([text] * batch, return_tensors="pt")
```
batch8 の中身は同一プロンプトの8本複製。全行が同じ長さなので、
パディングも attention mask の分岐も**原理的に発生しない**。
TML が問題にしているのは「バッチの中身が変わると、そのリクエストの数値が変わる」ことであり、
同じものを8本並べても、バッチの「中身の多様性」という軸を一切動かしていない。

### 欠陥2: 観測量が鈍すぎる (最大の欠陥)
旧プローブの digest は `digest(gen_ids)`、つまり**生成されたトークンID列**。
greedy 復号は argmax なので、top-1 と top-2 のロジット差(margin)を跨ぐ摂動が無い限り
出力は一切変わらない。

本プロジェクトの既存実測(`S9_logit_margin`)で、以下が分かっている:
- margin の最小値 0.0037、中央値 約2.07
- GPU 間で実際に観測された margin の絶対差は最大 2.10e-5 (最小 margin の約 1/178)

つまり**摂動は margin より2桁小さく、トークン列は原理的にほぼ動かない**。
旧実験が「3GPUとも一致した」と報告したのは、現象が無かったからではなく、
**現象を検出できる観測量を使っていなかったから**である可能性が高い。

### 欠陥3: 試行が各条件1回
TML の分岐率は 80/1000 = 8%。数%の事象を n=1 で「一致した」と結論するのは統計的に無意味。

## 新設計

### 測るもの
固定した「被験プロンプト」P のロジットが、**同じバッチに何が入っているか**によって変わるかを測る。
生成トークン列ではなく、**ロジットそのものをビット単位で比較する**。

### バッチ構成(configs)
P を固定し、以下の文脈で P の最終実トークン位置のロジットを取る。

| config | 内容 | 狙い |
|---|---|---|
| `b1` | [P] 単体 | 基準 |
| `b8_same` | [P]×8、Pは位置0 | **旧設計の再現**(対照として残す) |
| `b8_mixed_first` | [P] + 長さの異なるfiller 7本、Pは位置0 | バッチの中身の多様性 |
| `b8_mixed_last` | filler 7本 + [P]、Pは位置7 | **バッチ内の位置**の影響 |
| `b2_long` | [P, 非常に長いfiller] | 極端なパディング |
| `b16_mixed` | [P] + varied filler 15本 | バッチサイズの影響 |
| `b4_padheavy` | [P] + Pより大幅に長いfiller 3本 | パディング比率 |

さらに `b8_mixed_first` について padding_side を left/right の両方で測り、
**パディング側**も独立した軸として扱う。

### 記録する量
各 config につき:
- P の最終実トークン位置のロジット行(float32)の digest
- `b1` を基準とした最大絶対差・最大 ULP 差
- argmax のトークンID (= greedy で選ばれるトークン)
- top-1 と top-2 のロジット差 (margin)

加えて、各 config を**同一プロセス内で2回**実行し、プロセス内決定性を確認する
(config 間の差が、バッチ構成に起因するものであって測定ノイズでないことを示すため)。

### 副次実験: トークン列が動くか
同じ config 群で greedy 生成も行い、`b1` を基準とした最初の分岐位置を記録する。
ロジットが動いてもトークンが動かないなら、それ自体が重要な結果である。

## 事前登録された予測 (実装・実測の前に記録)

### 予測1: `b1` vs `b8_same` (同一プロンプト8本複製)
**ロジットは不一致になる。**
根拠: 全行が同じでも、バッチサイズが変われば GEMM のグリッド分割・split-k の判断が変わりうる。
旧実験がトークン列で「一致」としたのは観測量が鈍かったためであり、
ロジット水準では既に動いていたはず、という読み。

外れる場合(= 一致する): 均質バッチではカーネルが真に batch-invariant であり、
旧実験の「一致」は観測量の鈍さだけが理由ではなかったことになる。これはこれで報告に値する。

### 予測2: `b1` vs `b8_mixed_first` / `b8_mixed_last`
**ロジットは不一致になり、その差は予測1の差より大きい。**
根拠: 長さの異なる行が混ざるとパディングで系列長が伸び、attention と matmul の形状が変わる。

### 予測3: `b8_mixed_first` vs `b8_mixed_last` (バッチ内の位置だけが違う)
**ロジットは不一致になる。**
根拠: 行がどのタイルに載るかが変わり、縮約の分割が変わる。

### 予測4: トークン列
**全 config でほぼ一致する。** 分岐が起きるとしても生成の後半。
根拠: margin 中央値 約2.07 に対し、予測される摂動は 1e-5 オーダー。桁が違う。
→ 「ロジットは動くがトークンは動かない」という結果になると予測する。
   これは「batch-invariance は数値水準では破れているが、
   この規模では greedy 復号がそれを隠している」という主張になる。

### 予測5: 同一 config のプロセス内2回実行
**完全に一致する。** 単一ストリームの順伝播は決定的なはず。
外れる場合: 測定自体にノイズがあり、config 間の比較が成立しない。その場合は設計をやり直す。

## 本設計でも埋まらない限界(あらかじめ明記する)

- **モデルが小さい。** Qwen2.5-0.5B-Instruct。TML は Qwen3-235B-A22B-Instruct-2507。
  層が深いほど誤差は累積するので、効果量は本実測の方が小さいはずである。
  RTX 4090 の 24GB という制約から、より大きなモデルは本プロジェクトでは測らない。
- **本番サーバの継続的バッチングではない。** TML が指摘する中心的な経路は
  「サーバ負荷によってバッチ構成が非決定的に変動する」ことであり、
  本実験は単一プロセス内でバッチ構成を**明示的に**変える静的な実験である。
  カーネルの batch 依存性という同じ機構を突いてはいるが、同じ土俵ではない。
- **推論基盤が transformers である。** vLLM / SGLang のような本番推論基盤の
  カーネルとは実装が異なる。TML の報告は本番基盤を対象としている。
