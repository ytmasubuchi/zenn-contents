## 新規プローブの仕様

### S11 乱数消費順序のリファクタ耐性

**目的**: 「壊れること」の提示にとどめず、「どう書けば壊れないか」を示す。

2つの実装を対比する。

- **素朴版**: 単一の `Generator` を使い回す。実務のコードの大半がこれにあたる。
- **頑健版**: `SeedSequence.spawn()` で成分ごとに独立したストリームを持つ。

両者に対し、実務で実際に起きるリファクタ4パターンを適用する。

| パターン | 内容 |
|---|---|
| ループ分割 | `for i: a=rng(); b=rng()` を `for i: a=rng()` と `for i: b=rng()` に分ける |
| 呼び出し順の入れ替え | `x=f(rng()); y=g(rng())` を `y=g(rng()); x=f(rng())` にする |
| デッドコード除去 | 使用していない乱数呼び出しを削除する |
| 条件分岐の追加 | 早期returnにより乱数の消費数が変わる |

**基準版の定義**: リファクタを適用していない元のコード。素朴版・頑健版それぞれに基準版がある。
比較は常に**同じ実装の基準版との間**で行う(素朴版の基準 vs 素朴版のループ分割、など)。
素朴版と頑健版の値そのものを比較することはしない(別のストリームなので一致する理由がない)。

**記録する内容**: 実装(素朴/頑健) × パターン(基準+4種) の各組み合わせについて、
生成された値のdigest、同じ実装の基準版との一致/不一致、消費した乱数の個数。

**ホスト間比較の扱い**: S11はPRNGの生ビット列に依存するためL0に属し、
ホストを跨いでもdigestは一致するはずである。一致しない場合は本プローブの前提が崩れているため、
リファクタ耐性の結論を出す前にその原因を調べる。

**要件**: 単一プロセスで完結。GPU不要。CPUのみで実行可能。

### S12 cudnn.benchmark / cudnn.deterministic

**目的**: 中堅ML層が最も頻繁に遭遇する設定であり、かつ第4章L4の代表例として表に書かれているのに
未実測だった穴を塞ぐ。

`torch.backends.cudnn.benchmark` と `torch.backends.cudnn.deterministic` の2×2で、
畳み込みを含むモデルの順伝播・逆伝播の結果を比較する。

**要点**: `benchmark=True` は実行時のタイミング計測でアルゴリズムを選択するため、
**同一プロセス内の繰り返しでも結果が変わりうる**。プロセス内反復を必須とし、
`stable_within_process` を記録する。

**要件**: GPU必須。

### S13 CUBLAS_WORKSPACE_CONFIG

**目的**: `use_deterministic_algorithms(True)` 下でこの環境変数が無い場合の挙動を記録する。
一部の演算で PyTorch が例外を送出することが期待されるが、どの演算が該当するかは未確認である。

**ハーネス側の変更が必要**: 現在 `scripts/run_on_host.sh` は IMAGE=gpu のとき
`CUBLAS_WORKSPACE_CONFIG` を無条件に設定している。比較のため、設定しない経路を追加する。
**既存6configの挙動は一切変更しないこと。**

**要件**: GPU必須。

### S14 DataLoader の worker seeding

**目的**: PyTorchで最も有名な再現性の落とし穴を実測する。

`num_workers` を 0 / 2 / 4 と変え、データ拡張の結果列を比較する。

**要点**: PyTorchはworkerごとに torch の RNG を再シードするが、**numpy の RNG は再シードしない**。
`worker_init_fn` を指定しない場合、全workerが同一のnumpy乱数列を使い、拡張が重複する。
torch の RNG を使う実装と numpy の RNG を使う実装を両方測り、
**片方だけが壊れること**を示す。

**要件**: GPU不要。

### S15 反復の生データ記録

**目的**: 記事が2箇所で「生データは `results/` には無く、プロジェクトの判断記録にのみ残っている」と
認めている箇所を塞ぐ。再現性を主題とする記事がこの状態であることは弱点である。

`index_add_`(非決定)と KMeans の反復実行について、**各回のdigestを列として記録する**。

**注意**: `index_add_` は意図的に非決定であるため、新たに測る5回は記事が現在引用している
「最大絶対差 8.24×10⁻⁴」とは異なる値になる。記事には「別の機会に測った別の5回」として
両方を併記する。非決定性の実例が2組になるため、これは利点として扱う。

**要件**: GPU必須(index_add_部分)。KMeans部分はCPUで可。

## 判定フローとレベル定義の変更

### コード同一性を前提条件として追加する

コード変更をフローの判定項目として組み込むのは誤りである。レベルと並列な軸ではないため。
コードを変えれば、**L0と判定した計算であっても結果は変わる**。
`np.random.default_rng(42).random()` の呼び出し順を入れ替えれば、
IEEE754もPRNG仕様も関係なく値は変わる。

したがってフローの手前に**前提条件**として置く。

> 判定は、同一のコードに対して行う。乱数の消費順序を変えるリファクタは、
> L0の計算であっても結果を変える。コードを変更したら、レベル判定は無効になり、やり直しになる。

納品文言テンプレートにも、全レベル共通の但し書きとして
「本保証はコードを変更しない限りにおいて有効である」を入れる。

### L2 / L3 の定義の書き換え

> L0・L1・L4は計算の性質で決まる。**L2とL3は証拠の状態を表す。**
> L2は「文書化された保証が無く、かつ試した範囲では割れなかった」という主張であり、反証可能である。
> 新しい軸で割れた時点で、その計算はL3に移る。
> L2判定には、自分が何を試したかの記録が伴わなければ意味がない。

判定フローの該当ステップにも同趣旨を一文入れる。

### テンプレートの文言修正

**L1**(現在): 「[ライブラリ名]==[X.Y.Z]に固定する限り、実行環境を問わずビット単位で一致することを約束する。」

これはF2(乱数列の一致と計算結果の一致は別の保証)と正面から矛盾する。範囲を乱数列に限定する。

**L1**(修正後の趣旨): [ライブラリ名]が生成する**乱数列について**、実行環境を問わずビット単位で一致する。
その乱数を使った後段の計算は本保証の範囲外であり、L3の条件が別途かかる。

**L3**(現在): 「これらのいずれかが変われば一致しない。」
**L3**(修正後): 「これらのいずれかが変われば、**一致は保証しない**。」

### 第1章への追加

「なぜビット一致が要るのか」だけでなく、**いつ allclose で足りるのか**も書く。
ML の仕事の大半はビット一致を必要としない。それを認めたうえで必要になる場面を挙げる方が、
記事は押し付けがましくなくなり、読者が自分の状況を判定できる。

ビット一致が要る場面として挙げるもの: 納品契約に「同じ入力なら同じ結果」と書いた場合、
allcloseの閾値を正当化できない回帰テスト、規制のある領域の監査、
原因の二分探索によるデバッグ、計算結果のキャッシュの正当性。
