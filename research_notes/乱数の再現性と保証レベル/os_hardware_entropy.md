# Hardware and OS Entropy Sources Beneath a Programming Language's Random Module

## Hardware layer: Intel DRNG (RDRAND/RDSEED) and ARM RNDR/RNDRRS — how do CPU TRNGs physically work, and what do the instructions return?

### Takeaway
Intel's DRNG is a two-stage hardware pipeline — an all-digital thermal-noise entropy source feeding an AES-based conditioner, which in turn feeds a SP 800-90A CSPRNG (DRBG) — where RDRAND reads expanded DRBG output and RDSEED reads conditioned entropy samples close to the raw source; ARM's RNDR/RNDRRS are architecturally analogous (DRBG output vs. a fresh-reseeded/non-deterministic draw), with the actual circuit design left implementation-defined by the architecture manual.

### Cited Findings
- Intel's entropy source (ES) is "all-digital," runs on "a self-timed circuit" "asynchronously," uses "thermal noise within the silicon to output a random stream of bits at the rate of 3 GHz," and needs "no dedicated external power supply" (uses the same supply as core logic) — [Intel DRNG Software Implementation Guide](https://www.intel.com/content/www/us/en/developer/articles/guide/intel-digital-random-number-generator-drng-software-implementation-guide.html), accessed 2026-10-14.
- Raw ES bits (~3 Gbit/s) are fed to a conditioner that "takes pairs of 256-bit raw entropy samples generated by the ES and reduces them to a single 256-bit conditioned entropy sample using AES-CBC-MAC" — [Intel DRNG Software Implementation Guide](https://www.intel.com/content/www/us/en/developer/articles/guide/intel-digital-random-number-generator-drng-software-implementation-guide.html), accessed 2026-10-14.
- Online health tests (OHTs) run continuously: per-sample tests reject unhealthy raw samples (conditioner "ensures at least two healthy samples are mixed into each seed"), and a sliding-window test over 65,536 bits checks the ES is "operating correctly overall before it issues random numbers" — [Intel DRNG Software Implementation Guide](https://www.intel.com/content/www/us/en/developer/articles/guide/intel-digital-random-number-generator-drng-software-implementation-guide.html), accessed 2026-10-14.
- RDRAND "retrieves a hardware-generated random value from the SP800-90A compliant DRGB [DRBG]"; the DRBG itself is "a hardware CSPRNG that is based on AES in CTR mode and is compliant with SP800-90A" — [Intel DRNG Software Implementation Guide](https://www.intel.com/content/www/us/en/developer/articles/guide/intel-digital-random-number-generator-drng-software-implementation-guide.html), accessed 2026-10-14.
- RDSEED "retrieves a hardware-generated random seed value from the SP800-90B and C compliant ENRNG [Enhanced Non-deterministic RNG]" — i.e., conditioned entropy samples made "directly available to software," and "samples can be concatenated and the brute-force prediction resistance will scale with them" — [Intel DRNG Software Implementation Guide](https://www.intel.com/content/www/us/en/developer/articles/guide/intel-digital-random-number-generator-drng-software-implementation-guide.html), accessed 2026-10-14.
- Seed distribution is architecturally separated from the DRBG: "This pathway can be thought of as an alternating switch, with one seed going to the DRGB and the next seed going to the ENRNG. This construction ensures that a software application can never obtain the value used to seed the DRBG" — [Intel DRNG Software Implementation Guide](https://www.intel.com/content/www/us/en/developer/articles/guide/intel-digital-random-number-generator-drng-software-implementation-guide.html), accessed 2026-10-14.
- Reseed bound: "An upper bound of 511 128-bit samples will be generated per seed. That is, no more than 511×2=1022 sequential DRNG random numbers will be generated from the same seed value"; the DRBG "autonomously decides when it needs to be reseeded ... and is both unpredictable and transparent to the RDRAND caller" — [Intel DRNG Software Implementation Guide](https://www.intel.com/content/www/us/en/developer/articles/guide/intel-digital-random-number-generator-drng-software-implementation-guide.html), accessed 2026-10-14.
- Performance: the DRBG "can service a RDRAND transaction every 8 clocks for a maximum of 100 MTx per second," with a 64-bit-read throughput ceiling around 800 MB/sec and single-thread throughput of roughly 70–200 MB/sec depending on microarchitecture; RDSEED generation is slower than consumption, so software must retry — [Intel DRNG Software Implementation Guide](https://www.intel.com/content/www/us/en/developer/articles/guide/intel-digital-random-number-generator-drng-software-implementation-guide.html), accessed 2026-10-14.
- Compliance/certification: the DRNG design "leverages ... NIST SP800-90A, B, and C, FIPS-140-2, and ANSI X9.82," but "the DRNG is not a FIPS cryptographic module: it is an SP800-90 compliant RNG solution which can be CAVS certified ... per product" (i.e., per processor generation) — [Intel DRNG Software Implementation Guide](https://www.intel.com/content/www/us/en/developer/articles/guide/intel-digital-random-number-generator-drng-software-implementation-guide.html), accessed 2026-10-14.
- ARM's RNDR (AArch64 system register, requires FEAT_RNG or FEAT_RNG_TRAP + FEAT_AA64): "returns a 64-bit random number from an approved Random Bit Generator, where the Deterministic Random Bit Generator within the Random Bit Generator is reseeded from an approved entropy source at an IMPLEMENTATION DEFINED rate." On success PSTATE.NZCV = 0b0000; on failure (cannot return a genuine random number in reasonable time) PSTATE.NZCV = 0b0100 and the returned value is 0 — [ARM AArch64 system register reference, RNDR](https://arm.jonpalmisc.com/latest_sysreg/AArch64-rndr), accessed 2026-10-14 (secondary rendering of the ARM Architecture Reference Manual register description; could not independently fetch the primary ARM ARM PDF page in this session — see Gaps).
- RNDRRS: "returns a 64-bit random number from an approved Random Bit Generator, using either a Non-deterministic Random Bit Generator or one where the Deterministic Random Bit Generator is reseeded, where possible, from an approved entropy source before the return of the random number" — i.e., each RNDRRS call forces a fresh reseed/non-deterministic draw rather than relying on the DRBG's own implementation-defined reseed interval. Same success/failure NZCV semantics as RNDR. Present "only when (FEAT_RNG is implemented or FEAT_RNG_TRAP is implemented) and FEAT_AA64 is implemented" — [ARM AArch64 system register reference, RNDRRS](https://arm.jonpalmisc.com/latest_sysreg/AArch64-rndrrs), accessed 2026-10-14 (same secondary-source caveat as above).
- FEAT_RNG_TRAP lets EL3 firmware trap reads of RNDR/RNDRRS from any exception level by setting `SCR_EL3.TRNDR=1` — [ARM feature names search summary](https://arm.jonpalmisc.com/latest_sysreg/AArch64-rndrrs) and related ARM feature-name documentation, accessed 2026-10-14.

### Inferences
- The RDRAND/RDSEED split and the RNDR/RNDRRS split are the same conceptual distinction in both architectures: one instruction (RDRAND / RNDR) reads from a continuously-running DRBG that is reseeded only periodically, favoring throughput; the other (RDSEED / RNDRRS) forces or approximates a fresh draw from (or near) the raw entropy source, favoring a fresh-entropy guarantee at the cost of speed/availability.
- "Random seed" at the hardware layer is not a single bit string handed to software — it is architecturally walled off from RDRAND/RNDR callers (per Intel's explicit statement); software-level seeds (e.g., a Python integer) are a completely separate, much coarser concept layered far above this.

## NIST standards: what role do SP 800-90A, 800-90B, and 800-90C each play in this stack?

### Takeaway
The three publications form a layered contract: 800-90B validates that a physical/digital noise source actually produces claimed entropy (min-entropy estimation + health tests), 800-90A specifies the deterministic algorithms (DRBG constructions) that stretch a true-random seed into long pseudorandom output streams, and 800-90C specifies how to wire a validated entropy source and a DRBG together into a complete Random Bit Generator (RBG) with defined security classes.

### Cited Findings
- SP 800-90A Rev. 1 "specifies several deterministic random bit generator (DRBG) mechanisms based on cryptographic algorithms" (CTR_DRBG, Hash_DRBG, HMAC_DRBG) — [NIST SP 800-90A Rev. 1](https://nvlpubs.nist.gov/nistpubs/specialpublications/nist.sp.800-90ar1.pdf), accessed 2026-10-14.
- SP 800-90B "specifies the design principles and requirements for entropy sources used by Random Bit Generators, and the tests for validation of entropy sources"; it requires full documentation of how the noise source works and justification for its entropy, and uses **min-entropy** as the quantitative measure ("the uncertainty associated with predicting the value of an observation") — [NIST SP 800-90B](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/nist.sp.800-90b.pdf), accessed 2026-10-14.
- SP 800-90B mandates continuous and startup health tests performed on raw noise-source samples **before any conditioning**, including Stuck Test, Repetition Count Test, Adaptive Proportion Test, and Lag Predictor Test; the Adaptive Proportion Test specifically "is designed to detect a large loss of entropy that might occur as a result of some physical failure or environmental change affecting the noise source" — [NIST SP 800-90B overview materials](https://csrc.nist.gov/csrc/media/events/random-bit-generation-workshop-2012/documents/kelsey_800-90b.pdf), accessed 2026-10-14.
- SP 800-90C "provides guidance on the construction of an RBG from a randomness source and an approved DRBG mechanism," defining RBG construction classes RBG1, RBG2, RBG3, and RBGC — [NIST SP 800-90C](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-90C.pdf), accessed 2026-10-14.
- Intel explicitly maps its own hardware to this stack: RDRAND's DRBG is "SP800-90A compliant," while RDSEED's entropy source/conditioner is "SP800-90B and C compliant" — [Intel DRNG Software Implementation Guide](https://www.intel.com/content/www/us/en/developer/articles/guide/intel-digital-random-number-generator-drng-software-implementation-guide.html), accessed 2026-10-14.

### Inferences
- The NIST 800-90 series is the common vocabulary vendors (Intel, ARM silicon partners) use to describe compliance, which is why Intel's own guide can be read almost as a worked example of the 800-90A/B/C split: noise source + health tests (90B) → conditioner (bridges 90B/90C) → DRBG (90A) → full RBG (90C class).
- Because entropy-source certification under 800-90B is per-product/per-process-node (Intel notes CAVS certification is needed "per product" since "processor generations must be individually certified"), a blog author should not assume "my CPU supports RDRAND/RDSEED" implies a currently valid, specific NIST certificate — certification status is generation- and vendor-specific and changes over time.

### Gaps
- Did not independently verify ARM's own statement (if any) of which SP 800-90A DRBG construction or 800-90C RBG class its reference FEAT_RNG implementations target; the architecture manual leaves this implementation-defined, and no ARM document found in this session states a default choice.

## OS layer on Linux: how does the kernel RNG work after the Jason Donenfeld rewrite (5.17/5.18+), and is "/dev/random blocks" still accurate?

### Takeaway
Since the 2022 rewrite, Linux no longer uses the old SHA-1-based multi-pool design; entropy is mixed with BLAKE2s into one input pool and expanded for output using a ChaCha20-based CRNG, `/dev/random` and `/dev/urandom` now behave identically and neither blocks after early boot (the historical "/dev/random blocks for entropy" advice is obsolete since kernel 5.6), and `getrandom(2)` is the recommended interface because it is the only one of the three that correctly blocks during early boot until the CRNG is actually seeded.

### Cited Findings
- "/dev/random and /dev/urandom devices now do exactly the same, bringing the Linux kernel in line with FreeBSD and macOS. The changes in 5.17 eliminate use of the SHA-1 algorithm, now replaced by BLAKE2, a descendant of ChaCha20." Kernel 5.17 contained "the first stage of the big rewrite, with more changes following in 5.18" — [The Register, "New Linux kernel has improved random-number generation"](https://www.theregister.com/2022/03/21/new_linux_kernel_has_improved/), accessed 2026-10-14.
- Current design: BLAKE2s mixes entropy into a single 256-bit input pool ("once you have 256 bits of real entropy, further accumulation doesn't increase security"); ChaCha20 powers the CRNG output stage; per-CPU CRNG instances (added in 5.18) allow lock-free generation — [kernel-internals.org, "Random Number Generation"](https://kernel-internals.org/crypto/rng/), accessed 2026-10-14 (secondary/community technical summary, not an official kernel.org page — see Gaps).
- Hardware RNG inputs (RDRAND/RDSEED) are mixed in during CRNG initialization but are "intentionally not trusted as the sole source" — rationale given: "a compromised RDRAND cannot bias the output" when combined with interrupt-timing jitter and other sources; interrupt timing is captured via `add_interrupt_randomness()`; virtio-rng supplies entropy from the hypervisor for VMs; VMGENID is mixed in to reseed the CRNG when a VM resumes from a snapshot/clone — [kernel-internals.org](https://kernel-internals.org/crypto/rng/), accessed 2026-10-14.
- Boot-time state machine: `crng_init = 0` (unseeded at power-on) → `crng_init = 1` (early-seeded, ~128 bits, usable but not fully secure) → `crng_init = 2` (fully initialized, 256 bits); sources feeding this include interrupt jitter, RDRAND mixing, and a seed file restored at boot by `systemd-random-seed.service` from the prior shutdown — [kernel-internals.org](https://kernel-internals.org/crypto/rng/), accessed 2026-10-14.
- "Since Linux 5.6, the O_NONBLOCK flag is ignored as /dev/random will no longer block except during early boot process" — [man7.org random(4)](https://man7.org/linux/man-pages/man4/random.4.html), accessed 2026-10-14.
- Current man page guidance: "/dev/random interface is considered a legacy interface, and /dev/urandom is preferred and sufficient in all use cases, with the exception of applications which require randomness during early boot time; for these applications, getrandom(2) must be used instead, because it will block until the entropy pool is initialized" — [man7.org random(4)](https://man7.org/linux/man-pages/man4/random.4.html), accessed 2026-10-14.
- `/dev/urandom`: "returns random bytes using a pseudorandom number generator seeded from the entropy pool. Reads from this device do not block" (except possibly very early boot before any seeding). `/dev/random`: "legacy interface ... will return random bytes only within the estimated number of bits of fresh noise in the entropy pool, blocking if necessary" (historically; this blocking behavior itself was removed post-5.6 per the note above) — [man7.org random(4)](https://man7.org/linux/man-pages/man4/random.4.html), accessed 2026-10-14.
- `getrandom(2)`: "fills the buffer pointed to by buf with up to size random bytes." "By default, getrandom() draws entropy from the urandom source (i.e., the same source as the /dev/urandom device)." With `GRND_RANDOM` set, "random bytes are drawn from the random source (i.e., the same source as the /dev/random device)" (now a no-op distinction post-unification). "If the urandom source has not yet been initialized, then getrandom() will block, unless GRND_NONBLOCK is specified." Once initialized, "reads of up to 256 bytes will always return as many bytes as requested and will not be interrupted by signals" — [man7.org getrandom(2)](https://man7.org/linux/man-pages/man2/getrandom.2.html), accessed 2026-10-14.
- Entropy pool fundamentals (still-current framing): "The random number generator gathers environmental noise from device drivers and other sources into an entropy pool," and `/proc/sys/kernel/random/entropy_avail` and `poolsize` expose the pool's current entropy estimate and size — [man7.org random(7) / ArchWiki summary](https://wiki.archlinux.org/index.php/Random_number_generation), accessed 2026-10-14.
- VM-cloning security fix: the kernel checks an ACPI `vmgenid` value; "If the ID changes, the kernel mixes the ID into the entropy pool, changing it and thus making it unique," preventing cloned/snapshotted VMs from producing identical RNG output streams — [The Register](https://www.theregister.com/2022/03/21/new_linux_kernel_has_improved/), accessed 2026-10-14.

### Inferences
- For a Python-programmer audience, the practically important fact is: on any kernel from the last several years (5.6+ for the blocking fix, 5.17/5.18+ for the full ChaCha20/BLAKE2s rewrite), reading `/dev/urandom` or calling `getrandom()` after boot returns cryptographically strong bytes immediately — there is no "waiting for enough mouse movement/disk interrupts" scenario in steady-state operation; that scenario is now confined to the first moments after boot (and mainly matters for early-boot system services, not application code running later).
- The RDRAND/RDSEED mixing-but-not-trusting design mirrors the Intel DRNG findings above: the kernel treats the CPU TRNG as one noisy input among several rather than as an authoritative seed source, which is a deliberate defense against a hypothetically backdoored or flawed CPU RNG.

## Python's entropy: what does `os.urandom()` call, and what happens on `random.seed()` with no argument?

### Takeaway
`os.urandom()` is CPython's thin wrapper around the OS CSPRNG — `getrandom()` on Linux, `getentropy()`/`CCRandomGenerateBytes` on macOS/BSD, `BCryptGenRandom` on Windows — and it is documented as blocking-safe/secure by design (PEP 524); `random.seed(None)` seeds the (non-cryptographic) Mersenne Twister from OS randomness when available, falling back to system time only if OS randomness is unavailable.

### Cited Findings
- Official docs for `random.seed(a=None, version=2)`: "If a is omitted or None, the current system time is used. If randomness sources are provided by the operating system, they are used instead of the system time (see the os.urandom() function for details on availability)" — [Python 3 docs, `random.seed`](https://docs.python.org/3/library/random.html#random.seed), accessed 2026-10-14.
- The core PRNG CPython's `random` module wraps is the Mersenne Twister: "fast and threadsafe," producing "53-bit precision floats" with "period of 2^19937 − 1" — [Python 3 docs, `random`](https://docs.python.org/3/library/random.html#random.seed), accessed 2026-10-14.
- `version=2` (default): a `str`/`bytes`/`bytearray` seed "gets converted to an int and all of its bits are used"; `version=1` (legacy, pre-3.2 compatible) "generates a narrower range of seeds" for str/bytes — [Python 3 docs, `random.seed`](https://docs.python.org/3/library/random.html#random.seed), accessed 2026-10-14.
- `os.urandom()` is documented (per CPython docs, as summarized via web search since direct fetch was truncated) to call `getrandom()` on Linux, `getentropy()` on macOS/BSD, and `BCryptGenRandom` on Windows (replacing the older `CryptGenRandom` as of Python 3.11) — [Python 3 docs, `os.urandom`](https://docs.python.org/3/library/os.html#os.urandom), accessed 2026-10-14 (page content was truncated in the fetch tool; corroborated via secondary search summary — see Gaps).
- On Linux, CPython was changed so that `os.urandom()` always calls the `getrandom(size, 0)` syscall (blocking mode by default) rather than opening `/dev/urandom` as a file, avoiding file-descriptor-exhaustion and chroot/sandboxing issues; a separate `os.getrandom()` function (with a `flags` parameter) was added for Linux/Solaris to let callers opt into non-blocking behavior — [PEP 524, "Make os.urandom() blocking on Linux"](https://peps.python.org/pep-0524/); [bpo-27266](https://bugs.python.org/issue27266), accessed 2026-10-14.
- PEP 524's rationale: "On Linux 3.17 and newer, os.urandom() blocks until the system urandom entropy pool is initialized to increase the security," because unseeded urandom reads pre-initialization were considered a security risk (predictable output very early at boot) — [PEP 524](https://peps.python.org/pep-0524/), accessed 2026-10-14.
- Reported practical fallout and fix: `getrandom(0)` blocking until 128 bits of kernel entropy could stall system initialization scripts depending on Python at boot; CPython was adjusted to fall back to non-blocking behavior for initializing the internal hash-randomization secret and the default `random` module seeding path specifically (these uses are not security-critical the way `os.urandom()`/`random.SystemRandom` are) — [Python bug tracker discussion, bpo-27272 and related](https://bugs.python.org/issue27272); [LWN, "Python's os.urandom() in the absence of entropy"](https://lwn.net/Articles/693189/), accessed 2026-10-14.
- On macOS, there is an open CPython documentation gap (acknowledged by CPython maintainers): the implementation actually uses `CCRandomGenerateBytes` (falling back to `arc4random_buf`), but `getentropy()` is a true macOS **system call** (unlike on Linux where it's a libc wrapper around `getrandom()`), not vulnerable to file-descriptor exhaustion and usable even sandboxed/chrooted; this macOS-specific behavior was, as of this writing, not fully reflected in the official `os.urandom()` docs page — [CPython issue #116245, "os.urandom does not document CCRandomGenerateBytes"](https://github.com/python/cpython/issues/116245), accessed 2026-10-14.

### Inferences
- There are effectively two separate "random" subsystems in CPython with different entropy needs: (1) `os.urandom()` / `random.SystemRandom` / cryptographic uses, which must reach genuine OS CSPRNG output and are allowed to block at early boot for safety; and (2) the default `random.Random` (Mersenne Twister) used for `random.seed(None)`, which *tries* OS randomness first but is explicitly documented to fall back to wall-clock time, and is not cryptographically secure regardless of seed quality (MT output is fully predictable from ~624 consecutive outputs). A blog author explaining "no seed fixed" behavior for ordinary `random` module calls should be precise that even unseeded `random.random()` is not fit for security use — its *seed* may come from the OS CSPRNG, but its *output stream* does not inherit that CSPRNG's unpredictability guarantees once running.
- Because `os.urandom()` is what ultimately underlies the "OS randomness" path in `random.seed(None)`, "not fixing a seed" in ordinary Python code is, in practice, one call away from everything described in the Linux-kernel and CPU-TRNG sections above — but only at the moment of seeding, not for every subsequent `random()` call.

## PYTHONHASHSEED and hash randomization: what is it, why does it exist, what gets randomized, and does it affect `dict` vs `set` iteration order?

### Takeaway
Hash randomization (PEP 456, using SipHash) was introduced to stop hash-flooding denial-of-service attacks (oCERT-2011-003 / CVE-2012-1150) by randomizing the hash of `str`, `bytes`, and related types with a per-process 128-bit key drawn at startup; `PYTHONHASHSEED` controls that key (random by default, fixed/reproducible if set to an integer, disabled if set to `0`); this affects iteration order of hash-table-based containers like `set`, but not `dict`, whose insertion-order preservation has been a guaranteed language feature since Python 3.7 regardless of hash seed.

### Cited Findings
- The underlying vulnerability: "Python before 2.6.8, 2.7.x before 2.7.3, 3.x before 3.1.5, and 3.2.x before 3.2.3 computes hash values without restricting the ability to trigger hash collisions predictably, which allows context-dependent attackers to cause a denial of service (CPU consumption) via crafted input to an application that maintains a hash table" — [CVE-2012-1150, OpenCVE](https://app.opencve.io/cve/CVE-2012-1150), accessed 2026-10-14.
- PEP 456 frames the same issue via the original advisory: "CPython is still vulnerable to hash collision DoS attacks," citing **oCERT-2011-003** as the original report — [PEP 456, "Secure and interchangeable hash algorithm"](https://peps.python.org/pep-0456/), accessed 2026-10-14.
- PEP 456 adopted **SipHash24** as the default hash algorithm — "a cryptographic pseudo random function with a 128-bit seed and 64-bit output," already used by "Ruby, Perl, OpenDNS, Rust, Redis, FreeBSD and more" — [PEP 456](https://peps.python.org/pep-0456/), accessed 2026-10-14.
- Randomization applies to hash values of `str`, `bytes`, `datetime`-family objects (date/time/datetime), and `memoryview` objects; the 128-bit SipHash key (`_Py_HashSecret_t`) is "initialized in Python/random.c:_PyRandom_Init() exactly once at startup" — [PEP 456](https://peps.python.org/pep-0456/), accessed 2026-10-14.
- Official current documentation of `PYTHONHASHSEED`: "If this variable is not set or set to `random`, a random value is used to seed the hashes of str and bytes objects. If PYTHONHASHSEED is set to an integer value, it is used as a fixed seed for generating the hash() of the types covered by hash randomization... The integer must be a decimal number in the range [0, 4294967295]. Specifying the value 0 will disable hash randomization" — [Python 3 docs, `PYTHONHASHSEED`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONHASHSEED), accessed 2026-10-14.
- Stated purpose per the docs: "Hash randomization is intended to provide protection against a denial-of-service caused by carefully chosen inputs that exploit the worst case performance of a dict construction, O(n²) complexity," and its reproducible-seed mode exists "to allow repeatable hashing, such as for selftests for the interpreter itself, or to allow a cluster of python processes to share hash values" — [Python 3 docs, `PYTHONHASHSEED`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONHASHSEED), accessed 2026-10-14.
- `dict` ordering: as of Python 3.7, "the insertion-order preservation of dict objects has been declared to be an official part of the Python language spec," required of all conformant implementations (it was a CPython 3.6 implementation detail before that) — [Python Morsels, summarizing Python 3.7 changelog / language spec](https://www.pythonmorsels.com/dictionaries-are-ordered/), accessed 2026-10-14.
- `set` ordering: sets "are implemented as hash tables with no extra mechanism to track insertion order, with no order guarantee"; apparent stability for small runs is not a guarantee — [search-summarized community sources on Python set internals](https://switowski.com/blog/ordered-dictionaries/), accessed 2026-10-14 (see Gaps re: lack of a single authoritative quote).

### Inferences
- The practical consequence for a blog author: changing `PYTHONHASHSEED` between runs can change the iteration order of a `set` (and of `dict` keys only insofar as hash collisions affect internal slot placement for keys that are *not* insertion-ordered-relevant — but CPython's `dict` preserves insertion order as a language guarantee independent of hashing, so `dict` iteration order is **not** affected by `PYTHONHASHSEED`, while the internal **hash value** of its string/bytes keys still is). The clean statement: `dict` iteration order is guaranteed by insertion order since 3.7 (hash-seed-independent); `set` iteration order is hash-table-slot-dependent and therefore can change when `PYTHONHASHSEED` changes.
- "Fixing a seed" for reproducibility purposes (e.g., `random.seed(42)`) is a completely different mechanism from `PYTHONHASHSEED` — the former controls a PRNG's output stream, the latter controls the *hash function* used internally by the interpreter for `str`/`bytes`/etc. A program can produce identical `random` output across runs while still having different `set`-iteration order run-to-run, unless `PYTHONHASHSEED` is also fixed. This is an important distinction for a reproducibility-focused blog post.

### Gaps
- Did not find a single official CPython documentation page stating in one place "set iteration order depends on PYTHONHASHSEED" — this is well-established community knowledge and a direct, testable consequence of PEP 456 (set is hash-table-ordered; dict is insertion-ordered since 3.7), but the specific causal link to PYTHONHASHSEED for `set` was synthesized from PEP 456 + general set/dict ordering docs rather than one explicit NIST/CPython sentence. A blog author should verify this empirically (e.g., run the same `set` literal under different `PYTHONHASHSEED` values) before stating it as settled fact, though it follows directly from how CPython implements `set`.

## Virtualization/container layer: does Docker or a VM change where entropy comes from? What is virtio-rng?

### Takeaway
A Docker container shares the host's kernel and therefore its single kernel CSPRNG — `/dev/urandom` inside a container is the same kernel-level generator as on the host, not a container-local instance — while a full VM has its own guest kernel and guest entropy pool that can suffer slow/cold-start entropy unless the hypervisor supplies entropy via a paravirtual channel called virtio-rng.

### Cited Findings
- Containers "still use the host Linux kernel" despite having isolated filesystem/process/network namespaces — [dev.to, "Containers Are Isolated, But They Still Share the Kernel"](https://dev.to/muzasio/containers-are-isolated-but-they-still-share-the-kernel-j5c), accessed 2026-10-14.
- Regarding `/dev/urandom` specifically in containers: it is considered secure to share across containers because of its "stateless nature," meaning "even if two containers share the same device, they cannot predict or influence the output from another device node within another container"; however this is a shared *device*, not a namespace-isolated instance — some security literature notes a "theoretical possibility that a malicious container can predict the random output for another container or a host," and that a complete fix would require "a separate random device per namespace or even introduce a namespace for (pseudo)random number generators" (not implemented in mainline Linux as of these sources) — [search-summarized academic/technical sources on container RNG sharing], accessed 2026-10-14 (see Gaps — no single authoritative primary source found; treat with caution).
- virtio-rng is "a random number generator device that provides KVM virtual machines access to entropy from the host machine" — [search summary of QEMU/virtio-rng mailing list and Red Hat documentation](https://www.redhat.com/en/blog/red-hat-enterprise-linux-virtual-machines-access-random-numbers-made-easy), accessed 2026-10-14.
- QEMU's virtio-rng backend should be configured to draw from the host's `/dev/urandom` rather than `/dev/random`, because `/dev/urandom` is "(1) non-blocking, (2) draws from multiple entropy sources and effectively cannot run out and block other processes, and (3) works well enough for all but the most highly-demanding cryptographically security-sensitive applications"; this recommendation is attributed to Ted Ts'o (original `/dev/random` author), noting that on host systems with many hardware devices, `/dev/urandom` initializes "very quickly before any VMs are started" — [QEMU/virtio-rng mailing list discussion summary](https://lists.sr.ht/~philmd/qemu/patches/3941), accessed 2026-10-14.
- VM environments can suffer entropy starvation especially at early boot, since they often lack the physical interrupt-timing jitter (disk, keyboard, etc.) that seeds a bare-metal kernel's entropy pool; the recommended mitigation is hypervisor-supplied entropy via virtio-rng and/or CPU RDRAND — [Exoscale blog, "How to ensure entropy and proper random number generation in virtual machines"](https://www.exoscale.com/blog/random-numbers-generation-in-virtual-machines/), accessed 2026-10-14.
- The modern Linux kernel RNG rewrite added a specific VM-cloning defense (VMGENID/`vmgenid` via ACPI): "If the ID changes, the kernel mixes the ID into the entropy pool, changing it and thus making it unique," preventing cloned/snapshotted VM instances from producing identical RNG output streams — [The Register](https://www.theregister.com/2022/03/21/new_linux_kernel_has_improved/), accessed 2026-10-14.

### Inferences
- For the blog's audience: "does Docker change where my Python program's randomness comes from" — the answer is essentially no, as long as the container runs on the same host kernel (the normal Docker case on Linux): `os.urandom()` inside the container still resolves to the same host kernel CSPRNG (via `getrandom()`/`/dev/urandom`), because containers do not have their own kernel. The situation is different for a full VM (e.g., a cloud instance), where the guest has its own independent kernel RNG state that must itself be seeded — that's what virtio-rng is for.
- A nuance worth flagging to readers: identical/cloned containers or VM snapshots historically risked generating identical "random" sequences if they resumed from an identical entropy-pool state; the VMGENID mechanism in the modern Linux RNG is a direct fix for the VM-cloning case, but containers sharing a host kernel don't have an exact analogue of this problem since they're not restoring a serialized kernel RNG state the way a VM snapshot does.

### Gaps
- Could not locate a single authoritative, citable primary source (official Docker documentation, Moby project docs, or a peer-reviewed systems paper with a clear DOI/stable URL) stating in plain terms "containers share the host's single kernel CSPRNG instance for /dev/urandom." The claim is corroborated by multiple secondary/community technical sources and is consistent with basic container architecture (no kernel namespace isolation for the RNG subsystem), but a blog author citing this specific point should treat it as reasoned from container architecture fundamentals rather than a single quotable Docker-official statement.

## What does "fixing a seed" actually accomplish in terms of this stack — which layers get bypassed, which still participate?

### Takeaway
Fixing a seed (e.g., `random.seed(42)`) only overrides the *input* to CPython's software-level Mersenne Twister PRNG — it bypasses the OS CSPRNG call that would otherwise supply that input, but it does not touch, disable, or bypass any layer below `random.seed()`: the CPU TRNG, the kernel CSPRNG, `os.urandom()`, and `PYTHONHASHSEED`'s SipHash key all continue to operate (or remain available) exactly as they would without a fixed seed, for every other randomness consumer in the same process.

### Cited Findings
- `random.seed(a=None, version=2)`: supplying a non-`None` `a` is precisely what *replaces* the code path that otherwise reads "randomness sources ... provided by the operating system" (i.e., `os.urandom()`) — [Python 3 docs, `random.seed`](https://docs.python.org/3/library/random.html#random.seed), accessed 2026-10-14 (same citation as above, re-applied to this synthesis question).
- The hardware/kernel CSPRNG stack (Intel DRNG → RDRAND/RDSEED; kernel CRNG via ChaCha20/BLAKE2s; `getrandom()`/`os.urandom()`) exists and runs continuously regardless of what any single userspace program does with its own PRNG seed — none of the sources above describe any mechanism by which a Python-level `random.seed()` call reaches down into or alters kernel or hardware RNG state; they are architecturally one-directional (kernel/hardware supplies entropy *up* to `os.urandom()`, which `random.seed(None)` optionally reads *once*, at seed time) — synthesized from [Intel DRNG Guide](https://www.intel.com/content/www/us/en/developer/articles/guide/intel-digital-random-number-generator-drng-software-implementation-guide.html), [kernel-internals.org](https://kernel-internals.org/crypto/rng/), and [Python random.seed docs](https://docs.python.org/3/library/random.html#random.seed), all accessed 2026-10-14.
- `PYTHONHASHSEED` is an entirely separate control, set via environment variable *before* the interpreter starts, governing the SipHash key used for `hash()` of `str`/`bytes`/etc. for the lifetime of the process; fixing `random.seed()` inside a running program has no documented effect on this hash key, and conversely setting `PYTHONHASHSEED` has no documented effect on the Mersenne Twister state used by `random` — [PEP 456](https://peps.python.org/pep-0456/) and [Python 3 docs, `PYTHONHASHSEED`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONHASHSEED), accessed 2026-10-14.

### Inferences
- Layer-by-layer summary for the blog post (synthesized, not a single external citation, but each component traces to the findings above):
  - **Silicon (Intel DRNG / ARM FEAT_RNG):** always runs; unaffected by `random.seed()`. Still backs any `os.urandom()` call elsewhere in the same program, and backs the kernel's own entropy mixing.
  - **Kernel CSPRNG (ChaCha20/BLAKE2s CRNG, `/dev/urandom`, `getrandom()`):** always runs; unaffected by `random.seed()`. Continues to serve any other process or any other `os.urandom()` call in the same process.
  - **CPython's `os.urandom()` call path:** *bypassed specifically* by a fixed seed — this is the one call `random.seed(a)` with non-`None` `a` skips, since there is no need to ask the OS for entropy when the caller supplies the seed value directly.
  - **`random.seed()` / Mersenne Twister state:** this is what actually changes — a fixed seed makes the *entire subsequent output stream* of that `random.Random` instance deterministic and reproducible across runs/machines (for the same Python version's algorithm).
  - **`PYTHONHASHSEED` / SipHash key:** independent axis, not touched by `random.seed()`; must be fixed separately (and only at process start, via environment variable) if a reproducibility story also requires deterministic `set` iteration order or deterministic `str`/`bytes` `hash()` values.
- Net statement for the audience: "not fixing a seed" means your program's one-time ask to the OS CSPRNG (which itself is backed by the kernel's continuously-reseeded ChaCha20 generator, which is itself periodically fed by CPU TRNG output and other entropy sources) determines your PRNG's trajectory; "fixing a seed" means you supply that one value yourself and the OS/kernel/hardware chain is never consulted for *that* PRNG instance — but it keeps running for everything else on the machine (other processes, other seedings, TLS/crypto libraries, the kernel itself, etc.).

### Gaps
- No single external source states this full seven-layer summary end-to-end (it is necessarily a synthesis across the hardware, NIST, kernel, and CPython findings above); a blog author should present it as reasoned synthesis, not as a verbatim claim from any one cited document.
