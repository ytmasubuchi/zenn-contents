# Why LLM Inference Is Nondeterministic Even at Temperature 0, and What Temperature Actually Controls

## Batch invariance: the Thinking Machines Lab argument

### Takeaway
Thinking Machines Lab's September 10, 2025 research-blog post "Defeating Nondeterminism in LLM Inference" (by Horace He et al., first post on their "Connectionism" blog) argues that the dominant cause of nondeterministic greedy/temperature-0 LLM inference is **lack of batch invariance** in GPU kernels: a given request's numerical result depends on the batch size/shape it happens to be processed with, because reduction order inside RMSNorm, matmul, and attention kernels changes with batch size. They built batch-invariant kernels (open-sourced) and report going from 80 unique completions to 1 (bitwise-identical) across 1,000 greedy completions on Qwen3-235B.

### Cited Findings
- Source type: **engineering/research blog post** (not peer-reviewed), published by Thinking Machines Lab on its research blog "Connectionism," authored principally by Horace He, dated September 10, 2025. — [Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) (accessed 2026-10-14)
- Thinking Machines Lab announced the post as the launch of their research blog on X/Twitter, confirming authorship/venue. — [Thinking Machines on X](https://x.com/thinkymachines/status/1965826369721623001) (accessed 2026-10-14)
- Core claim, quoted: "the primary reason nearly all LLM inference endpoints are nondeterministic is that the load (and thus batch-size) nondeterministically varies!" — [Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) (accessed 2026-10-14)
- The post explicitly frames the common "concurrency + floating point non-associativity" explanation as **incomplete/wrong as usually stated** — floating-point non-associativity alone doesn't explain nondeterminism on a *single* sequence run alone; it only becomes visible because kernels are not "batch-invariant," i.e., the per-example numerical result changes depending on what else is in the batch. — [Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) (accessed 2026-10-14)
- They define batch invariance as: "the reduction order for each element must be fixed regardless of the batch-size of the kernel," and identify three kernel types in a transformer forward pass where this matters: **RMSNorm, matrix multiplication (matmul), and attention**. — [Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) (accessed 2026-10-14)
- RMSNorm: a batch-invariant strategy assigns one batch element per core (data-parallel across the batch dimension), which preserves a fixed reduction order regardless of batch size, at the cost of underutilizing cores for very small batches. — [Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) (accessed 2026-10-14)
- Matmul: standard "data-parallel" kernels tile the output matrix and let each core own a tile's full dot product/reduction, which is batch-invariant; but production kernels often use **Split-K** strategies (parallelizing along the reduction/K dimension, common for small-batch performance) which **break** batch invariance because the reduction is split and recombined differently depending on shape. Thinking Machines' batch-invariant matmul avoids Split-K, reporting roughly a 20% slowdown versus cuBLAS. — [Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) (accessed 2026-10-14)
- Attention: described as the hardest case because it has **two reduction dimensions** (the feature dimension and the sequence/KV-length dimension). Key quote (paraphrased from fetch): "when processing the 1000th query token in a sequence, the reduction order must be identical regardless of whether 0 tokens are in the KV cache (prefill) or 999 tokens are in the KV cache (decoding)." Standard "Split-KV"/FlashDecoding-style kernels use a variable number of splits depending on how many KV tokens there are (and depending on chunked-prefill boundaries), which breaks invariance; their fix is a **fixed split-size** scheme that keeps the reduction order identical regardless of the KV cache length / chunked-prefill boundary, and they update the KV cache and page table **before** the attention kernel runs so that keys/values are laid out consistently. — [Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) (accessed 2026-10-14)
- Reported experimental result: on Qwen/Qwen3-235B at temperature 0, standard vLLM produced **80 unique completions out of 1,000** identical-prompt samples; with all three kernels replaced by batch-invariant versions, **all 1,000 completions were bitwise identical**. — [Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) (accessed 2026-10-14)
- Reported performance cost: an unoptimized deterministic implementation on Qwen3-8B took ~55s vs ~26s for standard vLLM (≈2.1× slower); an optimized version with better attention kernels brought this down to ~42s. — [Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) (accessed 2026-10-14)
- They also argue this enables **bitwise-identical training/inference numerics**, which they say gives "true on-policy RL" (zero KL divergence between the sampling policy and the training policy) instead of needing off-policy correction (e.g., importance sampling). — [Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) (accessed 2026-10-14)
- Thinking Machines Lab open-sourced a companion PyTorch library, `batch_invariant_ops`, which substitutes batch-invariant kernel implementations (RMSNorm, MatMul, Softmax/Attention, etc.) for default PyTorch ops via `torch.Library`, enabling deterministic vLLM inference as a worked example; repo has ~1.1k stars, MIT license. Source type: **code repository**, not a paper. — [GitHub: thinking-machines-lab/batch_invariant_ops](https://github.com/thinking-machines-lab/batch_invariant_ops) (accessed 2026-10-14)
- vLLM itself is actively implementing this: GitHub issue/tracker #27433 ("[Feature]: Batch Invariant Feature and Performance Optimization") tracks adding batch-invariant kernels to vLLM, explicitly citing Thinking Machines Lab's blog post, with in-progress support for FlashInfer backend, DeepSeek-V3/R1, torch.compile integration, TRITON_MLA, and community testing across A10/A100/H100/GB300/RTX 4090 GPUs (as of accessed date, still marked in progress, not fully shipped for all model/backend combinations). — [vLLM GitHub Issue #27433](https://github.com/vllm-project/vllm/issues/27433) (accessed 2026-10-14)
- sglang (a competing inference engine) opened an analogous feature-tracking issue, "[Feature] Support deterministic inference with Batch Invariant Ops," and LMSYS Org (sglang's team) separately published a blog post "Towards Deterministic Inference in SGLang and Reproducible RL Training" (2025-09-22), indicating the batch-invariance framing was adopted industry-wide almost immediately after the Thinking Machines post. Source type: engineering blog / GitHub issue. — [sglang GitHub Issue #10278](https://github.com/sgl-project/sglang/issues/10278); [LMSYS Org blog](https://www.lmsys.org/blog/2025-09-22-sglang-deterministic/) (accessed 2026-10-14)

This is a **preprint, not peer-reviewed**; could not confirm from the fetch whether it predates or cites the Thinking Machines post, or the exact relationship between the two (see Gaps). — [arXiv:2506.09501](https://arxiv.org/pdf/2506.09501) (accessed 2026-10-14)

## Mechanism: how batch size changes reduction order (split-K/stream-K GEMM; attention over KV length)

### Takeaway
GPU matmul and attention kernels parallelize "reduction" dimensions (the inner/contraction dimension in matmul; the KV-length dimension in attention) across multiple cores/thread-blocks when a single query or small batch wouldn't otherwise saturate the GPU; the number and boundaries of these parallel splits are chosen dynamically based on the problem shape (which depends on batch size and, for attention, on how many KV tokens already exist / how prefill is chunked), and recombining the resulting partial sums in a different order or different split count changes the floating-point rounding — flipping bits even though the "same" mathematical sum is computed.

### Cited Findings
- Matmul result for a given row/vector can be bitwise different depending on whether it's run alone (batch size 1) or embedded in a larger batch, because the kernel picks a different tiling/parallelization strategy and floating-point addition is **not associative** — summing the same set of numbers in a different order can yield a different rounded result. — [On the Structure of Floating-Point Noise in Batch-Invariant GPU Matrix Multiplication, arXiv:2511.00025](https://arxiv.org/pdf/2511.00025) (preprint; accessed 2026-10-14)
- **Split-K**: a GEMM strategy that parallelizes work along the reduction (K) dimension across multiple thread blocks/cores — useful when the batch/output dimensions are too small to otherwise keep the GPU busy (e.g., small-batch decode steps) — then combines the partial sums, often via atomic adds, in whatever order threads finish (non-deterministic order) or in an order that depends on how many splits were chosen (which depends on batch shape). This breaks batch invariance because the reduction is carried out differently depending on batch size. — [Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) (accessed 2026-10-14)
- A batch-invariant matmul instead uses a **fixed data-parallel tiling**: divide the output into 2D tiles, and have one core handle the *entire* dot product/reduction for its tile regardless of batch size, so the reduction order never changes as batch size changes (at a performance cost for small batches, since some cores sit idle rather than help with Split-K). — [Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) (accessed 2026-10-14)
- A follow-on preprint ("Accelerating the Mitigation of LLM Inference Nondeterminism Across GPU Architectures," Liam Cooper, Shinnung Jeong, Hyeran Jeon, Jeffrey Young, Hyesoon Kim; Georgia Tech / UC Merced; arXiv:2609.25624, posted 2026-09-22; **preprint, not peer-reviewed**) proposes a **deterministic split-K** scheme as an alternative to atomic-based split-K: "small-batch decode shapes use a deterministic split-K scheme whose partial sums are combined in a fixed ascending order with no atomics" — i.e., keep the performance benefit of splitting the reduction, but fix the combination order so results don't depend on scheduling/batch size. — [arXiv:2609.25624](https://arxiv.org/html/2609.25624v1) (accessed 2026-10-14)
- That same paper reports that unmitigated BF16 inference diverges on 31–100% of test problems across different GPU architectures (A100, L40S, H100) due to each architecture selecting different matmul kernels/reduction orders, and that their deterministic-split-K + mitigations achieve bitwise-identical outputs across all three architectures, with reported 1.17–3.1× end-to-end speedup over "prior state of the art" determinism approaches. — [arXiv:2609.25624](https://arxiv.org/html/2609.25624v1) (accessed 2026-10-14)
- **Attention / KV-length reduction**: attention requires a running reduction (softmax normalization + weighted sum of values) over the key/value sequence length. Kernels like FlashAttention/"FlashDecoding"-style approaches split the KV sequence into chunks across parallel workers ("Split-KV") to use the GPU efficiently, especially during decoding when there's only one query token but potentially thousands of KV tokens. The **number of splits is typically chosen dynamically** based on how many KV tokens exist (which grows every decoding step) and, in **chunked prefill** or **paged-attention** setups, based on how the request's tokens are chunked relative to other concurrent requests' chunks in the same scheduler step. This means the same query token's attention reduction can be split into a different number of pieces, recombined in a different order, depending on how much is in the KV cache at that moment and what else is being processed concurrently — producing different floating-point rounding for mathematically the same attention output. — [Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) (accessed 2026-10-14)
- Thinking Machines Lab's fix: use a **fixed split-size** (not fixed split-*count*) strategy for attention, so the reduction order for a given query position's attention output is identical whether it's being computed with 0 KV-cache tokens (prefill) or 999 KV-cache tokens (decode) — and update the KV cache / page table *before* invoking the attention kernel so that the physical layout of keys/values is always consistent regardless of request-batching patterns. — [Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) (accessed 2026-10-14)
- **Stream-K**: searches did not surface a primary source discussing Stream-K specifically in the LLM-determinism context within the sources fetched; this term is well known in the GPU kernel literature (CUTLASS) as a generalization of split-K that further rebalances the reduction dimension across SMs for better load balancing, but no fetched source in this research session explicitly analyzed Stream-K's effect on batch invariance. Flagged as a gap below.

### Inferences
- The unifying mechanism across matmul and attention is the same: **whenever a kernel chooses to parallelize/split a reduction (sum) differently depending on the problem's shape (batch size, KV length, chunk boundaries), floating-point non-associativity turns "same math, different split strategy" into "different bits."** The batch-invariance fix is always the same pattern: fix the reduction's granularity/order independent of shape, typically at a performance cost.
- Chunked prefill and paged/continuous-batching schedulers are specifically implicated because they make a request's "shape" (how many of its tokens are processed together, what else shares the GPU step) depend on *scheduling decisions driven by concurrent traffic*, not just on the request itself — this is the direct link between "continuous batching" and "nondeterminism," addressed in the next section.

### Gaps
- Could not find a primary/official source specifically discussing **Stream-K** GEMM in the context of LLM inference determinism (as distinct from generic CUTLASS/Triton kernel-design literature). The research session's fetched sources discussed Split-K and Split-KV/FlashDecoding in detail but not Stream-K by name; do not assert Stream-K-specific claims beyond this.

## Greedy decoding and logit margins

### Takeaway
At temperature 0, the output token is `argmax` of the logit vector; a floating-point perturbation only changes the output if it's large enough to flip which logit is largest, which in practice only happens at positions where the top-1 and top-2 logits are nearly tied (a small "decision margin") — and because autoregressive decoding feeds each token back in as input, a single flipped token early in generation can cascade into a completely different continuation. Multiple 2026 preprints quantify this: flips are reported at roughly 0.3–1.3% of decode steps, concentrated almost entirely at near-tied positions.

### Cited Findings
- Formal framing: "A greedy token flips between two [numerically different executions] only when the hardware/kernel perturbs the top-1/top-2 logit difference by more than that difference itself," with "decision margin" at position *t* defined as the logit gap between the best and second-best candidate token. — [Accelerating the Mitigation of LLM Inference Nondeterminism Across GPU Architectures, arXiv:2609.25624](https://arxiv.org/html/2609.25624v1) (preprint; accessed 2026-10-14)
- That paper reports that **approximately 1% of token positions sit within 0.1 nats of a decision tie**, with a near-linear tail distribution of margins below that threshold — i.e., most positions have a comfortably large margin, but a consistent ~1% tail is "at risk" of flipping under small numerical perturbation. — [arXiv:2609.25624](https://arxiv.org/html/2609.25624v1) (accessed 2026-10-14)
- MarginGate (Kexin Chu, Yang Zhou, Wei Zhang; Univ. of Connecticut / UC Davis; arXiv:2605.30218, submitted 2026-05-28; **preprint**) directly measures batch-induced token flips in BF16 greedy decoding: flips occur in only **0.3–1.3% of synchronous decode steps** across five models and three benchmarks; on Llama-3.1-8B specifically, flips appear in just **0.48% of synchronous decode steps on MATH500**. — [MarginGate, arXiv:2605.30218](https://arxiv.org/html/2605.30218v1) (accessed 2026-10-14)
- MarginGate also shows that divergent (flip-prone) steps have measurably different logit-margin statistics than stable steps: at a margin threshold Δ=1.0, stable steps average only ~1.1 logits within that margin of the top one, while divergent steps average 2.3–2.7 (a 1.7–3.0× enrichment) — i.e., flips are concentrated exactly where a second near-tied candidate exists, as theory predicts. — [MarginGate, arXiv:2605.30218](https://arxiv.org/html/2605.30218v1) (accessed 2026-10-14)
- MarginGate further shows that selectively re-verifying only risky (low-margin) steps — rather than every step — can achieve full determinism while triggering verification on only ~18.56% of decode steps for Llama-3.1-8B and ~15.05% for Qwen2.5-14B, reducing overhead versus a "verify-every-token" baseline (which the paper calls "LLM-42") by 2.23× and 1.99× respectively. — [MarginGate, arXiv:2605.30218](https://arxiv.org/html/2605.30218v1) (accessed 2026-10-14)
- A separate preprint, "Greedy Decoding Is Not Precision-Invariant: Cross-Precision Output Divergence in LLM Inference" (Gaoyuan Du, Anam Nawaz Khan, Rex Zhou, Xiaoyang Liu, Deepayan Chakrabarti, Fnu Suya, Xueping Li; arXiv:2609.26621, Sept 2026; **preprint**) shows that running the *same* model/prompt in fp16 vs. bf16 vs. fp32 produces systematically different greedy token choices, not just random noise — the mechanism given is the same logit-margin-sensitivity argument (narrow top-1/top-2 margins + precision-dependent rounding → different argmax). Exact percentage figures were not extractable from the available fetch. — [arXiv:2609.26621](https://arxiv.org/pdf/2609.26621) (accessed 2026-10-14)
- Mitigation noted in the literature: computing in FP32 even when weights are stored in BF16 shrinks per-operation rounding error enough that near-tie argmax flips become rare (qualitative claim from the fetched summary of arXiv:2609.25624's mitigation strategy, consistent with its reported bitwise-identical cross-GPU results). — [arXiv:2609.25624](https://arxiv.org/html/2609.25624v1) (accessed 2026-10-14)

### Inferences
- The "single flipped token cascades into a fully different continuation" claim is a structural/logical consequence of autoregressive decoding (each generated token becomes part of the input context for all subsequent tokens) rather than something these papers needed to separately measure — but the *measured* fact that flips are rare-but-nonzero (0.3–1.3% of steps) means that for long generations the *probability that at least one flip occurs somewhere in the sequence* compounds and can become large even though per-token flip probability is low. (This specific "at least one flip in N tokens" compounding claim was not directly quantified in any fetched source — treat as inference, not citation.)
- Because flips concentrate at near-tied logit positions, tasks/domains that produce more "uncertain" or close calls between tokens (open-ended creative text, code with multiple valid stylistic choices, borderline classification) should show higher real-world divergence rates than tasks with highly peaked distributions (e.g., copying, simple arithmetic), though no fetched source directly measured this correlation.

- No fetched source gave a single, clean, oft-cited "X% of all greedy generations diverge end-to-end" statistic from a top-tier peer-reviewed venue; all the quantitative figures above come from 2026 arXiv preprints (MarginGate, the Georgia Tech/UC Merced paper, and the cross-precision paper) that have not been confirmed as peer-reviewed. Label these clearly as preprint-sourced measurements, not established/peer-reviewed consensus figures.

## Temperature: what it does mathematically and its effect on reproducibility

### Takeaway
Temperature rescales logits before softmax (`softmax(logits / T)`); at `T=0` this operation is mathematically undefined (division by zero), so real systems special-case `T=0` to mean "skip sampling and take argmax" (greedy decoding) rather than literally dividing by zero — vLLM's source does this explicitly via an epsilon threshold. For `T>0`, a seeded RNG makes the *sampling draw* reproducible in principle, but reproducibility still requires the logits themselves to be reproducible (fixed batch shape/kernels/hardware/dtype), and higher temperature generally makes output *sequences* more sensitive to any remaining nondeterminism in the logits, not less, because it flattens the probability distribution and makes the exact sampled token more sensitive to the precise (possibly perturbed) probability values and to the specific pseudorandom draw.

### Cited Findings
- vLLM's official `SamplingParams` documentation states for `temperature`: "Controls the randomness of the sampling. Lower values make the model more deterministic, while higher values make the model more random. Zero means greedy sampling." — [vLLM SamplingParams docs, v0.11.0](https://docs.vllm.ai/en/v0.11.0/api/vllm/sampling_params.html) (official vendor documentation; accessed 2026-10-14)
- vLLM's implementation detail (from source, as surfaced via the docs fetch): when `temperature` drops below an internal constant `_SAMPLING_EPS` (1e-5), vLLM forces `top_p=1.0`, `top_k=0`, `min_p=0.0`, and requires `n=1`, effectively routing the request to greedy/argmax decoding rather than literally dividing logits by ~0. If temperature is between 0 and an internal `_MAX_TEMP` (0.01) but not exactly 0, vLLM logs a warning and clamps temperature up to 0.01 "to prevent numerical errors." This directly answers "what do real implementations do at temperature=0": **vLLM switches to greedy decoding via an epsilon threshold, it does not compute `logits/0`.** — [vLLM SamplingParams docs, v0.11.0](https://docs.vllm.ai/en/v0.11.0/api/vllm/sampling_params.html) (accessed 2026-10-14)
- vLLM's `sampling_type` classification confirms three modes: `GREEDY` (temperature < 1e-5, deterministic given fixed kernels/logits), `RANDOM_SEED` (an explicit seed is provided, reproducible given fixed logits), and `RANDOM` (default, non-deterministic/unseeded). — [vLLM SamplingParams docs, v0.11.0](https://docs.vllm.ai/en/v0.11.0/api/vllm/sampling_params.html) (accessed 2026-10-14)
- Hugging Face `transformers` documentation: "`generate` uses greedy search decoding by default so you don't have to pass any parameters to enable it. This means the parameters `num_beams` is set to 1 and `do_sample=False`." Multinomial (temperature/top-k/top-p) sampling is enabled by setting `do_sample=True`. This confirms that in `transformers`, **temperature only has an effect when `do_sample=True`**; the library does not expose a literal "temperature=0" sampling mode distinct from `do_sample=False` — the documented way to get deterministic/argmax output is `do_sample=False` (greedy), not "temperature=0 with do_sample=True." — [Hugging Face: Text generation strategies, v4.47.0](https://huggingface.co/docs/transformers/v4.47.0/en/generation_strategies) (official vendor documentation; accessed 2026-10-14)
- `transformers` reproducibility pattern documented: call `from transformers import set_seed; set_seed(0)` (or any integer) before sampling-based generation to get reproducible multinomial sampling; `set_seed` sets the seed in Python's `random`, NumPy, and PyTorch (when installed). — [Hugging Face: Text generation strategies, v4.47.0](https://huggingface.co/docs/transformers/v4.47.0/en/generation_strategies) (accessed 2026-10-14)
- Confirmed from a separate search summary (not a direct quote-level fetch, treat as secondary-source-corroborated): repeated calls to `model.generate(..., do_sample=True)` with the same seed set once will **not** reproduce the same output on the second call unless the seed is reset before each call — `transformers` does not auto-reseed between generations — and for GPU determinism, `torch.cuda.manual_seed()` (or `torch.manual_seed()` covering CUDA) is additionally required, with the caveat that GPU operations can still vary with CUDA version/hardware even with seeds fixed. — [search-aggregated summary citing Hugging Face docs/forums] (accessed 2026-10-14) — **note: this specific claim was not re-verified against a primary-source direct quote in this session; treat as moderately-confident secondary reporting, not a verbatim vendor quote.**
- OpenAI's seed-parameter documentation/cookbook states the seed enables only a "best effort" at determinism (see API section below for exact wording) — directly relevant to "what temperature>0 + a seed actually guarantees."

### Inferences
- "Temperature divides logits before softmax" is the standard, uncontested mathematical definition (`p_i = exp(z_i/T) / sum_j exp(z_j/T)`); none of the fetched sources disputed this, though no single fetched source was captured giving this exact formula in those symbols — it is treated here as textbook-level, uncontested math rather than something requiring a citation beyond confirming vendor behavior around `T=0`/`T→0`.
- Because `T=0` is handled as a special-cased switch to argmax/greedy decoding in both vLLM (explicit epsilon-based branch in `SamplingParams`) and effectively in `transformers` (via `do_sample=False`, a separate code path from multinomial sampling), the claim "temperature=0 means no randomness is drawn from an RNG at all" is **true for the sampling step** — but this is exactly why "temperature=0 ⇒ reproducible" is false in practice: removing *sampling* randomness does nothing about the batch-variant, non-reproducible *logits* feeding into that final argmax (the mechanism described in the earlier sections).
- Raising temperature (`T>0`) does not make divergence *more* likely from the batch-invariance/logit-margin mechanism directly — logits are computed by the same forward pass regardless of `T` — but it changes what "divergence" means: at `T=0`, a small logit perturbation only changes output if it flips the argmax (requires crossing a specific, often-large margin); at `T>0`, *any* change to the logits changes the resulting *probabilities*, and since sampling draws a token proportional to probability, even a tiny probability shift can combine with the specific pseudorandom draw to select a different token — in effect, higher temperature flattens the distribution and makes more tokens "live candidates," increasing the practical surface area over which small numerical differences can change the sampled outcome, even though the *RNG draw itself* is reproducible given a fixed seed and fixed probabilities. This reasoning follows directly from the deterministic-greedy-vs-stochastic-sampling mechanics documented above, but was not itself stated as a single explicit claim in any one fetched source — flagged as an inference, not a found citation.

- No fetched source gave a single authoritative, explicit statement of the exact formula `softmax(z/T)` in vendor documentation (it is implicit/assumed knowledge); the blog author should treat this as standard ML textbook material rather than needing a specific citation, or cite a methods/background source if one is wanted.
- Could not independently re-verify (via direct primary-source quote in this session) the precise `transformers` behavior around re-seeding between successive `generate()` calls and `torch.cuda.manual_seed()` requirements; this came from an aggregated search summary rather than a direct document fetch quote. Treat with slightly lower confidence and ideally re-verify by reading `transformers`' `generation_strategies` or `set_seed` source directly before publishing a precise quote.

## Sampling implementation details: top-k/top-p, multinomial sampling, transformers vs. vLLM

### Takeaway
`transformers`' documented API surface distinguishes greedy (`do_sample=False`, deterministic) from multinomial/top-k/top-p sampling (`do_sample=True`, requires `set_seed` for reproducibility, and does not auto-reseed between calls); vLLM exposes an explicit `seed` field in `SamplingParams` and documents three internal sampling-type branches (GREEDY / RANDOM_SEED / RANDOM), with top_k/top_p/min_p all reset to "disabled" values whenever temperature is treated as zero. Neither vendor's fetched documentation gave an explicit, citable guarantee about tie-breaking determinism in top-k/top-p sorting or about multinomial-sampling device-independence; these points are recorded as gaps below rather than asserted.

### Cited Findings
- vLLM `SamplingParams.seed`: documented simply as "Random seed to use for the generation," type `Optional[int]`; per source, passing `-1` is normalized to `None` (i.e., "no seed"/non-deterministic). — [vLLM SamplingParams docs, v0.11.0](https://docs.vllm.ai/en/v0.11.0/api/vllm/sampling_params.html) (accessed 2026-10-14)
- vLLM `top_k` / `top_p` documented as: `top_k` "Controls the number of top tokens to consider. Set to 0 (or -1) to consider all tokens." `top_p` "Controls the cumulative probability of the top tokens to consider. Must be in (0, 1]. Set to 1 to consider all tokens." — [vLLM SamplingParams docs, v0.11.0](https://docs.vllm.ai/en/v0.11.0/api/vllm/sampling_params.html) (accessed 2026-10-14)
- vLLM explicitly forces `top_p=1.0`, `top_k=0`, `min_p=0.0` whenever temperature is treated as zero (i.e., top-k/top-p filtering is irrelevant/disabled in greedy mode) — see Temperature section above. — [vLLM SamplingParams docs, v0.11.0](https://docs.vllm.ai/en/v0.11.0/api/vllm/sampling_params.html) (accessed 2026-10-14)
- A search-aggregated summary (secondary, not independently re-verified via direct primary quote in this session) states that vLLM and "most modern inference engines" use the **Gumbel-Max trick** for sampling because it is more GPU-efficient than naive multinomial/categorical sampling, and that vLLM has implemented **per-prompt seed mixing**: each seeded request's effective seed is derived by mixing the user-supplied `seed` with the prompt content, so "a prompt's derived seed depends only on the (seed, prompt) pair, independent of batch composition and order" — i.e., vLLM has specifically engineered seeded sampling to *not* depend on what batch a request lands in (for the sampling step itself; this does not address the separate logits-computation nondeterminism discussed above). — [search-aggregated summary; cross-referenced against] [vLLM PR #50884: "Mix per-prompt seeds into seeded SamplingParams in the offline API"](https://github.com/vllm-project/vllm/pull/50884) (accessed 2026-10-14) — **flagged as moderate confidence; the PR title/existence corroborates the mechanism but exact wording was not independently re-fetched and quoted from the PR body itself.**
- `transformers` documented: "if set to `True`, `do_sample` ... enables decoding strategies such as multinomial sampling, beam-search multinomial sampling, Top-K sampling and Top-p sampling. All these strategies select the next token from the probability distribution over the entire vocabulary with various strategy-specific adjustments." — [Hugging Face: Text generation strategies, v4.47.0](https://huggingface.co/docs/transformers/v4.47.0/en/generation_strategies) (accessed 2026-10-14)
- `transformers` documents reproducibility via `set_seed(seed)`, used directly before calling `generate(..., do_sample=True, ...)`, and describes `do_sample=False`/greedy as the deterministic default path requiring no seed. — [Hugging Face: Text generation strategies, v4.47.0](https://huggingface.co/docs/transformers/v4.47.0/en/generation_strategies) (accessed 2026-10-14)
- An independent arXiv paper on cross-request effects in classifiers (not generation per se, but directly on-point for "does the sampling/inference implementation depend on device or batch") found that under **dynamic 8-bit integer quantization**, batch composition can change a model's output for a fixed input — because "the activation scale is computed over the whole batch, so the content of the other examples reaches the target through that shared scale" — producing up to ~3.7 percentage points of label flips at batch size 256 in their test setup; critically, they report this effect **disappears under full floating-point precision**, i.e., it's a quantization-specific batch-dependency, distinct from (additive to) the batch-invariance-of-reduction-order mechanism from Thinking Machines Lab. — [Same Text, Different Prediction: Serving-Context Nondeterminism in Text Classifiers, arXiv:2610.09111](https://arxiv.org/html/2610.09111) (workshop-accepted at NeurIPS 2026 workshops LIGHT/ODI/TAE — i.e., workshop-level peer review, not main-conference peer review; authors Santhosh Kumar Kasa and Siva Rajesh Kasa, Amazon; accessed 2026-10-14)

### Inferences
- The vLLM per-prompt seed-mixing mechanism (if the PR's stated intent is accurate) is a direct, explicit vendor acknowledgment that *without* such mixing, a seeded sampling draw's outcome **would** depend on batch composition/order — which is strong indirect evidence for the broader claim that naive multinomial/seeded-sampling implementations on GPUs are not inherently batch-order-independent, and had to be specifically engineered to be so.
- Neither vendor's documentation (as fetched) makes an explicit claim about deterministic tie-breaking in top-k/top-p sorting (e.g., what happens when two tokens have exactly equal logits at the top-k cutoff boundary) — this is a genuine documentation gap, not just a gap in this research pass.

## Continuous batching / paged attention: cross-request dependence

### Takeaway
Continuous batching (vLLM's signature serving optimization) and paged/chunked-prefill attention mean that a single request's exact computational "shape" at each decoding step — how many other sequences share the GPU step, how its tokens are chunked relative to others — is determined by a scheduler reacting to whatever concurrent traffic exists at that moment; combined with the batch-invariance mechanism above, this is the direct causal chain from "unrelated concurrent requests" to "this request's output changed." Official/primary acknowledgment of the *general* batching-causes-nondeterminism link is well documented (Thinking Machines Lab, vLLM's own batch-invariance tracking issue); a specific GitHub bug report of request-level nondeterminism in vLLM was found but without a maintainer technical diagnosis.

### Cited Findings
- vLLM's own engineering blog post, "Inside vLLM: Anatomy of a High-Throughput LLM Inference System," describes continuous batching: requests join and leave the in-flight batch dynamically every decode step (rather than waiting for a static batch to fully complete), and PagedAttention manages the KV cache as fixed-size "pages" (16 tokens per block by default) allocated on demand, potentially non-contiguous, with blocks freed/reused and sequences preempted/recomputed under memory pressure. Source type: **official vendor/engineering blog**, vllm.ai. — [Inside vLLM: Anatomy of a High-Throughput LLM Inference System](https://vllm.ai/blog/2025-09-05-anatomy-of-vllm) (accessed 2026-10-14)
- Combined with the batch-invariance mechanism (see above), this scheduling design is exactly what Thinking Machines Lab's post identifies as the practical cause of nondeterminism: "the primary reason nearly all LLM inference endpoints are nondeterministic is that the load (and thus batch-size) nondeterministically varies" — i.e., because continuous batching means the batch a given request's tokens are computed alongside varies run-to-run based on concurrent traffic, and non-batch-invariant kernels make the numeric result depend on that batch. — [Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) (accessed 2026-10-14)
- A filed vLLM bug report, Issue #11783 ("Continuing a generation is not deterministic"), documents a concrete case: generating text in one continuous pass vs. stopping and resuming generation from the same point (same prompt, same temperature=0) produced divergent token sequences (decoded text diverging at "expressing" vs. "rewriting"). However, **no maintainer gave a technical root-cause diagnosis in the thread**; a maintainer (`moinnadeem`) asked for a reproduction script, and the issue was eventually closed as "not planned" after going stale — i.e., this is a documented *symptom* report, not an *official explanation*. — [vLLM GitHub Issue #11783](https://github.com/vllm-project/vllm/issues/11783) (accessed 2026-10-14)
- vLLM's own feature-tracking issue #27433 for batch-invariant kernels is itself an implicit acknowledgment by the vLLM maintainers/community that standard (non-batch-invariant) vLLM inference is not deterministic under continuous batching, and that fixing it requires the kernel-level changes described above, not a scheduler-level fix alone. — [vLLM GitHub Issue #27433](https://github.com/vllm-project/vllm/issues/27433) (accessed 2026-10-14)

### Inferences
- The causal chain for "why does my output change when other people's requests hit the same server" is: (1) continuous batching + chunked prefill means the scheduler decides, per step, how many sequences/tokens are processed together, driven by whatever concurrent requests exist; (2) PagedAttention means KV cache layout/chunk boundaries for a given request can differ depending on this scheduling; (3) non-batch-invariant attention/matmul/RMSNorm kernels produce different floating-point rounding depending on (1) and (2); (4) at temperature 0 this only becomes *visible* in the final text when a logit-margin flip occurs (per the greedy-decoding section), but it is present in the logits on every single forward pass regardless of whether it happens to flip the argmax that time.
- Issue #11783 is a useful anecdotal illustration for the blog post ("even pausing and resuming the same generation can diverge") even though vLLM maintainers did not confirm the exact mechanism in that thread — the blog author should frame it as "a user-reported symptom consistent with the batch/kernel-shape-dependence mechanism documented by Thinking Machines Lab," not as "vLLM confirmed this specific bug was caused by X."

### Gaps
- Could not find a vLLM official documentation page (as opposed to a blog post or GitHub issue) that directly states, in so many words, "your output may depend on concurrent/unrelated requests on the same server due to continuous batching." The closest primary acknowledgments found are the batch-invariance tracking issue (#27433) and the Thinking Machines Lab post describing the general mechanism; recommend the author cite these rather than imply vLLM's docs contain an explicit warning sentence to this effect, since none was found.

### Cited Findings

## Precision (dtype) and logit-margin sensitivity: fp16 vs bf16 vs fp32

### Takeaway
fp32 has 8 exponent bits and 23 explicit mantissa bits (24 with the implicit leading bit); fp16 has 5 exponent bits and 10 explicit mantissa bits; bf16 has 8 exponent bits (matching fp32's range) but only 7 explicit mantissa bits — the fewest of the three. Fewer mantissa bits means coarser rounding per operation, which directly widens the "noise band" that can erase a close top-1/top-2 logit margin and flip the argmax; bf16, despite matching fp32's dynamic range, is the most precision-starved of the three formats and is explicitly called out in the literature as amplifying rounding-induced argmax flips.

### Cited Findings
- Bit layout: fp32 = 8 exponent bits + 24 mantissa bits (23 explicit + 1 implicit); fp16 (IEEE 754 half precision) = 5 exponent bits + 10 mantissa bits; bf16 (bfloat16, introduced by Google) = 8 exponent bits + 7 mantissa bits — matching fp32's exponent range (and thus dynamic range) but with much less precision than either fp32 or fp16. — [aggregated from multiple secondary technical sources, cross-checked for internal consistency: FP32 8/24, FP16 5/10, BF16 8/7] (accessed 2026-10-14) — note: this bit-count breakdown is standard/uncontested IEEE-754 and Google-bfloat16-spec knowledge; no single primary vendor spec page was fetched directly in this session, so cite as "standard floating-point format specification" if a single authoritative source is needed, and ideally re-verify against the IEEE 754-2019 standard or Google's official bfloat16 documentation before publishing exact bit counts as a direct quote.
- Direct citation on the consequence: "Low-precision formats such as BF16 amplify rounding differences, which can flip the argmax when the top candidate tokens are nearly tied." — [search-aggregated summary of arXiv:2609.25624 and related preprints] (accessed 2026-10-14)
- Mitigation reported in the literature: storing weights in BF16 but performing computation in FP32 shrinks per-operation rounding error down to FP32 level, at which point near-tie argmax flips become rare — this was the described strategy in the Georgia Tech/UC Merced paper's approach to achieving bitwise-identical cross-GPU outputs. — [Accelerating the Mitigation of LLM Inference Nondeterminism Across GPU Architectures, arXiv:2609.25624](https://arxiv.org/html/2609.25624v1) (preprint; accessed 2026-10-14)
- "Greedy Decoding Is Not Precision-Invariant: Cross-Precision Output Divergence in LLM Inference" (arXiv:2609.26621) is directly on point: it demonstrates that running the same model/prompt in fp16 vs bf16 vs fp32 produces systematically different greedy token choices, driven by the same logit-margin mechanism, though exact percentage figures could not be extracted from the fetch in this session (see Gaps in the "Greedy decoding and logit margins" section above). — [arXiv:2609.26621](https://arxiv.org/pdf/2609.26621) (preprint; accessed 2026-10-14)

### Inferences
- Because bf16 has only 7 explicit mantissa bits versus fp16's 10, bf16 rounds each intermediate value to roughly 2^-7 ≈ 0.78% relative precision per step versus fp16's roughly 2^-10 ≈ 0.098% — an order-of-magnitude coarser rounding per operation — which is the quantitative basis for the qualitative claim that "bf16 amplifies rounding differences" relative to fp16. (This specific relative-precision arithmetic is a direct, uncontested consequence of the bit-count figures above, not something that needed a separate citation beyond the bit-count sourcing itself; however, no fetched source presented this exact 2^-7 vs 2^-10 comparison in so many words — it is composed here from the raw bit counts as straightforward arithmetic, flagged as an inference for transparency.)
- Despite having more mantissa bits than bf16, fp16 is still coarser than fp32 (10 vs 23 explicit mantissa bits), so the general ordering of "precision floor" from finest to coarsest is fp32 > fp16 > bf16, which should translate directly into "fp32 computation is least prone to logit-margin-driven argmax flips, bf16 is most prone, with fp16 in between" — consistent with (though not verbatim-quoted from) the cited literature's framing of bf16 as the amplifying case and FP32 as the robust case.

- Could not fetch a single authoritative primary source (IEEE 754 standard text, or Google's original bfloat16 announcement/spec page) directly in this session to put an unambiguous, individually-quotable citation behind the exact bit-count numbers; the numbers themselves (FP32 8/24, FP16 5/10, BF16 8/7) are standard and essentially uncontested in the field, but the author should ideally attach a single canonical reference (e.g., IEEE 754-2019, or Google Cloud's "bfloat16: the secret to high performance on Cloud TPUs" page) before publication rather than relying on the aggregated secondary sourcing used here.
