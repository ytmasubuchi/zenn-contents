# Why Identical CPU Code with Identical Inputs Produces Different Floating-Point Results: SIMD, Threading, and BLAS

Research accessed 2026-10-14 unless otherwise noted. All claims below are sourced inline; items that could not be verified from official documentation are flagged explicitly in "Gaps" subsections.

## NumPy runtime CPU dispatch: how it works, the knobs, and whether results can change

### Takeaway
NumPy ships one build with multiple compiled versions of its inner loops (one per target instruction set) and chooses which compiled version to run at import/call time based on a runtime CPU feature scan. This is officially documented NumPy behavior (not a hack), it is configurable via build options (`--cpu-baseline`, `--cpu-dispatch`) and runtime environment variables (`NPY_DISABLE_CPU_FEATURES`, `NPY_ENABLE_CPU_FEATURES`), and NumPy maintainers have explicitly confirmed in a GitHub issue that different dispatch targets can yield numerically different (non-bitwise-identical) results for the same input.

### Cited Findings
- NumPy's dispatcher is based on "multi-source compiling," i.e., "taking a certain source and compiling it multiple times with different compiler flags and also with different C definitions that affect the code paths," enabling certain instruction sets per compiled object, then linking the resulting objects together — this is literally how one NumPy build contains an SSE2/baseline path and AVX2/AVX-512 paths simultaneously. — [How does the CPU dispatcher work? — NumPy v1.24 Manual](https://numpy.org/doc/1.24/reference/simd/how-it-works.html)
- "Baseline features" (`--cpu-baseline`) are the minimal set of required optimizations with no preprocessor guards — always on, usable anywhere. "Dispatch-able features" (`--cpu-dispatch`) are the additional optimizations that are not active by default and are selected via code marked `/*@targets avx2 avx512f vsx2 vsx3 asimd asimdhp */` in special `.dispatch.c` source files; NumPy builds a separate object per target and links them, with runtime logic choosing which to call. — [How does the CPU dispatcher work? — NumPy v1.24 Manual](https://numpy.org/doc/1.24/reference/simd/how-it-works.html)
- Default build options: `--cpu-baseline` default is `min` (minimum CPU features for broad platform compatibility: e.g. SSE2 baseline on x86-64); `--cpu-dispatch` default is `max -xop -fma4` (essentially all CPU features except AMD legacy XOP/FMA4). Example: `python -m build --wheel -Csetup-args=-Dcpu-baseline="avx2 fma3"`. — [CPU build options — NumPy v2.2 Manual](https://numpy.org/doc/2.2/reference/simd/build-options.html)
- Runtime restriction via environment variable: "Importing NumPy triggers a scan of the available CPU features from the set of dispatchable features. You can restrict this scan by setting the environment variable `NPY_DISABLE_CPU_FEATURES` to a comma-, tab-, or space-separated list of features to disable," e.g. `NPY_DISABLE_CPU_FEATURES="AVX2,FMA3"` (or, on current NumPy, a whole feature-group alias like `X86_V4`). This raises an error if the feature wasn't enabled via `cpu-dispatch` at build time, or emits a warning if the feature isn't available on the current CPU anyway. — [CPU build options — NumPy v2.2 Manual](https://numpy.org/doc/2.2/reference/simd/build-options.html); confirmed on the current stable docs as well — [CPU build options — NumPy stable Manual](https://numpy.org/doc/stable/reference/simd/build-options.html)
- `NPY_ENABLE_CPU_FEATURES` is the inverse "allow-list" mechanism: with it set, NumPy defaults to its compiled baseline and then enables only the dispatch features named in the variable if they are detected on the running CPU. Motivation given in the NumPy enhancement proposal: letting an operator force an identical, homogeneous CPU-feature set across heterogeneous machines by setting the same `NPY_ENABLE_CPU_FEATURES` value everywhere, rather than always auto-selecting the fastest available path per machine (which is precisely the mechanism that causes machine-to-machine divergence). `NPY_DISABLE_CPU_FEATURES` and `NPY_ENABLE_CPU_FEATURES` are mutually exclusive; baseline features can't be disabled; requesting a feature the CPU doesn't actually have raises `RuntimeError`. — [ENH: Add an "opt-in" feature in NumPy for CPU features, `NPY_ENABLE_CPU_FEATURES` · Issue #22058 · numpy/numpy](https://github.com/numpy/numpy/issues/22058); [PR #22137 adding `NPY_ENABLE_CPU_FEATURES`](https://github.com/numpy/numpy/pull/22137)
- `numpy.show_config()` is the documented introspection entry point: "Show libraries and system information on which NumPy was built and is being used," callable as `numpy.show_config(mode='stdout')` or `mode='dicts'` to get a parseable dict (includes BLAS/LAPACK library identity and build-time SIMD info). — [numpy.show_config — NumPy stable Manual](https://numpy.org/doc/stable/reference/generated/numpy.show_config.html)
- The low-level CPU-feature booleans are exposed as module attributes `__cpu_features__`, `__cpu_baseline__`, `__cpu_dispatch__`, generated from the dispatch header and importable as, e.g., `from numpy._core._multiarray_umath import __cpu_features__ as f, __cpu_dispatch__ as d`. — [numpy/_core/src/common/npy_cpu_dispatch.h](https://github.com/numpy/numpy/blob/main/numpy/_core/src/common/npy_cpu_dispatch.h) (confirms attribute generation); import path confirmed via NumPy's own test helper, historically `numpy.core._multiarray_umath` — [test_cpu_dispatcher.py](https://mitra.stanford.edu/kundaje/marinovg/oak/programs/numpy/core/tests/test_cpu_dispatcher.py)
- NumPy 2.0 renamed the private `numpy.core` namespace to `numpy._core`: "The `np.core` namespace is now officially private and has been renamed to `np._core`. The user should never fetch members from the `_core` directly... The layout of the `_core` module might change in the future without notice." This is why, on NumPy 2.x, the dispatch attributes live at `numpy._core._multiarray_umath.__cpu_features__` (etc.) rather than the old `numpy.core._multiarray_umath` path, and why importing from the old `numpy.core...` path now raises/deprecates. — [NumPy 2.0 migration guide](https://numpy.org/doc/stable/numpy_2_0_migration_guide.html)
- Direct, maintainer-confirmed evidence that the selected SIMD path changes **numerical** results (not just performance): in NumPy issue #23523, results of `np.sin`, `np.cos`, `np.exp`, `np.log` differ between AVX-512 and non-AVX-512 code paths by roughly 1–4 ULP (e.g., sine/cosine ~1.1e-16, exp ~2.9e-11, log ~8.8e-16 absolute differences in the reported examples), and these small per-element differences can compound into much larger (~1e-5) differences in downstream computations like rotation matrices. NumPy maintainer **mattip** confirmed this is an intentional "speed-vs-consistency tradeoff": "We accept differences of up to 4 ULP from the golden results, depending on which implementations are used." Workarounds discussed include setting `NPY_DISABLE_CPU_FEATURES` to turn off the AVX-512 variants, or `NPY_ENABLE_CPU_FEATURES` to pin a specific allowed set. — [BUG: AVX-512 results differ from non-AVX-512 for sin, cos, exp, log, etc. · Issue #23523 · numpy/numpy](https://github.com/numpy/numpy/issues/23523)

### Inferences
- Because the whole point of `--cpu-dispatch` is "detect the best available instruction set per machine and use it," two otherwise-identical x86_64 machines that differ only in which SIMD extensions their CPUs expose (e.g., one supports AVX-512F/CD/BW/DQ/VL, the other tops out at AVX2) will, by default, silently execute different compiled kernels of the same NumPy function on the same input array — and per NumPy's own maintainers, this is expected to produce different (not bitwise-identical) floating point output in general, not just different speed.
- `np.show_config()` plus the `__cpu_features__`/`__cpu_baseline__`/`__cpu_dispatch__` triplet is the correct way for a blog author to actually prove, on each of the two machines under test, which SIMD path was active — this is the mechanism-level smoking gun for "why did machine A and machine B disagree."

### Gaps
- I could not find an official NumPy documentation page (as opposed to a GitHub issue) that explicitly states, in the SIMD/build-options reference docs themselves, "different CPU dispatch targets can produce different numerical results." The acknowledgement that this is expected/tolerated currently lives in a GitHub issue thread (#23523) and in NumPy's own universal-intrinsics architecture docs (which describe *why* ufuncs like `sin`/`cos`/`exp`/`log` have per-target vectorized implementations), not in a single canonical "note: results may differ" doc paragraph. Treat the GitHub issue as the primary citable evidence of maintainer acknowledgement; note explicitly in any write-up that this acknowledgement is sourced from an issue tracker, not a docs page.
- I was not able to fetch the exact current wording of `numpy.show_config()`'s example output (BLAS name, found/not-found SIMD features) from the docs page content returned by the fetch tool; the function signature and one-line description are confirmed, but a literal "found: AVX2 / not found: AVX512" sample block was not captured verbatim.

## Pairwise summation: algorithm, block size, and interaction with SIMD width

### Takeaway
Since NumPy 1.9 (2014), `np.sum`/`np.add.reduce` uses pairwise (cascade) summation instead of naive left-to-right accumulation, applied only along the "fast" (contiguous, innermost) axis and only in blocks of ≤ 8192 elements at the top level, recursing down to a base case of 128 elements that is unrolled 8-way (effectively processing 16 partial sums per block) to let the compiler vectorize it. Because the width and number of SIMD lanes used inside that unrolled base case depend on which SIMD ISA NumPy's dispatcher picked (SSE2 vs AVX2 vs AVX-512), the exact grouping/order of additions — and hence the rounding — can differ between machines with different detected instruction sets, even though both are doing "pairwise summation" in the documented algorithmic sense.

### Cited Findings
- Official release-note description of the feature's introduction (NumPy 1.9.0, "Improvements → Better numerical stability for sum in some cases"): "Pairwise summation is now used in the sum method, but only along the fast axis and for groups of the values <= 8192 in length." The note adds that `var` and `std` also benefit since they're sum-based. — [NumPy 1.9.0 Release Notes](https://numpy.org/doc/stable/release/1.9.0-notes.html)
- Current `numpy.sum` documentation explicitly documents both the rationale and the caveat: "For floating point numbers the numerical precision of sum (and `np.add.reduce`) is in general limited by directly adding each number individually to the result causing rounding errors in every step. However, often numpy will use a numerically better approach (partial pairwise summation) leading to improved precision in many use-cases. This improved precision is always provided when no axis is given... When a reduction along an axis is performed [...] the reduction operation may pick a different pairwise summation order." (paraphrase of documented behavior; precision depends on whether the sum is along the fast/contiguous axis). It also explicitly recommends summing in a higher-precision dtype (`float64`) for large sums of `float32` because "numerical errors can become significant." — [numpy.sum — NumPy devdocs Manual](https://numpy.org/devdocs/reference/generated/numpy.sum.html)
- Source-level implementation detail: NumPy's C implementation (`numpy/core/src/umath/loops.c.src`, historically; now under `numpy/_core/src/umath/`) defines `#define PW_BLOCKSIZE 128` as the base-case block size for the pairwise/cascade summation recursion, and a comment in the source notes that "as the inner loop is unrolled eight times it is effectively 16" — i.e., the 128-element base case is summed using an 8-way-unrolled loop (commonly described elsewhere as "8 accumulators"), which is the piece of code that actually gets compiled once per SIMD target by the CPU dispatcher described above. — [numpy/numpy/core/src/umath/loops.c.src (GitHub, historical revision)](https://github.com/numpy/numpy/blob/95ffd706890c472a1c06e4e07cbe4f259407216e/numpy/core/src/umath/loops.c.src); current file at [numpy/core/src/umath/loops.c.src @ master](https://github.com/numpy/numpy/blob/master/numpy/core/src/umath/loops.c.src)
- Above the 128-element base case, NumPy recurses by splitting the block roughly in half (classic pairwise/cascade summation: recursively sum two halves and add the two partial sums), switching to the unrolled-8 linear accumulation only once a sub-block is ≤ 128 elements; the top-level blocking constant most commonly cited for where this pairwise strategy is engaged end-to-end is the ≤ 8192-element groups named in the 1.9.0 release note above. — [NumPy 1.9.0 Release Notes](https://numpy.org/doc/stable/release/1.9.0-notes.html); algorithmic background on recursive pairwise summation generally — [Pairwise summation — Wikipedia](https://en.wikipedia.org/wiki/Pairwise_summation)

### Inferences
- The 128-element, 8-way-unrolled base case is exactly the loop body that NumPy's CPU dispatcher compiles multiple times (once per target ISA). On an SSE2-only path, 8 unrolled scalar/SSE2 accumulators might map to e.g. 2-wide double-precision SIMD lanes; on an AVX2 path, 4-wide lanes; on an AVX-512 path, 8-wide double-precision lanes (or 16-wide single precision) — meaning the *same* logical "8 running partial sums" in the C source can be realized as a different number of SIMD accumulator registers and a different grouping of which array elements land in which partial sum, depending on the detected ISA. Since floating-point addition is not associative, different groupings of the same 128 (or 8192) values into partial sums generally produce a different final bit pattern. This is the concrete mechanism connecting "pairwise summation + CPU dispatch" to "same `np.sum` call, different bits, across an AVX2 machine and an AVX-512 machine."
- Because pairwise summation is explicitly documented as being applied "only along the fast axis," summing the same logical data via `arr.sum(axis=0)` vs `arr.sum(axis=1)` (or on a transposed/non-contiguous view) can also change which summation order is used — an additional, orthogonal source of result differences that a blog author should keep separate from the SIMD-path explanation.

### Gaps
- I could not fetch the exact current (not historical-revision) line numbers or comments in `numpy/_core/src/umath/loops.c.src` confirming `PW_BLOCKSIZE` is still 128 in the latest NumPy source (I verified it via a historical commit and via search-engine-summarized current-file content, but did not get a live fetch of the present-day file contents to quote verbatim). Treat "128 elements / unrolled 8×" as very likely still accurate but flag that it was confirmed via a slightly older pinned commit plus secondary summarization rather than a direct line-by-line read of the current `master` file.
- I found no single NumPy documentation page or GitHub issue in this research session that explicitly states, in so many words, "`np.sum` of the same array differs between an AVX2 machine and an AVX-512 machine" for the summation path specifically (as distinct from the confirmed `sin`/`cos`/`exp`/`log` ULP differences in issue #23523, which are transcendental functions, not reduction/summation). The AVX2-vs-AVX-512 divergence for `np.sum` itself is an inference from (a) the documented pairwise-summation algorithm plus (b) the documented CPU-dispatch mechanism plus (c) the general non-associativity of floating-point addition — not a directly-cited bug report about `np.sum` specifically. This should be presented to the blog author as a well-supported mechanistic inference, not as an independently documented empirical fact.

## SIMD generations on x86_64 and aarch64, and documented reports of differing reduction results

### Takeaway
On x86_64, the SIMD generations that matter for NumPy's dispatcher are SSE2 (baseline), SSE4.x, AVX, AVX2 (plus FMA3), and AVX-512 (with sub-features F/CD/BW/DQ/VL etc., aliased by NumPy as groups like `X86_V2`/`X86_V3`/`X86_V4`); each generation doubles (SSE→AVX) or further widens (AVX→AVX-512) the number of 64-bit/32-bit lanes processed per vector instruction, which changes how many parallel partial accumulators a reduction loop uses. On aarch64, NEON (Advanced SIMD) is the fixed 128-bit baseline, while SVE/SVE2 are explicitly "vector-length agnostic" (hardware may implement 128–2048-bit vectors; the same compiled SVE code adapts its lane count at runtime), meaning a reduction loop's accumulator count is not even fixed at compile time, only at run time, on SVE hardware. A directly-documented report of NumPy itself giving different results under different SIMD paths exists for transcendental ufuncs (`sin`/`cos`/`exp`/`log`, AVX-512 vs. non-AVX-512); no equivalent NumPy-specific bug report for the reduction/`sum` path specifically was found, though the adjacent PyTorch ecosystem has an analogous, directly documented report.

### Cited Findings
- NumPy's CPU-dispatch mechanism explicitly targets x86 SIMD generations by name in its dispatch tags, e.g. `/*@targets avx2 avx512f vsx2 vsx3 asimd asimdhp */` — where `avx2`, `avx512f` are x86_64 targets and `asimd`/`asimdhp` are the Arm NEON ("Advanced SIMD") / half-precision targets, confirming NumPy treats SSE2/AVX2/AVX-512 and NEON as first-class, separately-compiled dispatch targets side by side. — [How does the CPU dispatcher work? — NumPy v1.24 Manual](https://numpy.org/doc/1.24/reference/simd/how-it-works.html)
- Current NumPy docs disable/feature-group examples use the alias `X86_V4` (an x86-64-v4 feature-level alias bundling AVX-512 sub-features) in `NPY_DISABLE_CPU_FEATURES="X86_V4"`, confirming NumPy's build/runtime dispatch explicitly reasons about x86-64 microarchitecture "levels" (which map to SSE2-only / AVX2 / AVX-512 tiers). — [CPU build options — NumPy stable Manual](https://numpy.org/doc/stable/reference/simd/build-options.html)
- Arm's own architecture documentation: SVE "can be Vector Length Agnostic (VLA), which means that the size of the vector registers is not fixed, and hardware implementers are free to choose the size that works best for the intended workloads" (128 up to 2048 bits, in 128-bit increments), and "SVE includes instructions that permit vector code to adapt automatically to the current vector length at runtime. The programmer does not know the size of the registers that are available so code must be written to be vector-length agnostic." SVE is also explicitly a separate instruction encoding from NEON ("Advanced SIMD"), not an extension of it: "SVE is a separate, optional extension with a new set of instruction encodings and is not an extension of Advanced SIMD (aka Neon)." — [Port Code to Arm Scalable Vector Extension (SVE): From Arm Neon to SVE — Arm Learning Paths](https://learn.arm.com/learning-paths/servers-and-cloud-computing/sve/sve_basics/); [SVE and Neon coding compared (Arm Developer documentation PDF)](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/Learn%20the%20Architecture/102131_0100_01_SVE_and_Neon_coding_compared.pdf)
- Directly documented report of a SIMD-path-dependent numerical divergence in NumPy itself: AVX-512 vs non-AVX-512 code paths for `sin`, `cos`, `exp`, `log` differ by ~1–4 ULP, confirmed by NumPy maintainer mattip as an accepted tradeoff. — [Issue #23523 · numpy/numpy](https://github.com/numpy/numpy/issues/23523) (already cited above; repeated here as the concrete "documented report" requested)
- Adjacent ecosystem report (not NumPy itself, but the same CPU-dispatch mechanism class of bug, useful as corroborating evidence for a blog author): a PyTorch issue reports that results differ depending on whether the CPU supports AVX-512, even when the code explicitly requests the AVX2 kernel via `ATEN_CPU_CAPABILITY=avx2`, and a related oneDNN issue reports that convolution forward results differ between AVX-512 VNNI and AVX2 kernels. — [Reproducibility of results without AVX512 by setting ATEN_CPU_CAPABILITY=avx2 · Issue #155552 · pytorch/pytorch](https://github.com/pytorch/pytorch/issues/155552); [convolution forward results are different in AVX512 VNNI and AVX2 · Issue #1354 · uxlfoundation/oneDNN](https://github.com/uxlfoundation/oneDNN/issues/1354)

### Inferences
- Wider SIMD registers mechanically increase the number of independent partial-sum "lanes" a reduction loop can run concurrently before those lanes are horizontally combined into a single scalar: a 128-bit SSE2 double-precision vector holds 2 accumulator lanes, a 256-bit AVX2 vector holds 4, and a 512-bit AVX-512 vector holds 8 (with the loop-unrolling factor, e.g. NumPy's 8×, further multiplying how many *independent* partial sums exist before horizontal combination). Different lane counts mean a different grouping of the same input elements into partial sums, and — because float addition isn't associative — a different final rounded result in general, even before any multithreading is involved.
- On SVE hardware, because the vector length itself is a runtime property of the specific CPU (not fixed by the compiled binary), two different "AVX-512-class" aarch64 SVE machines from different vendors could each run the identical compiled SVE binary yet still use different numbers of reduction lanes purely because their physical SVE vector length differs — a strictly aarch64-specific extra degree of freedom that has no x86_64 analogue (x86_64 AVX-512 lane width is fixed at compile/dispatch-selection time, not discovered per-instruction at runtime the way SVE's is).

### Gaps
- No official NumPy documentation or issue was found that enumerates "SSE2 baseline / AVX / AVX2 / AVX-512F,DQ,VL" as a labeled list with explicit accumulator-count consequences for reductions; the lane-count-per-ISA-generation reasoning above is standard SIMD architecture knowledge (vector width ÷ element size = lane count) applied to NumPy's documented mechanism, not a direct quote from a NumPy source confirming "AVX-512 reductions use 8 lanes for np.sum." Flag this inference as architecturally sound but not NumPy-documentation-verified in those exact terms.
- No NumPy-specific GitHub issue reporting a bitwise-different `np.sum`/reduction result (as opposed to `sin`/`cos`/`exp`/`log`) between AVX2 and AVX-512 machines was located in this research pass; the PyTorch/oneDNN reports are the closest directly-documented analogues found and should be cited as "adjacent ecosystem, not NumPy itself."

## BLAS threading and bit-level reproducibility: OpenBLAS, MKL, BLIS, and official acknowledgements

### Takeaway
All major multithreaded BLAS implementations (OpenBLAS, Intel MKL/oneMKL, BLIS) parallelize GEMM by partitioning the blocked, cache-tiled GotoBLAS2-style algorithm (five nested loops around packing routines and a micro-kernel) across threads along one or more matrix dimensions; different thread counts change how partial products/sums are grouped and combined, and because floating-point addition is not associative, this changes the bit pattern of the result in general. Intel's oneMKL is the only one of the three with an official, documented, named reproducibility feature — Conditional Numerical Reproducibility (CNR) — which explicitly exists because MKL's own runtime CPU dispatch and its threading both change results by default; OpenBLAS has acknowledged, in its own issue tracker, concrete cases of multithreaded GEMM producing wrong/inconsistent results due to race conditions in its threading implementation (a bug, since partially fixed, as opposed to an inherent floating-point-ordering property), and does not appear to ship an equivalent "pin the result" reproducibility mode.

### Cited Findings
- GEMM algorithm shared across modern BLAS implementations: "Modern libraries like BLIS, OpenBLAS, AMD AOCL, and Intel oneMKL follow the GotoBLAS2 approach, formulating GEMM as a blocked algorithm consisting of five nested loops around two packing routines and a micro-kernel," with blocking chosen "so that submatrices fit in the various caches" (L1/L2/L3) and sub-matrices of A and B packed into buffers before the micro-kernel call. — [Anatomy of High-Performance Many-Threaded Matrix Multiplication (BLIS team, IPDPS'14 paper, UT Austin FLAME group)](https://www.cs.utexas.edu/~flame/pubs/blis3_ipdps14.pdf)
- Multithreading is layered onto this blocked algorithm by partitioning one or more of the nested loops across threads: "Matrices may be partitioned in multiple dimensions simultaneously to attain scalable, high-performance parallelism on multicore and many-core architectures, using a thread-specific control tree infrastructure," and BLIS specifically "employs 'quadratic partitioning' when computing dimension sub-ranges for each thread to achieve proper load balance." Changing the thread count therefore changes which sub-ranges (and hence which partial products and partial sums) are assigned to which thread and in what order they are later combined. — [Anatomy of High-Performance Many-Threaded Matrix Multiplication](https://www.cs.utexas.edu/~flame/pubs/blis3_ipdps14.pdf); [flame/blis GitHub repository](https://github.com/flame/blis)
- **Intel oneMKL Conditional Numerical Reproducibility (CNR)** — official documentation: CNR "enables functions to return bitwise reproducible floating-point results from run to run," but only under stated conditions: calls occur "in a single executable" and "the number of computational threads used by the library does not change" throughout the run; a "strict CNR mode" removes the thread-count constraint for a specific, limited subset of routines. — [Obtaining Numerically Reproducible Results — oneMKL Developer Guide (Linux)](https://www.intel.com/content/www/us/en/docs/onemkl/developer-guide-linux/2023-0/obtaining-numerically-reproducible-results.html); [Conditional Numerical Reproducibility Control — oneMKL Developer Reference](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-fortran/2023-2/conditional-numerical-reproducibility-control.html)
- Why CNR is needed at all (official rationale): oneMKL "does run-time processor dispatching in order to identify the appropriate internal code paths," so different processors trigger different optimized branches (e.g., SSE2 through AVX2/AVX-512), potentially reordering floating-point operations; additionally "threading variations can reorder operations," and even data alignment of input arrays can affect the computation sequence used. — [Obtaining Numerically Reproducible Results — oneMKL Developer Guide](https://www.intel.com/content/www/us/en/docs/onemkl/developer-guide-linux/2023-0/obtaining-numerically-reproducible-results.html)
- CNR is configured with the environment variable `MKL_CBWR` (Conditional Bitwise Reproducibility), set as `MKL_CBWR="<branch>"` or `MKL_CBWR="BRANCH=<branch>"`, with branch values including `AUTO`, `COMPATIBLE`, and specific ISA branches such as `SSE2`, `SSE4_2`, `AVX`, `AVX2`, `AVX512` (branches other than `AUTO`/`COMPATIBLE` are only available on genuine Intel processors; `COMPATIBLE` exists specifically because "Intel and Intel compatible CPUs have approximation instructions (for example, rcpps/rsqrtps) that may return different results," so it forces a code path avoiding those lower-precision approximation instructions). — [Specifying Code Branches — oneMKL User Guide (mirrored)](http://portal.nacad.ufrj.br/online/intel/mkl/common/mkl_userguide/GUID-DCB010F6-DDBF-4A00-8BB3-049BEFDC2ED2.htm); [Setting the Environment Variable for Conditional Numerical Reproducibility — oneMKL Developer Guide (Linux)](https://www.intel.com/content/www/us/en/docs/onemkl/developer-guide-linux/2023-0/set-env-var-for-cond-numerical-reproducibility.html)
- Documented performance cost of CNR: restricting to a specific code path can make performance "degrade by more than a half" in some cases, and even the unrestricted CNR functionality can reduce performance "10-20% because the new functionality restricts algorithms to maintain the order of operations." — [Getting Reproducible Results with Intel MKL (Intel white paper, SC13 workshop archive)](https://sc13.supercomputing.org/sites/default/files/WorkshopsArchive/pdfs/wp140s1.pdf)
- OpenBLAS's own issue tracker documents an acknowledged bug (not a general floating-point-ordering disclosure) in which `cblas_sgemm` produced grossly wrong results ("completely different," not minor rounding, e.g. LMS ~8210.9 vs. expected) when called from many threads simultaneously, worse on high-core-count systems but reproducible even on a desktop i7-6700. OpenBLAS maintainer **martin-frbg** attributed this to "suspected races in the multithreaded level 3 BLAS implementation," specifically a thread-local-storage (TLS) optimization added "to remove significant overhead at thread startup" that "had... a few shortcomings." The problematic TLS code was disabled in OpenBLAS 0.3.3, and a `USE_LOCKING` build option was added later (~May 2019) to address the underlying race condition even when `USE_THREAD=0`. — [cblas_sgemm gives incorrect results in heavily multi-threaded programs · Issue #1755 · OpenMathLib/OpenBLAS](https://github.com/OpenMathLib/OpenBLAS/issues/1755)

### Inferences
- There is an important distinction a blog author should preserve: (1) MKL's CNR addresses the *expected, inherent* non-reproducibility caused by non-associative floating-point summation combined with runtime CPU dispatch and thread-count-dependent partitioning — this is normal, documented behavior, not a bug; (2) the OpenBLAS #1755 report is a *correctness bug* (a data race producing grossly wrong answers, not merely different-but-individually-valid rounding), which OpenBLAS fixed/mitigated via `USE_LOCKING`/disabling the offending TLS optimization. Both are real, documented mechanisms by which "same code, same input, different thread count ⇒ different bits," but they are different *kinds* of phenomena (expected rounding-order variation vs. a since-patched threading race), and conflating them would overstate what MKL's CNR is "fixing" relative to what OpenBLAS's fix addressed.
- Because OpenBLAS has no publicly documented CNR-equivalent "pin the floating-point operation order regardless of thread count" feature (none was found in this research pass), the practical reproducibility lever for OpenBLAS-linked NumPy is simply to fix the thread count (`OPENBLAS_NUM_THREADS=1` or a constant value) rather than to select a documented reproducibility mode — this is weaker than MKL's CNR, which documents a specific mechanism and specific bitwise guarantees.

### Gaps
- I did not find official OpenBLAS project documentation (as opposed to GitHub issues) that discusses reproducibility as a general design topic, nor any OpenBLAS-published statement analogous to MKL's CNR docs acknowledging "GEMM results vary with thread count by design." The evidence found is limited to the #1755 bug report (a race condition, now mitigated) rather than a general FAQ entry on floating-point/thread-count variation. This should be stated to the blog author as a gap: OpenBLAS's *acknowledged, documented* reproducibility issue is narrower (and bug-flavored) than MKL's CNR, even though the underlying floating-point non-associativity concern presumably applies to OpenBLAS's threaded GEMM in general.
- I did not find specific official BLIS documentation (as opposed to the academic BLIS paper) with an explicit reproducibility/FAQ statement. The BLIS evidence here is from the IPDPS'14 academic paper describing the library's own threading design, which is authoritative on *mechanism* but is not itself a "BLIS documentation page" in the sense of a maintained docs site.
- I did not verify a specific, official FAQ/doc statement quantifying exactly how many threads is "enough" to trigger a different reduction order in any of the three libraries (i.e., "at N≥2 threads the partitioning changes"); this is implied by the documented threading/partitioning mechanism but not separately quantified in an official doc.

## Which BLAS ships with which NumPy, and how to tell at runtime

## Thread-count environment variables: which library reads which, and the "must set before import" gotcha

### Takeaway
Each threaded numerical library reads its own environment variable at *initialization time* (first touch of the library, generally at process/library load, not at call time): OpenMP-based code (including scikit-learn's own Cython/OpenMP code and also what MKL and some OpenBLAS builds use internally for threading) reads `OMP_NUM_THREADS`; OpenBLAS reads `OPENBLAS_NUM_THREADS`; MKL reads `MKL_NUM_THREADS`; NumExpr reads `NUMEXPR_NUM_THREADS` (preferred) or falls back to `OMP_NUM_THREADS`; Apple's Accelerate/vecLib reads `VECLIB_MAXIMUM_THREADS`. Because these libraries configure their internal thread pools once, at load time, setting the variable *after* `import numpy` (or after the BLAS shared library is first loaded) has no effect — it must be set in the process environment before the interpreter imports NumPy/SciPy/the relevant library.

### Cited Findings
- scikit-learn's official parallelism documentation enumerates the three layers and their respective controls: "The `n_jobs` parameters of estimators always control the amount of parallelism managed by joblib... OpenMP is used to parallelize code written in Cython or C, relying on multi-threading exclusively. By default... as many threads as logical cores... You can control the exact number of threads using the `OMP_NUM_THREADS` environment variable." For the BLAS layer: "scikit-learn relies heavily on NumPy and SciPy, which internally call multi-threaded linear algebra routines... implemented in libraries such as MKL, OpenBLAS or BLIS," controllable via `MKL_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `BLIS_NUM_THREADS` (and also via `threadpoolctl`). — [Parallelism, resource management, and configuration — scikit-learn docs](https://scikit-learn.org/stable/computing/parallelism.html)
- `threadpoolctl` (the joblib/scikit-learn-maintained library purpose-built to introspect/limit native thread pools) is documented as providing "Python helpers to limit the number of threads used in native libraries that handle their own internal threadpool (BLAS and OpenMP implementations)" and explicitly supports OpenMP plus the main BLAS libraries; usage pattern `OMP_NUM_THREADS=2 python -m threadpoolctl -i numpy scipy` is given by scikit-learn's own docs as a way to inspect what a given environment actually resolves to. — [joblib/threadpoolctl GitHub repository](https://github.com/joblib/threadpoolctl); usage example via [scikit-learn parallelism docs](https://scikit-learn.org/stable/computing/parallelism.html)
- `NUMEXPR_NUM_THREADS` is documented (NumExpr user guide) as the preferred environment variable for controlling NumExpr's internal thread pool size, with `OMP_NUM_THREADS` as a fallback. — [NumExpr User Guide](https://numexpr.readthedocs.io/en/latest/user_guide.html)
- `VECLIB_MAXIMUM_THREADS` is documented/cited (via secondary summarization of library documentation) as the variable controlling thread count for Apple's Accelerate/vecLib BLAS backend on macOS. — summarized from search of threadpoolctl/numexpr documentation; **this specific attribution was captured via aggregated search-tool summary rather than a direct fetch of an Apple or threadpoolctl primary-source page; flagged as weaker-sourced.**
- The "must set before import" gotcha is explicitly explained by community technical sources: "OPENBLAS_NUM_THREADS is read by OpenBLAS at initialization and controls the size of its internal thread pool... You must set the environment variable before importing numpy... setting them after import will have no effect since OpenBLAS has already been initialized." — [Taming BLAS Threads in Scheduled Python Jobs — DEV Community](https://dev.to/mattleeee/taming-blas-threads-in-scheduled-python-jobs-nka) (**this is a blog/community post, not official documentation — flagged explicitly as required**). The mechanism itself (thread pool created once at library load) is consistent with, though not verbatim quoted from, OpenBLAS's own GitHub issue discussions about thread-count configuration (e.g., issue threads about `openblas_set_num_threads` not always taking effect after the fact). — [Inconsistency between openblas_get_num_threads and openblas_set_num_threads · Issue #760 · OpenMathLib/OpenBLAS](https://github.com/OpenMathLib/OpenBLAS/issues/760)
- scikit-learn's docs also note an oversubscription interaction relevant to reproducibility debugging: joblib (`loky` backend, joblib ≥ 0.14) auto-limits child-process thread pools via `max_threads = n_cpus // n_jobs`, but "setting `OMP_NUM_THREADS`, `MKL_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, or `BLIS_NUM_THREADS` manually takes precedence over joblib's mitigation," and with the `threading` backend "there is no mechanism to avoid oversubscription." — [Parallelism, resource management, and configuration — scikit-learn docs](https://scikit-learn.org/stable/computing/parallelism.html)

### Inferences
- For a blog author trying to make two machines agree bit-for-bit, the practical checklist implied by these sources is: set every one of `OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `MKL_NUM_THREADS`, `NUMEXPR_NUM_THREADS`, `VECLIB_MAXIMUM_THREADS` (as applicable to the actual backend in use, confirmed via `show_config()`/`threadpoolctl`) to the same fixed value, and set them in the shell/launcher *before* the Python process starts (or at the very top of the script before `import numpy`), since post-import assignment is a documented-by-mechanism no-op for the native thread pools.

### Gaps
- I was not able to fetch the threadpoolctl README directly (fetch calls to related pages returned secondary/aggregated summaries rather than the verbatim README text), so the full list of libraries threadpoolctl recognizes (and exact supported variable names) is sourced from search-result summarization rather than a direct README read in this session. The core variables used in this note (`OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `MKL_NUM_THREADS`) are independently corroborated by the official scikit-learn docs page, which was fetched directly.
- The `VECLIB_MAXIMUM_THREADS` attribution to Apple Accelerate/vecLib was not confirmed against an Apple-published primary source in this session.

## OpenMP reduction clauses: why they are not deterministic, and whether any version guarantees reproducibility

### Takeaway
The OpenMP specification explicitly and deliberately leaves the order and location of combination in a `reduction` clause unspecified, and states in plain terms that bitwise-identical results are **not guaranteed**, even comparing one parallel run to another with the same thread count. This has been true at least since OpenMP 5.0 and remains the documented behavior through 5.2; no OpenMP version found in this research provides an opt-in "reproducible/deterministic reduction order" guarantee analogous to MKL's CNR.

### Cited Findings
- OpenMP 5.0 specification, reduction clauses section: "The location in the OpenMP program at which values are combined and the order in which values are combined are unspecified." And explicitly on reproducibility: "Therefore, when comparing sequential and parallel runs, or when comparing one parallel run to another (even if the number of threads used is the same), there is no guarantee that bitwise-identical results will be obtained or that side effects (such as floating-point exceptions) will be identical or take place at the same location in the OpenMP program." — [2.19.5 Reduction Clauses and Directives — OpenMP 5.0 Specification](https://www.openmp.org/spec-html/5.0/openmpsu107.html)
- The same unspecified-order language is present in the OpenMP 5.1 reduction clauses section, confirming continuity of this design decision across versions. — [2.21.5 Reduction Clauses and Directives — OpenMP 5.1 Specification](https://www.openmp.org/spec-html/5.1/openmpsu117.html)
- Also documented: "the number of times that the combiner expression is executed and the order of these executions for any reduction clause are unspecified" — i.e., not only is the order unspecified, the OpenMP runtime isn't even required to combine values a fixed, predictable number of times in a fixed sequence. — [2.19.5 Reduction Clauses and Directives — OpenMP 5.0 Specification](https://www.openmp.org/spec-html/5.0/openmpsu107.html)

### Inferences
- Because the spec explicitly disclaims bitwise reproducibility "even if the number of threads used is the same," an OpenMP-parallelized reduction (such as used inside BLIS or inside MKL/OpenBLAS's own threading layers, or inside scikit-learn/LightGBM/XGBoost's Cython/C++ hot loops) is, by the standard's own text, not guaranteed deterministic run-to-run on a single fixed machine/thread-count configuration — let alone across two different machines. This is the standards-level justification underlying why every other tool in this note (MKL's CNR, LightGBM's `deterministic`, XGBoost's `deterministic_histogram`) has to build its own bespoke, non-default reproducibility mechanism on top of OpenMP/threaded reductions rather than relying on OpenMP to provide one.

### Gaps
- I did not find, in OpenMP 5.0, 5.1, or the portions of 5.2 fetched, any clause, appendix, or directive (e.g., a hypothetical `reduction(reproducible: +:x)` or similar) that provides an opt-in deterministic/reproducible reduction-order guarantee in any OpenMP version up to and including what was checked (5.0–5.2). This supports — but does not exhaustively prove for literally every OpenMP version/TR up to 2026 — the claim in the task's key questions that no such "reproducible" guarantee exists. Recommend the blog author state this as "not found in OpenMP 5.0–5.2" rather than an absolute claim about all possible future or draft OpenMP versions, since this session did not check OpenMP 6.0 (released 2024) specification text directly.

## LightGBM and XGBoost: documentation on determinism and thread count

### Takeaway
LightGBM documents a `deterministic` parameter (default `false`) that trades speed for stable results "using the same data and the same parameters (and different `num_threads`)" — but only reliably when combined with `force_row_wise=true` or `force_col_wise=true`, because LightGBM's default histogram-building strategy itself depends on thread count/data shape. XGBoost does not document a single umbrella "determinism" flag, but it does document a specific, narrower mechanism — `deterministic_histogram` (GPU `hist`, default `true`) — that exists precisely because "histogram building is not deterministic due to the non-associative aspect of floating point summation," fixed via a floating-point pre-rounding technique at a documented small accuracy cost.

### Cited Findings
- LightGBM official parameter docs, `deterministic`: default `false`, type bool; "setting this to `true` should ensure the stable results when using the same data and the same parameters (and different `num_threads`)"; but "results may differ across different seeds, LightGBM versions, compiler binaries, or systems," enabling it "may slow down training," and the docs explicitly instruct: set `force_col_wise=true` or `force_row_wise=true` when `deterministic=true` "to avoid potential instability due to numerical issues." — [LightGBM Parameters documentation](https://lightgbm.readthedocs.io/en/latest/Parameters.html)
- LightGBM official parameter docs, `force_row_wise`: default `false`; "set this to `true` to force row-wise histogram building"; recommended "when the number of data points is large and the total number of bins is relatively small," or `num_threads` is small (≤16); doubles Dataset memory cost; mutually exclusive with `force_col_wise`. `force_col_wise`: the column-wise analogue, recommended for large column counts/large total bins or large `num_threads` (>20), and reduces memory cost instead. When neither is forced, "LightGBM tests both approaches and uses the faster one" — meaning the histogram-building strategy (and thus the summation order inside histogram construction) can itself vary by data shape/thread count unless pinned. — [LightGBM Parameters documentation](https://lightgbm.readthedocs.io/en/latest/Parameters.html)
- LightGBM's `num_threads` parameter documentation explicitly warns: "please don't change this during training, especially when running multiple jobs simultaneously by external packages, otherwise it may cause undesirable errors," reinforcing that thread count is read/fixed at a specific point and not safely mutable mid-run. — [LightGBM Parameters documentation](https://lightgbm.readthedocs.io/en/latest/Parameters.html)
- XGBoost's `deterministic_histogram` parameter (GPU `hist`/`gpu_hist`): default `true`; documented purpose is exactly to counteract that "histogram building is not deterministic due to the non-associative aspect of floating point summation" on GPU; it works via "a pre-rounding routine... to mitigate the issue, which may lead to slightly lower accuracy"; can be set `false` to disable (trading determinism back for a small amount of potential accuracy/speed). — [XGBoost GPU Support documentation, historical release docs](https://xgboost.readthedocs.io/en/release_1.3.0/gpu/)
- XGBoost's general `nthread`/`n_jobs` parameter: "defaults to the maximum number of threads available if not set," and the docs advise considering thread contention and hyperthreading when choosing a value explicitly. — [XGBoost Parameters documentation](https://xgboost.readthedocs.io/en/stable/parameter.html)
- XGBoost's `hist` tree method (CPU) is documented as building a histogram via sketching run once up front ("runs sketching before training... the subsequent per-node histogram is built upon this global sketch"), contrasted with `approx`, which re-sketches before every tree using the current Hessian-weighted rows; the docs note `approx` "sometimes yields better accuracy, but with slower computation performance" than `hist`. — [XGBoost Tree Methods documentation](https://xgboost.readthedocs.io/en/stable/treemethod.html)

### Inferences
- Both LightGBM and XGBoost documentation converge on the same root cause as the BLAS/OpenMP material above: histogram-building reductions are sums over subsets of rows/bins, computed by multiple threads, and "non-associative floating point summation" is the phrase both ecosystems use (LightGBM via "numerical issues" needing `force_row_wise`/`force_col_wise`, XGBoost via its explicit `deterministic_histogram` doc string) — i.e., gradient boosting determinism problems are the *same* underlying mechanism as `np.sum`/BLAS non-reproducibility, just occurring inside the library's own histogram-building loops rather than inside NumPy/BLAS reduction loops.
- Because LightGBM's `deterministic` flag is explicitly scoped to "same data, same parameters, different `num_threads`" on CPU, and does not claim cross-machine/cross-CPU-architecture reproducibility, a blog author should not expect `deterministic=true` alone to make two different physical machines (e.g., one AVX2, one AVX-512) agree bit-for-bit — only to make repeated runs *on one machine* with varying thread counts agree.

### Gaps
- I attempted to fetch GitHub issue #5023 ("Model reproducibility with histogram tree method," dmlc/xgboost) and GitHub issue #6320 ("[python-package] How do I make LightGBM's output deterministic?", lightgbm-org/LightGBM) for maintainer-level detail beyond the official parameter docs, but both fetches timed out in this research session and were not successfully retrieved. The claims above are sourced entirely from the official parameter/docs pages (xgboost.readthedocs.io, lightgbm.readthedocs.io), which is actually the stronger/more "official documentation over blog post" source per the task's constraints, but it means maintainer commentary/nuance from those two issue threads (e.g., any documented caveats about checkpoint-resume non-determinism reported in issue #10324) was not independently verified; flagging issue #10324 ("Hist training with checkpointing is non-deterministic based on subsample") only as a title seen in search results, not as a verified/fetched claim.
- I did not find official XGBoost documentation for a CPU-side (non-GPU) analogue of `deterministic_histogram`; the documented mechanism found is specific to `gpu_hist`. Whether CPU `hist` has a similarly named/documented determinism toggle was not confirmed in this session — flag as a gap rather than assuming none exists.

## joblib / scikit-learn parallelism: does `n_jobs` change results?

### Takeaway
Yes — scikit-learn's own GitHub issue tracker documents concrete, confirmed cases where changing `n_jobs` changes an estimator's results even with `random_state` fixed (e.g., `RandomForestRegressor`), and the official scikit-learn "Parallelism, resource management, and configuration" docs describe the three parallelism layers (joblib/`n_jobs`, OpenMP, BLAS) without making a blanket guarantee that output is independent of `n_jobs`; the "Controlling randomness" docs do not resolve the `n_jobs`×`random_state` interaction explicitly, and that gap is itself tracked as an open scikit-learn discussion.

### Cited Findings
- Official scikit-learn docs on parallelism: n_jobs controls joblib-managed parallelism (process- or thread-based depending on backend, default `loky`); OpenMP-based code (Cython/C) is controlled via `OMP_NUM_THREADS`; and "scikit-learn relies heavily on NumPy and SciPy, which internally call multi-threaded linear algebra routines (BLAS & LAPACK) implemented in libraries such as MKL, OpenBLAS or BLIS" — i.e., even a single scikit-learn `fit()` call potentially stacks all three parallelism mechanisms discussed elsewhere in this note. — [Parallelism, resource management, and configuration — scikit-learn docs](https://scikit-learn.org/stable/computing/parallelism.html)
- A confirmed, title-level GitHub report: "RandomForestRegressor results not reproducible when n_jobs=-1 even if random_state set," with results reported reproducible when `n_jobs=1` — i.e., parallel execution (here, joblib-level forest-building across trees, which itself triggers nested BLAS/OpenMP calls per tree) introduces run-to-run or configuration-to-configuration non-determinism not present in the serial path. — [RandomForestRegressor results not reproducible when n_jobs=-1 even if random_state set · Issue #11137 · scikit-learn/scikit-learn](https://github.com/scikit-learn/scikit-learn/issues/11137)
- A more recent, still-open community question on exactly this interaction: "Are there any pitfalls by combining `n_jobs` and `random_state`?" — indicating scikit-learn's own "Controlling randomness" documentation does not explicitly address whether `random_state` and `n_jobs > 1` interact unexpectedly, which the scikit-learn team itself treats as an open documentation gap as of this discussion. — [Are there any pitfalls by combining `n_jobs` and `random_state`? · Issue #30811 · scikit-learn/scikit-learn](https://github.com/scikit-learn/scikit-learn/issues/30811)

### Inferences
- The mechanism is consistent with everything else in this note: scikit-learn estimators that use `n_jobs` typically farm out BLAS-heavy or OpenMP-heavy subcomputations (tree-building, pairwise distance kernels, etc.) across workers; different `n_jobs` values change how work (and therefore floating-point reduction order) is partitioned across threads/processes, which is the same category of effect documented explicitly for OpenMP reductions and BLAS GEMM elsewhere in this note. scikit-learn's docs describe the *mechanism* (three parallelism layers) without making an explicit reproducibility guarantee, and user-facing GitHub issues confirm the *practical consequence* (different `n_jobs` ⇒ different results) for at least one concrete estimator (`RandomForestRegressor`).

### Gaps
- I did not find an official scikit-learn documentation page (as opposed to a GitHub issue) that explicitly states, in prose, "changing `n_jobs` can change an estimator's numerical output" as a general, named caveat (e.g., in a "Common pitfalls" or "Controlling randomness" guide). The scikit-learn docs fetched in this session describe the parallelism *mechanism* thoroughly but were not observed to contain an explicit, general "n_jobs affects results" disclaimer; the concrete evidence found is at the level of specific GitHub issues (#11137, #30811) about specific estimators, not a general documented statement. This should be presented to the blog author as "documented by confirmed bug reports for at least one estimator; not stated as a blanket doc-level warning," which is a meaningfully weaker/more specific claim than "scikit-learn documents that n_jobs changes results" in general.

## Overall synthesis note for the report writer

The single unifying mechanism behind every item above is: (1) IEEE-754 floating-point addition/multiplication is not associative, so any change in the *order or grouping* in which partial results are combined can change the final rounded bit pattern; and (2) essentially every layer of the numerical stack — NumPy's SIMD-dispatched, pairwise-summed reductions; BLAS's thread-partitioned, cache-blocked GEMM; OpenMP's unordered reduction combination; and gradient-boosting libraries' thread-partitioned histogram building — deliberately reorders/regroups operations for performance, and (with the partial exception of Intel MKL's CNR and the narrower `deterministic`/`deterministic_histogram`/`force_row_wise` flags in LightGBM/XGBoost) does **not** guarantee a fixed order by default. Two "identical x86_64" machines can disagree because they differ in (a) detected SIMD feature level (changing NumPy's compiled kernel and BLAS's internal dispatch branch, hence the grouping inside reductions/GEMM), (b) BLAS vendor/implementation (OpenBLAS vs. MKL vs. BLIS — different packing/blocking/threading code entirely), and/or (c) effective thread count at runtime (changing how work, and thus partial sums, are partitioned) — and all three of these are independently documented, in official sources, as behaviors that can change floating-point results, not merely performance.
