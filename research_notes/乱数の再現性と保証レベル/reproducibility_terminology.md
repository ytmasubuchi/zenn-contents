# Standardized Vocabulary for "Reproducibility" — Terminology and Formal Definitions

## ACM Artifact Review and Badging: verbatim Repeatability/Reproducibility/Replicability definitions (v1.1), and what changed from the original (v1.0-era) definitions

### Takeaway
ACM's current policy (Version 1.1, dated August 24, 2020) defines three distinct levels along a "same team / different team" × "same setup / different setup" grid — Repeatability (same team, same setup), Reproducibility (different team, same setup, using the original author's artifacts), and Replicability (different team, different setup, using independently developed artifacts). Critically, ACM **swapped** the meanings of "Reproducibility" and "Replicability" relative to its original (2016) definitions, explicitly at NISO's recommendation, to align with the broader scientific research community's usage — so older sources (including ACM's own pre-2020 pages and papers citing them) use the two words with **opposite** team/setup mappings from the current ACM/NISO convention. A blog claiming "this result is reproducible" should specify which convention it is using, because the plain word's meaning inverted within ACM's own history.

### Cited Findings

**Current ACM definitions (Version 1.1, August 24, 2020), verbatim** — from the "Artifact Review and Badging - Current" page (fetched via Wayback Machine snapshot dated 2024-01-02, since the live page returned HTTP 403 to automated fetches; snapshot URL: http://web.archive.org/web/20240102044447/https://www.acm.org/publications/policies/artifact-review-and-badging-current):

> "Terminology
> A variety of research communities have embraced the goal of reproducibility in experimental science. Unfortunately, the terminology in use has not been uniform. Because of this we find it necessary to define our terms. The following are inspired by the International Vocabulary for Metrology (VIM); see the Appendix for details.
>
> **Repeatability (Same team, same experimental setup)**
> The measurement can be obtained with stated precision by the same team using the same measurement procedure, the same measuring system, under the same operating conditions, in the same location on multiple trials. For computational experiments, this means that a researcher can reliably repeat her own computation.
>
> **Reproducibility (Different team, same experimental setup)***
> The measurement can be obtained with stated precision by a different team using the same measurement procedure, the same measuring system, under the same operating conditions, in the same or a different location on multiple trials. For computational experiments, this means that an independent group can obtain the same result using the author's own artifacts.
>
> **Replicability (Different team, different experimental setup)***
> The measurement can be obtained with stated precision by a different team, a different measuring system, in a different location on multiple trials. For computational experiments, this means that an independent group can obtain the same result using artifacts which they develop completely independently."
— [ACM Artifact Review and Badging - Current (Wayback Machine snapshot, 2024-01-02, of https://www.acm.org/publications/policies/artifact-review-and-badging-current)](http://web.archive.org/web/20240102044447/https://www.acm.org/publications/policies/artifact-review-and-badging-current) (accessed 2026-10-14)

**The explicit note on the swap, verbatim** (footnote attached to the asterisks above):
> "*As a result of discussions with the National Information Standards Organization (NISO), it was recommended that ACM harmonize its terminology and definitions with those used in the broader scientific research community, and ACM agreed with NISO's recommendation to swap the terms "reproducibility" and "replication" with the existing definitions used by ACM as part of its artifact review and badging initiative. ACM took action to update all prior badging to ensure consistency."
— [ACM Artifact Review and Badging - Current](http://web.archive.org/web/20240102044447/https://www.acm.org/publications/policies/artifact-review-and-badging-current) (accessed 2026-10-14)

**ACM's badge-level language (v1.1)**, which maps directly onto the two swapped terms:
> "Results Reproduced v1.1 The main results of the paper have been obtained in a subsequent study by a person or team other than the authors, using, in part, artifacts provided by the author.
> Results Replicated v1.1 The main results of the paper have been independently obtained in a subsequent study by a person or team other than the authors, without the use of author-supplied artifacts."
— [ACM Artifact Review and Badging - Current](http://web.archive.org/web/20240102044447/https://www.acm.org/publications/policies/artifact-review-and-badging-current) (accessed 2026-10-14)

**ACM's explicit tolerance statement (v1.1), directly relevant to "numerical reproducibility" claims**, verbatim:
> "In each cases, exact replication or reproduction of results is not required, or even expected. Instead, the results must be in agreement to within a tolerance deemed acceptable for experiments of the given type. In particular, differences in the results should not change the main claims made in the paper."
— [ACM Artifact Review and Badging - Current](http://web.archive.org/web/20240102044447/https://www.acm.org/publications/policies/artifact-review-and-badging-current) (accessed 2026-10-14)

**Original (pre-2020, "v1.0"-era) ACM definitions, verbatim** — ACM's badging policy was "Approved June 2016" per the citation in the secondary source below; these are quoted directly from Lorena A. Barba's paper "Terminologies for Reproducible Research" (arXiv:1802.03311v1, January 2018), which transcribes the ACM policy text as it stood at that time (footnote in that paper cites "Approved June 2016, https://www.acm.org/publications/policies/artifact-review-badging"):

> "Repeatability (Same team, same experimental setup.) The measurement can be obtained with stated precision by the same team using the same measurement procedure, the same measuring system, under the same operating conditions, in the same location on multiple trials. For computational experiments, this means that a researcher can reliably repeat her own computation.
>
> Replicability (Different team, same experimental setup.) The measurement can be obtained with stated precision by a different team using the same measurement procedure, the same measuring system, under the same operating conditions, in the same or a different location on multiple trials. For computational experiments, this means that an independent group can obtain the same result using the author's own artifacts.
>
> Reproducibility (Different team, different experimental setup.) The measurement can be obtained with stated precision by a different team, a different measuring system, in a different location on multiple trials. For computational experiments, this means that an independent group can obtain the same result using artifacts which they develop completely independently."
— [Lorena A. Barba, "Terminologies for Reproducible Research," arXiv:1802.03311v1, January 2018, pp. 4-5](https://arxiv.org/pdf/1802.03311) (accessed 2026-10-14)

**What changed, stated precisely**: Comparing the two blocks above term-by-term: "Repeatability" is unchanged (same team, same setup) in both versions. But "different team, same experimental setup, using the author's own artifacts" was called **Replicability** in the original (2016) ACM definitions and is now called **Reproducibility** in the current (v1.1, 2020) definitions. Conversely, "different team, different experimental setup, independently-developed artifacts" was called **Reproducibility** originally and is now called **Replicability**. This is a direct, acknowledged inversion of the two terms — not a drafting refinement.

**Independent confirmation that this swap tracks a long-standing community split**: Barba's 2018 survey documents that, before the 2020 ACM change, the literature already split into two camps using the words in opposite senses — one group (which she labels "B1," including Claerbout/Donoho/Peng-style usage) calling the minimum standard ("same data + same methods = same results") "reproduce," and another ("B2," including Drummond 2009) calling that same minimum standard "replicate." The pre-2020 ACM definitions aligned with the "B2" / Drummond-style swapped convention; the post-2020 (v1.1) ACM definitions realign with the "B1" / Claerbout-Donoho-Peng convention, which is also NIST's and NISO's preferred usage. [Lorena A. Barba, "Terminologies for Reproducible Research," arXiv:1802.03311v1 (Jan. 2018), pp. 1, 4](https://arxiv.org/pdf/1802.03311) (accessed 2026-10-14)

### Inferences
- Any blog post or article that cites an ACM-style definition of "reproducibility" without a date or version number is ambiguous, because the ACM definitions of "reproducibility" and "replicability" literally reversed meaning in 2020. Citing "ACM v1.1 (2020)" (or quoting the full same-team/different-team sentence) removes the ambiguity.
- Because this is an acknowledged terminology swap (not merely two different organizations' independent disagreement), the blog author should treat pre-2020 ACM-derived definitions as superseded and flag them explicitly if quoting older papers that use "ACM-style" repeatability/reproducibility/replicability language.

## NISO Reproducibility Badging and Definitions (RP-31-2021): its relationship to ACM's definitions

### Takeaway
NISO's Recommended Practice (RP-31-2021, "Reproducibility Badging and Definitions," approved January 15, 2021, published January 28, 2021) is a *different, complementary* badging scheme — not a restatement of ACM's Repeatability/Reproducibility/Replicability triad. NISO defines four badges (Open Research Objects [ORO], Research Objects Reviewed [ROR], Results Reproduced [ROR-R], Results Replicated [RER]) and explicitly maps them onto existing badges from ACM, the Center for Open Science, IEEE, Springer Nature, Elsevier, and Wiley in its Appendix A — and it adopts the **National Academies of Sciences, Engineering, and Medicine (NASEM) 2019** definition of reproducibility as its substantive definition, rather than writing an independent one. It was NISO (specifically discussions with the NISO working group) that recommended ACM swap "reproducibility" and "replication," as ACM's own v1.1 page states.

### Cited Findings
- NISO RP-31-2021 adopts the NASEM 2019 definition verbatim as its working definition of reproducibility: "This Recommended Practice has adopted the National Academies of Sciences Engineering Medicine, definition of Reproducibility: 'We define reproducibility to mean computational reproducibility—obtaining consistent results using the same input data, computational steps, methods, code, and conditions of analysis.'" — [NISO RP-31-2021, Reproducibility Badging and Definitions, Section 2.3 "Results Reproduced (ROR-R)," p. 4](https://cds.iisc.ac.in/faculty/simmhan/ccgrid2023/www-archive/groups.niso.org/higherlogic/ws/public/download/24810/RP-31-2021_Reproducibility_Badging_and_Definitions.pdf) (accessed 2026-10-14)
- NISO's four badges are: **Open Research Objects (ORO)** — "author-created digital objects used in the research (including data and code) are permanently archived in a public repository... and are made available via standard open licenses"; **Research Objects Reviewed (ROR)** — "all relevant author-created digital objects used in the research... were reviewed according to the criteria provided by the badge issuer"; **Results Reproduced (ROR-R)** — "an additional step was taken or facilitated by the badge issuer... to certify that an independent party has regenerated computational results using the author-created research objects, methods, code, and conditions of analysis"; **Results Replicated (RER)** — "an independent study, aimed at answering the same scientific question, has obtained consistent results leading to the same findings (potentially using new artifacts or methods)." — [NISO RP-31-2021, Section 2, pp. 3-4](https://cds.iisc.ac.in/faculty/simmhan/ccgrid2023/www-archive/groups.niso.org/higherlogic/ws/public/download/24810/RP-31-2021_Reproducibility_Badging_and_Definitions.pdf) (accessed 2026-10-14)
- NISO explicitly cross-maps to ACM in a note under its ORO badge: "This definition corresponds to the Association for Computing Machinery (ACM) 'Artifacts Available' badge, and to the combined Center for Open Science (COS) 'Open Data' and 'Open Materials' (pertaining to digital objects) badges." Likewise, the ROR badge note states: "This badge corresponds to the ACM 'Artifacts Evaluated' badge, while the Institute of Electrical and Electronics Engineers (IEEE) has used a 'Code Reviewed' badge." — [NISO RP-31-2021, Sections 2.1-2.2, p. 3](https://cds.iisc.ac.in/faculty/simmhan/ccgrid2023/www-archive/groups.niso.org/higherlogic/ws/public/download/24810/RP-31-2021_Reproducibility_Badging_and_Definitions.pdf) (accessed 2026-10-14)
- NISO's Appendix A.1 reproduces ACM's current (v1.1) badge list and definitions directly (Artifacts Available, Artifacts Evaluated—Functional, Artifacts Evaluated—Reusable, Results Replicated, Results Reproduced), including: "Results Replicated: The main results of the paper have been obtained in a subsequent study by a person or team other than the authors, using, in part, artifacts provided by the author." and "Results Reproduced: The main results of the paper have been independently obtained in a subsequent study by a person or team other than the authors, without the use of author-supplied artifacts." — [NISO RP-31-2021, Appendix A.1, p. 8](https://cds.iisc.ac.in/faculty/simmhan/ccgrid2023/www-archive/groups.niso.org/higherlogic/ws/public/download/24810/RP-31-2021_Reproducibility_Badging_and_Definitions.pdf) (accessed 2026-10-14)
- NISO's foreword explains its origin: "In the spirit of the NASEM effort, in March 2019, a group of research-publishing stakeholders formed a committee under the aegis of NISO to develop a set of recognition standards to be universally deployed across the scholarly publishing output. The work of that group resulted in this recommended practice." — [NISO RP-31-2021, Section 1.1 "Overview," p. 1](https://cds.iisc.ac.in/faculty/simmhan/ccgrid2023/www-archive/groups.niso.org/higherlogic/ws/public/download/24810/RP-31-2021_Reproducibility_Badging_and_Definitions.pdf) (accessed 2026-10-14)
- NISO's own membership overlapped directly with ACM: the NISO Reproducibility Badging and Definitions Working Group included "Wayne Graves (co-chair), ACM" as a listed member, which corroborates ACM's statement that the swap resulted from "discussions with the National Information Standards Organization (NISO)." — [NISO RP-31-2021, Foreword, p. iv](https://cds.iisc.ac.in/faculty/simmhan/ccgrid2023/www-archive/groups.niso.org/higherlogic/ws/public/download/24810/RP-31-2021_Reproducibility_Badging_and_Definitions.pdf) (accessed 2026-10-14); corroborating press coverage of the January 2021 publication: [NISO, "NISO's Recommended Practice on Reproducibility Badging and Definitions Now Published" (press release)](https://www.niso.org/press-releases/2021/01/nisos-recommended-practice-reproducibility-badging-and-definitions-now) (accessed 2026-10-14)

### Inferences
- Note 2 under NISO's ORO badge shows NISO's and ACM's taxonomies are not a simple one-to-one mapping of names but are cross-referenced badge-by-badge; readers should not assume "NISO reproducibility" and "ACM reproducibility" are interchangeable labels — NISO's "ROR-R" (Results Reproduced) most closely parallels ACM's current "Results Reproduced" badge (same underlying NASEM-style definition), while NISO's "RER" (Results Replicated) parallels ACM's "Results Replicated" badge.
- Because ACM's working group co-chair (Wayne Graves) sat on the NISO committee, the 2020 ACM swap and the 2021 NISO recommended practice should be read as a single coordinated harmonization effort across the two bodies, not two independent definitions that happen to agree.

### Gaps
- None of the central terminology questions were unanswerable; this question was fully resolved by the primary-source PDF (fetched directly, pages extracted and read as images).

## ISO/IEC and metrology (VIM) definitions of repeatability and reproducibility, and their relevance

### Takeaway
The VIM (JCGM 200:2012, "International Vocabulary of Metrology – Basic and General Concepts and Associated Terms," 3rd edition) is the explicitly cited origin of ACM's repeatability/reproducibility language — ACM's own policy page states its terms were "inspired by the International Vocabulary for Metrology (VIM)" and reproduces VIM's definitions in an appendix. VIM defines "measurement repeatability" and "measurement reproducibility" purely in terms of which experimental conditions are held constant versus varied (operator, instrument, location, procedure, time), not in terms of "team" per se, and conspicuously does **not** define "replicability" at all — a gap that ACM/NISO and the wider computing community had to fill themselves.

### Cited Findings
- VIM 2.20, "repeatability condition of measurement": "condition of measurement, out of a set of conditions that includes the same measurement procedure, same operators, same measuring system, same operating conditions and same location, and replicate measurements on the same or similar objects over a short period of time." — [JCGM, International Vocabulary of Metrology (VIM), 3rd ed., §2.20](https://jcgm.bipm.org/vim/en/2.20.html) (accessed 2026-10-14)
- VIM 2.21, "measurement repeatability": "measurement precision under a set of repeatability conditions of measurement." An informative annotation (dated 1 December 2014) notes "of measurement" can be dropped without ambiguity. — [JCGM, VIM, 3rd ed., §2.21](https://jcgm.bipm.org/vim/en/2.21.html) (accessed 2026-10-14)
- VIM 2.24, "reproducibility condition of measurement": "condition of measurement, out of a set of conditions that includes different locations, operators, measuring systems, and replicate measurements on the same or similar objects," with notes: "NOTE 1 The different measuring systems may use different measurement procedures. NOTE 2 A specification should give the conditions changed and unchanged, to the extent practical." — [JCGM, VIM, 3rd ed., §2.24](https://jcgm.bipm.org/vim/en/2.24.html) (accessed 2026-10-14)
- VIM 2.25, "measurement reproducibility": "measurement precision under reproducibility conditions of measurement," with the note that relevant statistical terms are in ISO 5725-1:1994 and ISO 5725-2:1994, and an informative annotation that "of measurement" can be dropped. — [JCGM, VIM, 3rd ed., §2.25](https://jcgm.bipm.org/vim/en/2.25.html) (accessed 2026-10-14)
- ACM's own appendix cites VIM directly: "The primary reference for terminology in physical measurement is International Vocabulary of Metrology – Basic and General Concepts and Associated Terms (VIM), 3rd edition, JCGM 200:2012... The connection to experimental computer science is this: the result of an experiment can be thought of as a measurement, albeit one of a virtual object." — [ACM Artifact Review and Badging - Current, Appendix](http://web.archive.org/web/20240102044447/https://www.acm.org/publications/policies/artifact-review-and-badging-current) (accessed 2026-10-14)
- Barba (2018) notes the key gap: "The document contains no definition of 'replicability' but both definitions above use the phrase 'replicate measurements.'" She also observes that VIM's "reproducibility condition" changes at least one of: instrument, location, or operator, while the object of study/measurand stays the same — and flags that "conditions for physical measurements are a distant analogy for the complex processes of a full scientific workflow," i.e., VIM was not written with computational experiments or research teams in mind. — [Lorena A. Barba, "Terminologies for Reproducible Research," arXiv:1802.03311v1, p. 5](https://arxiv.org/pdf/1802.03311) (accessed 2026-10-14)

### Inferences
- VIM is relevant background/pedigree for ACM's terms but is not itself a computing-community standard — it is a metrology document about physical measurement precision. The computing community's "team" axis (same team vs. different team) is an addition ACM made on top of VIM; VIM itself only varies instrument/operator/location/procedure/time, with no notion of "which research group performed the measurement" as a distinct axis.
- Because VIM doesn't define "replicability," any claim that "replicability" is "the VIM/ISO definition" is imprecise — it should be attributed to ACM/NISO/NASEM as an extension beyond VIM, not to VIM itself.

### Gaps
- I did not locate a distinct ISO/IEC standard (outside VIM/JCGM 200, which is jointly published by BIPM/IEC/IFCC/ILAC/ISO/IUPAC/IUPAP/OIML) that separately defines computational/software reproducibility; VIM appears to be the only ISO-family document in this space that ACM and the literature cite.

## ML community (NeurIPS/ICML) reproducibility checklists: what they ask authors to report about randomness and environment

### Takeaway
Two related but distinct checklists exist: (1) the original "Machine Learning Reproducibility Checklist" (Joelle Pineau et al.), versions 1.x–2.0, which NeurIPS required at submission from 2019 onward and which explicitly asks for the "exact number of training and evaluation runs" and "a description of the computing infrastructure used"; and (2) the current NeurIPS "Paper Checklist" (used in recent years, e.g. 2022-2024 cycles), which asks more pointedly whether authors reported error bars with respect to random seeds and disclosed specific compute resources (worker type, memory, execution time) needed to reproduce each experiment. ICML's guidelines likewise point authors to a reproducibility checklist. Neither checklist mandates fixing/reporting a specific numeric seed value as a blanket requirement, but both require disclosure of the *number of runs* and *variance across runs* (which is how randomness from seeding is to be surfaced), plus full hardware/software environment disclosure.

### Cited Findings
- The Machine Learning Reproducibility Checklist (v2.0, April 7, 2020) by Joelle Pineau, under "For all reported experimental results, check if you include," lists verbatim: "The exact number of training and evaluation runs." / "A clear definition of the specific measure or statistics used to report results." / "A description of results with central tendency (e.g. mean) & variation (e.g. error bars)." / "The average runtime for each result, or estimated energy cost." / "A description of the computing infrastructure used." Under "For all shared code related to this work," it also lists: "Specification of dependencies." — [Joelle Pineau, "The Machine Learning Reproducibility Checklist (v2.0, Apr. 7 2020)"](https://www.cs.mcgill.ca/~jpineau/ReproducibilityChecklist.pdf) (accessed 2026-10-14)
- The same source notes the v2.0 revision's scope change: "This version (v. 2.0), is renamed the Machine Learning Paper Reproducibility Checklist, and is designed to be used simultaneously with the ML Code Submission checklist... This change clearly acknowledge[s] that the paper and the code are two separate research artefacts, each with their own checklist." — [Pineau, ReproducibilityChecklist v2.0, p. 2](https://www.cs.mcgill.ca/~jpineau/ReproducibilityChecklist.pdf) (accessed 2026-10-14)
- The NeurIPS 2019 Reproducibility Program report (Pineau et al., JMLR 2021 / arXiv:2003.12206) describes the checklist's deployment: "Version 1.1 was first deployed as a trial with NeurIPS 2018 papers, and the edited version 1.2 was deployed during the NeurIPS 2019 review process, with authors required to fill it at both initial submission and final camera-ready phases," and reports that about one third of reviewers found the checklist helpful. — [Pineau et al., "Improving Reproducibility in Machine Learning Research," JMLR 22 (2021), summarized at arXiv:2003.12206](https://www.jmlr.org/papers/volume22/20-303/20-303.pdf) (accessed 2026-10-14)
- The current NeurIPS paper checklist (per the 2022 guidelines and consistent later-year supplemental checklists on papers.neurips.cc) includes an "Experimental Result Reproducibility" item asking whether the paper "fully discloses all the information needed to reproduce the main experimental results," a compute-resources item requiring, "For each experiment... sufficient information on the computer resources (type of compute workers, memory, time of execution) needed to reproduce the experiments," and an item asking "if they reported error bars... with respect to the random seed after running experiments multiple times." — [NeurIPS 2022 Paper Checklist Guidelines](https://neurips.cc/Conferences/2022/PaperInformation/PaperChecklist); example instantiated checklists: [NeurIPS 2024 Datasets and Benchmarks Track supplemental checklist, papers.neurips.cc](https://papers.neurips.cc/paper_files/paper/2024/file/c00d37d6b04d73b870b963a4d70051c1-Supplemental-Datasets_and_Benchmarks_Track.pdf) (accessed 2026-10-14)
- ICML also directs authors to reproducibility expectations in its paper guidelines (ICML 2024 Paper Guidelines page), though I was not able to retrieve ICML's own checklist item wording verbatim within this task's search budget — see Gaps.

### Inferences
- The ML community's operational answer to "how do you report randomness" is not "state the seed value" but "run multiple times, report the variance/error bars across seeds, and disclose the exact run count" — i.e., statistical reporting of seed-induced variance rather than a promise of single-run bit-identical repetition. This is a materially different reproducibility contract than ACM's "exact replication... is not required... results must be in agreement to within a tolerance" language, but both converge on the same idea: equality is not the bar, a stated/quantified closeness is.

## Numerical reproducibility specifically: tolerance vs. exact equality, bitwise vs. numerically-equivalent guidance

### Takeaway
There is an identifiable, named distinction in the scientific-computing literature between "bitwise" (or "bit-for-bit") reproducibility — identical binary output — and a weaker, more commonly advocated standard of reproducibility "to within a tolerance" or "to a given number of digits," because floating-point addition/multiplication are not associative, so parallel execution order, compiler, and hardware differences change low-order bits even when "the same computation" is performed. ACM's own badging policy (quoted above) adopts the tolerance framing explicitly for its Results Reproduced/Replicated badges, which is a useful, authoritative "acceptance criterion" statement a blog can cite directly rather than reaching only into the HPC numerical-analysis literature.

### Cited Findings
- ACM's acceptance-criterion language (already quoted above, repeated here for this question): "In each cases, exact replication or reproduction of results is not required, or even expected. Instead, the results must be in agreement to within a tolerance deemed acceptable for experiments of the given type. In particular, differences in the results should not change the main claims made in the paper." — [ACM Artifact Review and Badging - Current](http://web.archive.org/web/20240102044447/https://www.acm.org/publications/policies/artifact-review-and-badging-current) (accessed 2026-10-14)
- On bitwise reproducibility as a named, strict standard: "Bitwise reproducibility is defined as the ability to recreate a run, and have its output match that of a previous run bit-for-bit," and "Numerical reproducibility in the strictest sense means obtaining bitwise identical results from multiple runs of the same code that consume the same inputs." — summarized from search of HPC numerical-reproducibility literature (title: "Enabling Bitwise Reproducibility for the Unstructured Computational Motif," MDPI Applied Sciences 2024) [https://www.mdpi.com/2076-3417/14/2/639] (accessed 2026-10-14) — **note: this is a paraphrase surfaced by a web-search summarizer tool, not a verbatim-fetched quotation from the paper itself; treat the exact wording as unconfirmed, though the substance (bitwise = bit-for-bit match; a named, named-distinct weaker standard exists) is corroborated by the independent source below.**
- On the reason bit-for-bit matching fails in practice and the weaker alternative: "In floating point arithmetic, addition and multiplication are not always associative, so the order in which array elements are multiplied and/or added affects truncation and rounding, ultimately affecting the final result, so bitwise identical results are often not guaranteed," and "A less stringent requirement than bitwise reproducibility would be to accept results with errors less than machine precision, leading to the need for a tolerance range for results... it may make sense to relax the requirement of bitwise reproducibility and settle on reproducible results within an accepted range of variation (or uncertainty)." — paraphrase surfaced from search of the HPC/numerical-reproducibility literature (same caveat as above: not independently verified against a verbatim-fetched primary source within this task's budget).
- There is a documented debate about whether bit-for-bit matching is even a desirable goal in HPC: proponents of relaxed tolerance "have advocated the quest for guaranteed accuracy and the use of small computing precision rather than bit-for-bit reproducibility, for speed and energy-consumption reasons," and conversely "high-precision does not guarantee bit-for-bit reproducibility, but it can ensure reproducibility to a given number of digits with high probability" — i.e., the HPC community already treats "reproducible to N digits" as a legitimate, separate acceptance criterion from "bit-for-bit identical." (Same sourcing caveat as above.)

### Inferences
- For the blog's purposes, the single strongest, most directly citable, primary-sourced formulation of "state a tolerance rather than claiming exact equality" is ACM's own badging-policy sentence quoted above ("results must be in agreement to within a tolerance deemed acceptable... differences... should not change the main claims"). This is preferable to the HPC-literature paraphrases below it, which I could not verify verbatim within budget.
- A precise acceptance criterion for a numerical result, synthesizing the two bodies of guidance found, would need to state: (a) the comparison metric (e.g., relative error, absolute error, ULPs, or an application-level outcome such as "same top-1 class"), (b) the tolerance threshold, and (c) whether the criterion is "bit-for-bit" (the strictest, rarely required), "numerically equivalent within floating-point rounding" (e.g., agreement to within machine epsilon accumulated error), or "within a stated application-relevant tolerance" (ACM's framing, and the most common practical standard for ML results where stochastic training makes bit-for-bit matching impossible even in principle).

## Software supply chain: "Reproducible Builds" and how it differs from numerical/computational reproducibility

### Takeaway
"Reproducible Builds" (the project, at reproducible-builds.org) defines reproducibility as a property of the *build/compilation toolchain* — that compiling the same source code, in the same declared environment, with the same instructions, always yields **bit-for-bit identical binary artifacts**, verifiable by hashing. This is a security/supply-chain integrity property (proving a distributed binary matches its claimed source, detecting tampering/backdoors), and it is a categorically different claim from the kind of "reproducibility" the blog is otherwise discussing (whether a *computation's numerical output* — e.g., a trained model's accuracy, a simulation's result — matches across runs). A build can be perfectly "reproducible" in the Reproducible Builds sense while the *program it produces* is numerically non-reproducible (e.g., due to multithreading, floating-point non-associativity, or random seeding at runtime), and vice versa — numerically-stable, exactly-reproducible computational output says nothing about whether the binary that produced it can be rebuilt bit-for-bit by a third party.

### Cited Findings
- The project's own definition, verbatim: "A build is reproducible if given the same source code, build environment and build instructions, any party can recreate bit-by-bit identical copies of all specified artifacts." — [Reproducible Builds, "Definition" page](https://reproducible-builds.org/docs/definition/) (accessed 2026-10-14)
- The project's homepage framing, verbatim: Reproducible Builds is described as "a set of software development practices that create an independently-verifiable path from source to binary code." — [reproducible-builds.org homepage](https://reproducible-builds.org/) (accessed 2026-10-14)
- Verification method, as described on the definition page: verification happens "through bit-by-bit comparison, typically using cryptographically secure hash functions to confirm the artifacts match exactly" (per the definition page's further explanation). — [Reproducible Builds, "Definition" page](https://reproducible-builds.org/docs/definition/) (accessed 2026-10-14)
- Purpose/motivation, from search summary of the homepage: "Reproducible Builds provide certainty that software is genuine and has not been tampered with. This allows people to verify that binaries downloadable from the net actually come from the corresponding sources and have not, for example, had malware added to them." — [reproducible-builds.org](https://reproducible-builds.org/) (accessed 2026-10-14)

### Inferences (one-paragraph clarification for the blog)
Reproducible Builds is about the **compilation/packaging pipeline**: "if I give you my source code and you follow my build instructions in the declared environment, your binary file is byte-for-byte identical to mine" — a deterministic-compiler, supply-chain-security property, checked by comparing file hashes. This is entirely orthogonal to the question the rest of this note addresses, which is whether **running** a program (the already-built binary, or an interpreted/compiled ML pipeline) on possibly-different hardware, with possibly-different random seeds or floating-point execution order, **produces the same numbers**. A project can have a perfectly reproducible build (identical binary) that still produces different output on different runs because of runtime randomness or non-deterministic parallel floating-point reduction order; conversely, a program's numerical output can be exactly reproducible across machines even if the binaries that run it were built non-reproducibly (e.g., containing embedded build timestamps that differ byte-for-byte but don't affect runtime behavior). The blog should keep these two senses of "reproducible" clearly separated and, if it invokes "Reproducible Builds" terminology at all, flag explicitly that it is a build-artifact/security concept, not a claim about a computation's numerical output.
