# Sources of Nondeterminism in GPU Computation (CUDA / PyTorch) and Official Reproducibility Mechanisms

Scope note: PyTorch quotes below are taken from the **PyTorch 2.14 documentation** (docs.pytorch.org/docs/2.14/..., fetched 2026-10-14; this is the version served at the "stable" alias at the time of research). NVIDIA quotes are from the **current (2026) cuBLAS and cuDNN** documentation unless otherwise noted. Where a statement is version-specific, the version is given inline.

## PyTorch's official "Reproducibility" page: exact claims about same-machine, cross-release, and cross-platform reproducibility

### Takeaway
PyTorch's official position, stated in the opening paragraph of its "Reproducibility" notes page, is an explicit **non-guarantee**: results are not guaranteed to be identical across releases, commits, or platforms, and not even guaranteed to match between CPU and GPU execution with the same seed. The page frames determinism as something the user must actively opt into at a cost to performance, not a default property of PyTorch.

### Cited Findings
- "Completely reproducible results are not guaranteed across PyTorch releases, individual commits, or different platforms. Furthermore, results may not be reproducible between CPU and GPU executions, even when using identical seeds." — [PyTorch Reproducibility notes, PyTorch 2.14](https://docs.pytorch.org/docs/2.14/notes/randomness.html) (accessed 2026-10-14)
- "However, there are some steps you can take to limit the number of sources of nondeterministic behavior for a specific platform, device, and PyTorch release." — same source (note the qualifier: determinism is only ever claimed "for a specific platform, device, and PyTorch release," never across them.)
- "First, you can control sources of randomness that can cause multiple executions of your application to behave differently. Second, you can configure PyTorch to avoid using nondeterministic algorithms for some operations, so that multiple calls to those operations, given the same inputs, will produce the same result." — same source
- Warning box on the same page: "Deterministic operations are often slower than nondeterministic operations, so single-run performance may decrease for your model. However, determinism may save time in development by facilitating experimentation, debugging, and regression testing." — same source
- `torch.manual_seed()`: "You can use torch.manual_seed() to seed the RNG for all devices (both CPU and CUDA)." — same source
- "Some PyTorch operations may use random numbers internally. torch.svd_lowrank() does this, for instance. Consequently, calling it multiple times back-to-back with the same input arguments may give different results. However, as long as torch.manual_seed() is set to a constant at the beginning of an application and all other sources of nondeterminism have been eliminated, the same series of random numbers will be generated each time the application is run in the same environment." — same source (note "in the same environment" — another implicit cross-platform caveat)
- CUDA convolution benchmarking: "The cuDNN library, used by CUDA convolution operations, can be a source of nondeterminism across multiple executions of an application. ... Due to benchmarking noise and different hardware, the benchmark may select different algorithms on subsequent runs, even on the same machine." — same source (explicitly: nondeterminism can occur even on the *same machine*, across runs, because of benchmarking noise)
- "Disabling the benchmarking feature with torch.backends.cudnn.benchmark = False causes cuDNN to deterministically select an algorithm, possibly at the cost of reduced performance." — same source
- CUDA RNN/LSTM: "In some versions of CUDA, RNNs and LSTM networks may have non-deterministic behavior. See torch.nn.RNN() and torch.nn.LSTM() for details and workarounds." — same source
- DataLoader: "DataLoader will reseed workers following the Randomness in multi-process data loading algorithm. Use worker_init_fn() and generator to preserve reproducibility." The page gives the canonical pattern: a `seed_worker(worker_id)` function that reads `torch.initial_seed() % 2**32` and reseeds NumPy/`random`, combined with a `torch.Generator` passed as `generator=g` to `DataLoader`. — same source
- `torch.use_deterministic_algorithms()`: "lets you configure PyTorch to use deterministic algorithms instead of nondeterministic ones where available, and to throw an error if an operation is known to be nondeterministic (and without a deterministic alternative)." — same source
- Scaled Dot Product Attention (SDPA) determinism table (new content on the 2.14 page, not present in older PyTorch doc versions): MATH backend is "Deterministic / Deterministic" (forward/backward); FLASH_ATTENTION is "Deterministic / Non-deterministic" because "The backward pass uses non-deterministic atomic operations by default" (fixable via `torch.use_deterministic_algorithms(True, warn_only=False)`); EFFICIENT_ATTENTION backward is non-deterministic because it "may split work across keys (num_splits_key > 1) for performance"; CUDNN_ATTENTION backward is non-deterministic, and the doc notes "cuDNN provides an opt-in deterministic backward for float16 starting in cuDNN 9.18 (via set_deterministic_algorithm), but this has not yet been integrated into PyTorch." — [same source](https://docs.pytorch.org/docs/2.14/notes/randomness.html)
- "Bitwise matching numerics across different SDPA backends are not guaranteed, even for the same inputs and dtype. Each backend performs floating-point accumulation in a different order, and because floating-point addition is not associative, the results will differ between backends." — same source (this is a direct, named statement of the floating-point non-associativity mechanism, applied specifically to attention kernels)
- "Operations like torch.empty() and torch.Tensor.resize_() can return tensors with uninitialized memory that contain undefined values... torch.utils.deterministic.fill_uninitialized_memory is set to True by default, which will fill the uninitialized memory with a known value if torch.use_deterministic_algorithms(True) is set." — same source

### Inferences
- The page's repeated phrasing "for a specific platform, device, and PyTorch release" functions as PyTorch's de facto reproducibility contract: determinism is only ever promised within one fixed (hardware, software-version) combination, never across upgrades or across different GPUs.
- The newly documented SDPA determinism table (present in the 2.14 docs fetched here) is evidence that PyTorch's own documented determinism story has materially expanded/changed recently as fused-attention kernels became the default attention path; a blog citing this should note that older PyTorch versions' docs did not carry this table.

### Gaps
- I could not confirm the exact version of PyTorch in which the SDPA determinism table was first added (it is present in 2.14, fetched here); could not access earlier version diffs to pin down the introduction release.
- The page does not explicitly use the term "CUBLAS_WORKSPACE_CONFIG" — that linkage is established via `torch.use_deterministic_algorithms` runtime behavior and the "CUDA semantics" page's "cuBLAS workspaces" section, not the Reproducibility page itself (see next section).

## `torch.use_deterministic_algorithms(True)`: behavior, non-deterministic-operation list, and performance cost

### Takeaway
`torch.use_deterministic_algorithms(mode, *, warn_only=False)` forces PyTorch to either substitute a slower deterministic kernel or raise a `RuntimeError` for operations whose only CUDA implementation is nondeterministic; PyTorch's own docs enumerate dozens of affected ops and state flatly that "deterministic operations tend to have worse performance than nondeterministic operations."

### Cited Findings
- Definition: "Sets whether PyTorch operations must use 'deterministic' algorithms. That is, algorithms which, given the same input, and when run on the same software and hardware, always produce the same output. When enabled, operations will use deterministic algorithms when available, and if only nondeterministic algorithms are available they will throw a RuntimeError when called." — [torch.use_deterministic_algorithms, PyTorch 2.14](https://docs.pytorch.org/docs/2.14/generated/torch.use_deterministic_algorithms.html) (accessed 2026-10-14)
- Note box: "This setting alone is not always enough to make an application reproducible. Refer to Reproducibility for more information." — same source
- Full documented list of operations that **switch to a deterministic algorithm** when `mode=True` (i.e., they have a deterministic alternative, used at a performance cost): `torch.nn.Conv1d/2d/3d` and `ConvTranspose1d/2d/3d` (CUDA), `torch.nn.ReplicationPad1d/2d/3d` (CUDA, differentiating), `torch.bmm()` (sparse-dense CUDA), `torch.cumsum()` (CUDA, float/complex), `torch.Tensor.__getitem__()` (CPU, differentiating, list-of-tensors index), `torch.Tensor.index_put()` (accumulate=False; accumulate=True on CPU), `torch.Tensor.put_()` (accumulate=True, CPU), `torch.Tensor.scatter_add_()` (CUDA), `torch.gather()` (CUDA, requires grad), `torch.index_add()` (CUDA), `torch.index_select()` (CUDA, differentiating), `torch.repeat_interleave()` (CUDA, differentiating), `torch.Tensor.index_copy()` (CPU or CUDA), `torch.Tensor.scatter()` (src is Tensor, CUDA), `torch.Tensor.scatter_reduce()` (reduce='sum' or 'mean', CUDA), `torch.nn.MaxPool3d` (CUDA, differentiating), `torch.nn.Embedding` (CUDA, differentiating). — same source
- Full documented list of operations that **throw `RuntimeError`** when `mode=True` because they have **no deterministic implementation at all**: `torch.nn.AvgPool3d`, `torch.nn.AdaptiveAvgPool2d`, `torch.nn.AdaptiveAvgPool3d`, `torch.nn.AdaptiveMaxPool2d` (all CUDA, differentiating), `torch.nn.FractionalMaxPool2d`, `torch.nn.FractionalMaxPool3d` (CUDA, differentiating), `torch.nn.MaxUnpool1d/2d/3d`, `torch.nn.functional.interpolate()` in `linear`/`bilinear`/`bicubic`/`trilinear` modes (CUDA, differentiating), `torch.nn.ReflectionPad1d/2d/3d` (CUDA, differentiating), `torch.nn.NLLLoss` (CUDA), `torch.nn.CTCLoss` (CUDA, differentiating), `torch.nn.EmbeddingBag` with `mode='max'` (CUDA, differentiating), `torch.Tensor.put_()` (accumulate=False; or accumulate=True on CUDA), `torch.histc()` (CUDA), `torch.bincount()` (CUDA with weights), `torch.median()` with indices (CUDA), `torch.nn.functional.grid_sample()` (CUDA, differentiating), `torch.Tensor.scatter_reduce()` with `reduce='prod'` (CUDA), `torch.Tensor.resize_()` (quantized tensor). — same source
- Worked example of the error: `>>> torch.use_deterministic_algorithms(True); torch.randn(2, 2).cuda().index_add_(0, torch.tensor([0, 1]), torch.randn(2, 2))` produces `RuntimeError: index_add_cuda_ does not have a deterministic implementation, but you set 'torch.use_deterministic_algorithms(True)'. ...` — same source (note: `index_add_` is also listed, inconsistently, in the "has a deterministic alternative" list for `torch.index_add()`, non-in-place; the in-place `index_add_` variant used in the error example is one of the harder cases — flagged as a nuance, not a contradiction, since the doc distinguishes the out-of-place function from some in-place/backward paths)
- `warn_only` parameter: "warn_only (bool, optional) – If True, operations that do not have a deterministic implementation will throw a warning instead of an error. Default: False" — same source
- Performance cost statement: "Note that deterministic operations tend to have worse performance than nondeterministic operations." — same source
- Additional cost: enabling this setting also forces `torch.utils.deterministic.fill_uninitialized_memory` behavior (filling uninitialized memory with a known value), which the Reproducibility page separately states "is detrimental to performance." — [Reproducibility notes](https://docs.pytorch.org/docs/2.14/notes/randomness.html)
- `torch.compile`/Inductor cost: "When this setting is turned on, the Inductor deterministic mode is also t[urned] on automatically. In deterministic mode, Inductor would avoid doing on device benchmarking that affect numerics." This includes: not padding matmul input shapes, not autotuning templates (matmul/conv/attention kernels fall back to the eager kernel instead of the fastest autotuned one), not autotuning Triton reduction configs, skipping autotuning in coordinate-descent tuning, not reordering computation/communication, and disabling dynamic RBLOCK scaling for occupancy. — [torch.use_deterministic_algorithms, PyTorch 2.14](https://docs.pytorch.org/docs/2.14/generated/torch.use_deterministic_algorithms.html)
- Explicit scope limitation: "This flag does not detect or prevent nondeterministic behavior caused by calling an inplace operation on a tensor with an internal memory overlap or by giving such a tensor as the out argument for an operation. In these cases, multiple writes of different data may target a single memory location, and the order of writes is not guaranteed." — same source

### Inferences
- The two lists (switchable vs. hard-error) together show that nondeterminism in deep learning is concentrated in **backward passes of pooling/sampling/loss ops** and in **scatter/gather/index-accumulate ops** — i.e., exactly the places where multiple input elements must be atomically summed into fewer output elements, which is the atomics mechanism discussed below.
- The Inductor/`torch.compile` cost list shows that the "performance cost" of determinism is not limited to kernel choice; it also forecloses several compiler-level optimizations (autotuning, padding, operator reordering), compounding the slowdown for compiled models beyond eager-mode kernel substitution alone.

### Gaps
- PyTorch's docs state the qualitative claim "deterministic operations tend to have worse performance" but do not give a single documented quantitative benchmark (e.g., "X% slower") on this page; any specific slowdown percentage would need to come from a separate benchmark, which was not located in this research pass.

## `CUBLAS_WORKSPACE_CONFIG=:4096:8` / `:16:8`: why required, what it controls, which CUDA version

### Takeaway
NVIDIA's own cuBLAS documentation states that bit-wise reproducibility is guaranteed only "when a single CUDA stream is active"; once multiple concurrent streams share a cuBLAS handle, the library may pick different internal algorithms for performance, breaking the guarantee. `CUBLAS_WORKSPACE_CONFIG` fixes this by forcing a specific, static GPU-memory workspace layout so the library can no longer silently switch code paths. PyTorch itself raises a runtime error directing users to set this variable when deterministic mode is requested on CUDA ≥ 10.2.

### Cited Findings
- "By design, all cuBLAS API routines from a given toolkit version, generate the same bit-wise results at every run when executed on GPUs with the same architecture and the same number of SMs." — [cuBLAS documentation, "Results Reproducibility," docs.nvidia.com/cuda/cublas](https://docs.nvidia.com/cuda/cublas/) (accessed 2026-10-14)
- "This guarantee no longer holds when multiple CUDA streams are active or fixed-point emulation is used." — same source. (i.e., even on identical hardware and identical cuBLAS version, multi-stream execution alone is sufficient to break bitwise reproducibility.)
- Mechanism: "the library may optimize total performance by picking different internal implementations" when multiple concurrent streams are active. — same source
- Remedy and exact cost: "users can set a debug environment variable CUBLAS_WORKSPACE_CONFIG to ':16:8' (may limit overall performance) or ':4096:8' (will increase library footprint in GPU memory by approximately 24MiB)." — same source. "The first configuration instructs cuBLAS to allocate eight buffers of 16 KB each in GPU memory while the second setting creates two buffers of 4 MB each." — same source (note: `:4096:8` syntax is `:[SIZE_KB]:[COUNT]`, so this is 8 buffers of 4096 KiB = 32 MiB total request, consistent with the "~24MiB increase" figure cited for the net additional footprint over default allocation)
- Alternatives documented by NVIDIA: "Users can alternatively provide a separate workspace for each used stream using the cublasSetWorkspace() function, have one cuBLAS handle per stream, or use cublasLtMatmul() instead of GEMM-family of functions with user owned workspace. ... Providing workspace via cublasSetWorkspace() avoids both the allocation cost and the fallback path, and is required to guarantee reproducible results [in that configuration]." — same source
- PyTorch's own "cuBLAS workspaces" documentation (CUDA semantics page) describes the variable's format precisely: "The workspace size per allocation can be specified via the environment variable CUBLAS_WORKSPACE_CONFIG with the format :[SIZE]:[COUNT]. As an example, the default workspace size per allocation is CUBLAS_WORKSPACE_CONFIG=:4096:2:16:8 which specifies a total size of 2 * 4096 + 8 * 16 KiB. To force cuBLAS to avoid using workspaces, set CUBLAS_WORKSPACE_CONFIG=:0:0." — [PyTorch CUDA semantics, PyTorch 2.14](https://docs.pytorch.org/docs/2.14/notes/cuda.html) (accessed 2026-10-14)
- PyTorch's runtime enforcement (documented behavior confirmed via PyTorch GitHub issue discussion and widely-reproduced error text, not found verbatim on the current docs page itself): calling `torch.use_deterministic_algorithms(True)` on CUDA ≥ 10.2 without the env var set raises `RuntimeError: Deterministic behavior was enabled with either 'torch.use_deterministic_algorithms(True)' or 'at::Context::setDeterministicAlgorithms(true)', but this operation is not deterministic because it uses CuBLAS and you have CUDA >= 10.2. To enable deterministic behavior in this case, you must set an environment variable before running your PyTorch application: CUBLAS_WORKSPACE_CONFIG=:4096:8 or CUBLAS_WORKSPACE_CONFIG=:16:8.` The variable "should be set prior to the call to torch.use_deterministic_algorithms(True)" and must be set before CUDA context/library initialization. — [PyTorch GitHub issue discussion, aggregated](https://github.com/pytorch/pytorch/issues/120240); [PyTorch PR #41377, "Throw error if torch.set_deterministic(True) is called with nondeterministic CuBLAS config"](https://github.com/pytorch/pytorch/pull/41377)

### Inferences
- The CUDA-version trigger ("CUDA >= 10.2") lines up with cuBLAS's own documented caveat about multi-stream nondeterminism: CUDA 10.2 is when PyTorch's internal GEMM dispatch started using multiple streams/handles in ways that could hit the cuBLAS multi-stream fallback path, so the workaround is specifically about disabling that fallback, not a general cuBLAS versioning issue.
- `:4096:8` vs `:16:8` is a size/performance tradeoff: `:4096:8` (8 × 4 MiB = 32 MiB of workspace) wastes more memory but is less likely to force cuBLAS down the slower reproducibility path for large GEMMs, while `:16:8` (8 × 16 KiB) uses far less memory but "may limit overall performance" because workspace is too small for some kernels to use their fastest implementation.

### Gaps
- I could not directly fetch the PyTorch source file that contains the literal current error string to confirm it has not been reworded in 2.14; the string is cited from issue-tracker secondary sources and is consistent with long-standing PyTorch behavior since at least 1.8, but I could not verify the exact current wording against the live PyTorch 2.14 codebase in this session.
- NVIDIA's cuBLAS doc page did not state a specific minimum cuBLAS/CUDA Toolkit version at which `CUBLAS_WORKSPACE_CONFIG` was introduced as a recognized variable; PyTorch's own reproducibility guidance associates the requirement with "CUDA >= 10.2."

## cuDNN: `torch.backends.cudnn.benchmark` and `torch.backends.cudnn.deterministic`

### Takeaway
`cudnn.benchmark=True` lets cuDNN auto-tune by running several convolution algorithms per input shape and caching the fastest — introducing run-to-run nondeterminism because the "fastest" algorithm can vary with benchmarking noise and hardware state. `cudnn.deterministic=True` forces cuDNN to only pick from algorithms that are themselves bitwise-deterministic, which is a narrower guarantee than `torch.use_deterministic_algorithms()`.

### Cited Findings
- "A bool that, if True, causes cuDNN to benchmark multiple convolution algorithms and select the fastest." — [torch.backends.cudnn.benchmark, PyTorch 2.14 `torch.backends`](https://docs.pytorch.org/docs/2.14/backends.html) (accessed 2026-10-14)
- "A bool that, if True, causes cuDNN to only use deterministic convolution algorithms. See also torch.are_deterministic_algorithms_enabled() and torch.use_deterministic_algorithms()." — [torch.backends.cudnn.deterministic, same source]
- `torch.backends.cudnn.benchmark_limit`: "A int that specifies the maximum number of cuDNN convolution algorithms to try when torch.backends.cudnn.benchmark is True. Set benchmark_limit to zero to try every available algorithm. Note that this setting only affects convolutions dispatched via the cuDNN v8 API." — same source
- Mechanism and risk, from the Reproducibility notes page: "When a cuDNN convolution is called with a new set of size parameters, an optional feature can run multiple convolution algorithms, benchmarking them to find the fastest one. Then, the fastest algorithm will be used consistently during the rest of the process for the corresponding set of size parameters. Due to benchmarking noise and different hardware, the benchmark may select different algorithms on subsequent runs, even on the same machine." — [PyTorch Reproducibility notes, PyTorch 2.14](https://docs.pytorch.org/docs/2.14/notes/randomness.html)
- "Disabling the benchmarking feature with torch.backends.cudnn.benchmark = False causes cuDNN to deterministically select an algorithm, possibly at the cost of reduced performance. However, if you do not need reproducibility across multiple executions of your application, then performance might improve if the benchmarking feature is enabled... Note that this setting is different from the torch.backends.cudnn.deterministic setting." — same source
- Relationship between the two flags: "While disabling CUDA convolution benchmarking ... ensures that CUDA selects the same algorithm each time an application is run, that algorithm itself may be nondeterministic, unless either torch.use_deterministic_algorithms(True) or torch.backends.cudnn.deterministic = True is set. The latter setting controls only this behavior, unlike torch.use_deterministic_algorithms() which will make other PyTorch operations behave deterministically, too." — same source (this is the key clarifying statement: `benchmark=False` alone only fixes *which* algorithm gets selected across runs — it does not make that algorithm's output deterministic if the algorithm itself internally uses atomics)
- Underlying NVIDIA-side cause for "that algorithm itself may be nondeterministic": cuDNN's own documentation states certain convolution/pooling backward algorithms "use atomic operations in a way that introduces truly random floating point rounding errors," naming `cudnnConvolutionBackwardFilter` with `CUDNN_CONVOLUTION_BWD_FILTER_ALGO_0` or `_ALGO_3`, `cudnnConvolutionBackwardData` with `CUDNN_CONVOLUTION_BWD_DATA_ALGO_0`, `cudnnPoolingBackward` when using `CUDNN_POOLING_MAX`, `cudnnSpatialTfSamplerBackward`, and `cudnnCTCLoss`/`cudnnCTCLoss_v8` with `CUDNN_CTC_LOSS_ALGO_NON_DETERMINSTIC`. — [NVIDIA cuDNN Backend documentation, "Odds and Ends"](https://docs.nvidia.com/deeplearning/cudnn/backend/latest/developer/misc.html) (accessed 2026-10-14)
- Baseline guarantee and its limit (same NVIDIA page): "most of cuDNN's routines from a given version generate the same bit-wise results across runs when executed on GPUs with the same architecture," but "Across different architectures, no cuDNN routines guarantee bitwise reproducibility," giving the explicit example of "the same routine run on NVIDIA Volta and NVIDIA Turing architecture." — same source

### Inferences
- `cudnn.benchmark` and `cudnn.deterministic` address two independent failure modes: (1) *which* algorithm cuDNN picks can vary run-to-run (fixed by `benchmark=False`), and (2) *that* algorithm's own internal accumulation order can be nondeterministic regardless of which one is picked (fixed only by `deterministic=True` or `use_deterministic_algorithms(True)`, which restrict selection to the atomics-free algorithm variants).
- Because benchmark-selected algorithms are chosen based on timing measurements, "benchmarking noise" nondeterminism is a scheduling/timing artifact (OS jitter, other GPU workload, clock throttling) rather than a numeric one — distinct in kind from the atomics-based nondeterminism described next.

### Gaps
- Could not verify an exact statement from NVIDIA about whether cuDNN v9.18's new opt-in deterministic FlashAttention-style backward (`set_deterministic_algorithm`, referenced in the PyTorch SDPA table above) is documented with its own "Reproducibility" section; this was only found referenced from the PyTorch side.

## Atomic operations: why `atomicAdd` on floats is nondeterministic, and which DL ops use atomics

### Takeaway
`atomicAdd` guarantees that each read-modify-write is indivisible (no lost updates), but it makes no guarantee about the *order* in which concurrently-scheduled threads' adds are applied; combined with the non-associativity of floating-point addition, a different commit order produces a different final sum. In deep learning, this affects any backward/forward op that must scatter-accumulate many inputs into fewer outputs on the GPU — PyTorch's own deterministic-algorithms list names index_add, scatter_add_, embedding backward, and several pooling backwards as exactly the ops affected.

### Cited Findings
- `atomicAdd` semantics: "atomicAdd(address, val) reads the ... word old located at the address address in global or shared memory, computes (old + val), and stores the result back to memory at the same address. These three operations are performed in one atomic transaction and return[s the] old value... the operation is atomic in the sense that it is guaranteed to be performed without interference from other threads. In other words, no other thread can access this address until the operation is complete." — CUDA atomic functions semantics, aggregated from NVIDIA CUDA C Programming Guide content (I was not able to directly load the specific page/anchor in this session — see Gaps — so this wording should be treated as a close paraphrase of the official definition rather than a directly-verified verbatim quote; the atomicity guarantee itself — "no interference," "no other thread can access ... until complete" — is the standard, long-stable CUDA Programming Guide formulation).
- Critically, atomicity is only about **mutual exclusion**, not about **order**: the Programming Guide's guarantee covers correctness of each individual add (no lost updates), but it does not specify which thread's add happens first, second, etc. Because thread scheduling on a GPU is itself nondeterministic (warp/block scheduling order depends on runtime occupancy, memory latency, and other concurrent kernels), the sequence of partial sums — and hence the rounding behavior of the accumulation — varies from launch to launch even with identical inputs.
- Floating-point non-associativity as the amplifying factor is stated directly by PyTorch for a closely related case (attention backends): "Each backend performs floating-point accumulation in a different order, and because floating-point addition is not associative, the results will differ between backends." — [PyTorch Reproducibility notes, PyTorch 2.14](https://docs.pytorch.org/docs/2.14/notes/randomness.html). The same non-associativity argument is the documented reason cuDNN gives for atomics-based nondeterminism (see cuDNN section above): algorithms using atomic adds "introduce truly random floating point rounding errors." — [NVIDIA cuDNN "Odds and Ends"](https://docs.nvidia.com/deeplearning/cudnn/backend/latest/developer/misc.html)
- DL operations PyTorch documents as using nondeterministic (presumably atomics-based) CUDA kernels, confirmed from the official `torch.use_deterministic_algorithms` operation lists (quoted in full above): **scatter/index-accumulate family** — `torch.Tensor.scatter_add_()` (CUDA), `torch.index_add()` (CUDA), `torch.Tensor.index_put()` with `accumulate=True`, `torch.Tensor.scatter_reduce()` with `reduce='sum'`/`'mean'`/`'prod'`; **embedding** — `torch.nn.Embedding` backward (CUDA) and `torch.nn.EmbeddingBag` backward with `mode='max'` (CUDA, no deterministic alternative at all); **pooling backwards** — `torch.nn.MaxPool3d` backward (CUDA, has deterministic alt), `torch.nn.AvgPool3d`, `AdaptiveAvgPool2d/3d`, `AdaptiveMaxPool2d`, `FractionalMaxPool2d/3d` backward (CUDA, no deterministic alternative); **loss functions** — `torch.nn.CTCLoss` backward (CUDA), `torch.nn.NLLLoss` (CUDA); **attention** — FlashAttention and memory-efficient-attention backward kernels ("non-deterministic atomic operations by default", per the SDPA table). — [torch.use_deterministic_algorithms, PyTorch 2.14](https://docs.pytorch.org/docs/2.14/generated/torch.use_deterministic_algorithms.html) and [Reproducibility notes](https://docs.pytorch.org/docs/2.14/notes/randomness.html)
- cuDNN side: the specific backward-convolution and pooling algorithms named as atomics-based and nondeterministic are `cudnnConvolutionBackwardFilter` (`ALGO_0`, `ALGO_3`), `cudnnConvolutionBackwardData` (`ALGO_0`), `cudnnPoolingBackward` with `CUDNN_POOLING_MAX`, `cudnnSpatialTfSamplerBackward`, `cudnnCTCLoss`/`cudnnCTCLoss_v8` with `CUDNN_CTC_LOSS_ALGO_NON_DETERMINSTIC`. — [NVIDIA cuDNN "Odds and Ends"](https://docs.nvidia.com/deeplearning/cudnn/backend/latest/developer/misc.html)
- The NVIDIA/Duncan-Riach-associated `framework-reproducibility` project (formerly `framework-determinism`) states its own scope as: "provide documentation, status, patches, and tools related to determinism (bit-accurate, run-to-run reproducibility) in deep learning frameworks, with a focus on determinism when running on GPUs." — [github.com/NVIDIA/framework-reproducibility](https://github.com/NVIDIA/framework-reproducibility) (accessed 2026-10-14; README fetched via raw.githubusercontent.com)

### Inferences
- The two independent, converging statements — PyTorch's "floating-point addition is not associative, the results will differ between backends" and NVIDIA cuDNN's "atomic operations ... introduce truly random floating point rounding errors" — together give the complete causal chain for the blog: (1) GPU thread/warp scheduling order is not fixed run-to-run, (2) `atomicAdd` only prevents lost updates, not reordering, so (3) the sequence of partial sums differs between runs, and (4) because `(a+b)+c != a+(b+c)` in floating point, different sequences produce different final bit patterns — all without any single step being "wrong."
- Scatter/gather-style accumulation (embedding backward, scatter_add, index_add) is structurally the same pattern as convolution/pooling backward with atomics (many-to-one reduction over an output addressed by a runtime-computed index), which is why PyTorch's and NVIDIA's lists of nondeterministic ops cluster around the same operation shape.

## TF32 (TensorFloat-32): definition, GPU generation support, PyTorch flags, and default-value history

### Takeaway
TF32 is a tensor-core compute mode (not a storage format) that takes FP32 inputs, truncates the multiplicand to a 10-bit mantissa for the multiply, and accumulates in full FP32 — available since Ampere. PyTorch exposed TF32 controls since 1.7, defaulted CUDA-matmul TF32 **on** through 1.11 then flipped it **off** by default from 1.12 onward (cuDNN-convolution TF32 has remained on by default throughout), and starting with PyTorch 2.9 introduced a new, more granular `fp32_precision` string-based API ("ieee"/"tf32") intended to eventually replace the boolean `allow_tf32` flags.

### Cited Findings
- Precision definition: "TF32 tensor cores are designed to achieve better performance on matmul and convolutions on torch.float32 tensors by rounding input data to have 10 bits of mantissa, and accumulating results with FP32 precision, maintaining FP32 dynamic range." — [PyTorch CUDA semantics, "TensorFloat-32 (TF32) on Ampere (and later) devices," PyTorch 2.14](https://docs.pytorch.org/docs/2.14/notes/cuda.html) (accessed 2026-10-14)
- NVIDIA's own framing: TF32 "computes the products" at reduced mantissa precision (TF32 format: "8 exponent bits, 10 bits of mantissa, and one sign bit") and "accumulate[s] those products into an FP32 output," i.e., full FP32 accumulation. — [NVIDIA Developer Blog, "Accelerating AI Training with NVIDIA TF32 Tensor Cores"](https://developer.nvidia.com/blog/accelerating-ai-training-with-tf32-tensor-cores/) (accessed 2026-10-14)
- GPU generations: "NVIDIA Ampere GPU architecture introduced the third generation of Tensor Cores, with the new TensorFloat32 (TF32) mode." — same source. PyTorch's doc consistently refers to "Ampere or newer GPUs" for both `torch.backends.cuda.matmul.allow_tf32` and `torch.backends.cudnn.allow_tf32`. — [torch.backends, PyTorch 2.14](https://docs.pytorch.org/docs/2.14/backends.html)
- Accuracy/perf tradeoff quantified by PyTorch's own worked example (A100, 10240×10240 matmul): with TF32 on, "ab_tf32 ... takes 0.016s on GA100" vs. FP32 "ab_fp32 ... takes 0.11s on GA100" — roughly 7× faster — while the max absolute error vs. a double-precision reference grows from 0.0031 (FP32) to 0.1747 (TF32), i.e., roughly two orders of magnitude larger relative error (0.000039 vs. 0.0022). — [PyTorch CUDA semantics, PyTorch 2.14](https://docs.pytorch.org/docs/2.14/notes/cuda.html)
- NVIDIA's accuracy claim at the training-workload level: "All the dozens of considered DL workloads match FP32 accuracy, loss values, and training behavior, with no changes to hyperparameters or training scripts," with "speedups of 2-6x ... observed in practice for single-precision training of various workloads when moving from V100 to A100." — [NVIDIA Developer Blog, TF32 Tensor Cores](https://developer.nvidia.com/blog/accelerating-ai-training-with-tf32-tensor-cores/)
- PyTorch flags (legacy, boolean): "torch.backends.cuda.matmul.allow_tf32 — A bool that controls whether TensorFloat-32 tensor cores may be used in matrix multiplications on Ampere or newer GPUs. allow_tf32 is going to be deprecated." "torch.backends.cudnn.allow_tf32 — A bool that controls where TensorFloat-32 tensor cores may be used in cuDNN convolutions on Ampere or newer GPUs. allow_tf32 is going to be deprecated." — [torch.backends, PyTorch 2.14](https://docs.pytorch.org/docs/2.14/backends.html)
- Default-value history, stated explicitly by PyTorch: "Starting in PyTorch 1.7, there is a new flag called allow_tf32. ... This flag defaults to True in PyTorch 1.7 to PyTorch 1.11, and False in PyTorch 1.12 and later." For the two separate flags: "The flag below controls whether to allow TF32 on matmul. This flag defaults to False in PyTorch 1.12 and later. torch.backends.cuda.matmul.allow_tf32 = True" and "The flag below controls whether to allow TF32 on cuDNN. This flag defaults to True. torch.backends.cudnn.allow_tf32 = True" — [PyTorch CUDA semantics, PyTorch 2.14](https://docs.pytorch.org/docs/2.14/notes/cuda.html) (so: **matmul TF32 default flipped off in 1.12; cuDNN-convolution TF32 has remained on by default** through at least 2.14 under the legacy API)
- Newer, more granular API (introduced "After PyTorch 2.9" per PyTorch's own doc): "we provide a new sets of APIs to control the TF32 behavior in a more fine-grained way... We can set float32 precision per backend and per operators." Settings shown: `torch.backends.fp32_precision`, `torch.backends.cuda.matmul.fp32_precision`, `torch.backends.cudnn.fp32_precision`, `torch.backends.cudnn.conv.fp32_precision`, `torch.backends.cudnn.rnn.fp32_precision`, each accepting the string `"ieee"` ("we will use FP32 as internal computation precision") or `"tf32"` ("we will allow to use TF32 as internal computation precision"), with explicit precedence rules (an operator-specific setting overrides the generic/backend setting). "Old settings with allow_tf32 ... [are] going to be deprecated... we do not support ... mix of old and new settings." — [PyTorch CUDA semantics, PyTorch 2.14](https://docs.pytorch.org/docs/2.14/notes/cuda.html)
- `torch.set_float32_matmul_precision(precision)`: documented options are `"highest"` (avoid lower precision — i.e., standard FP32, **no TF32**), `"high"` (allow TF32, or treat an FP32 number as the sum of two bfloat16 numbers), and `"medium"` (allow BF16). On Ampere/Hopper, `"high"`/`"medium"` are what actually engages TF32-class Tensor Core matmul; the **default is `"highest"`**, i.e., **TF32 is off by default for the general `set_float32_matmul_precision` global knob as well**, matching the `allow_tf32` default since 1.12. — aggregated from [docs mirror / PyTorch doc content via search](https://www.aidoczh.com/pytorch/generated/torch.set_float32_matmul_precision.html) (direct fetch of the live `docs.pytorch.org` page failed with a network error in this session — flagged as not independently re-verified against the primary page); corroborated by a PyTorch maintainer's own words below.
- Confirmation that this default is intentional and a recurring point of user confusion: in GitHub issue "TF32 is disabled by default without warning," PyTorch collaborator **ngimel** responded: "We won't enable tf32 by default, because it leads to a lot of confusion and user complaints. Similarly, people don't like receiving warnings when everything is operating normally." — [pytorch/pytorch issue #153195](https://github.com/pytorch/pytorch/issues/153195) (accessed 2026-10-14)
- Scope of what TF32 affects beyond raw matmul/conv calls: "besides matmuls and convolutions themselves, functions and nn modules that internally use[] matmuls or convolutions are also affected. These include nn.Linear, nn.Conv*, cdist, tensordot, affine grid and grid sample, adaptive log softmax, GRU and LSTM." — [PyTorch CUDA semantics, PyTorch 2.14](https://docs.pytorch.org/docs/2.14/notes/cuda.html)
- Support on later GPU generations (Hopper, Blackwell): TF32 continues to be supported as the standard reduced-precision FP32 tensor-core mode; Hopper's 4th-generation tensor cores "support FP16/BF16/TF32" with improved accumulation (a "fused-dot-add" with a 25-bit fractional accumulator vs. a prior 24-bit design); Blackwell's 5th-generation tensor cores add native FP4/FP6/FP8 "micro-tensor" formats alongside the existing precision modes. — aggregated from search of NVIDIA architecture documentation/whitepapers (not independently fetched/verbatim-verified in this session for the Hopper/Blackwell accumulator-bit-width figures specifically — flagged below)

### Inferences
- The split defaults (`cuda.matmul.allow_tf32` off since 1.12, `cudnn.allow_tf32` on by default throughout) mean a model relying purely on `nn.Conv2d` layers is *silently* running in reduced TF32 precision by default on Ampere+ GPUs, while a model relying on `nn.Linear`/raw matmul is *not* — a frequent, easy-to-miss source of apparent "precision inconsistency" between convolutional and linear-algebra-heavy code paths on the same GPU with default settings.
- The move to the string-based `fp32_precision` API (2.9+) with explicit "ieee" vs. "tf32" naming (dropping the word "allow") signals PyTorch deliberately reframing TF32 from "an optional speed boost" to "an explicit alternate numerical contract," likely in response to confusion such as that surfaced in issue #153195.

### Gaps
- Could not independently re-fetch the live `docs.pytorch.org` page for `torch.set_float32_matmul_precision` in this session (network/socket errors on repeated attempts); the precision-level wording ("highest"/"high"/"medium" definitions) is reconstructed from a documentation mirror and secondary aggregation, not verified against the current primary page text verbatim.
- Could not obtain a primary NVIDIA source (architecture whitepaper or developer blog, directly fetched) confirming the specific Hopper 25-bit / prior 24-bit accumulator bit-width claim or detailed Blackwell TF32-specific statements; this was only obtained via aggregated search-engine synthesis, not a verified direct quote. Flag this specific figure as unverified if used in the blog.
- Could not find an explicit NVIDIA or PyTorch statement giving a precise release date for when Blackwell driver/toolkit support for TF32 shipped; assume continuity with Ampere/Hopper behavior unless the blog needs a specific citation, in which case further verification is required.

## Reproducibility across different GPU models/architectures, and across cuBLAS/cuDNN versions

### Takeaway
NVIDIA's own documentation draws the reproducibility boundary narrowly: cuBLAS guarantees bitwise-identical results only "on GPUs with the same architecture and the same number of SMs" (so even two cards of the same architecture family but different SM counts are not covered), and cuDNN explicitly states "no cuDNN routines guarantee bitwise reproducibility" across different architectures (its own example: Volta vs. Turing). Both guarantees are scoped to "a given toolkit version" / "a given version," i.e., they do not extend across library version upgrades either.

### Cited Findings
- cuBLAS: "By design, all cuBLAS API routines from a given toolkit version, generate the same bit-wise results at every run when executed on GPUs with the same architecture and the same number of SMs. ... This guarantee no longer holds when multiple CUDA streams are active or fixed-point emulation is used." — [cuBLAS documentation, "Results Reproducibility"](https://docs.nvidia.com/cuda/cublas/) (accessed 2026-10-14)
- cuDNN: "most of cuDNN's routines from a given version generate the same bit-wise results across runs when executed on GPUs with the same architecture," but certain atomics-based routines are exceptions even on the same architecture (see atomics section above); and "Across different architectures, no cuDNN routines guarantee bitwise reproducibility," with the explicit worked example "the same routine run on NVIDIA Volta and NVIDIA Turing architecture." — [NVIDIA cuDNN Backend documentation, "Odds and Ends"](https://docs.nvidia.com/deeplearning/cudnn/backend/latest/developer/misc.html) (accessed 2026-10-14)
- A concrete, PyTorch-side demonstration of "same architecture family, different GPU model ⇒ different results" for CUDA's own RNG (not cuBLAS/cuDNN, but the same class of claim) is documented in an open PyTorch GitHub issue: "Seeding with torch.manual_seed(s) + torch.cuda.manual_seed_all(s) and drawing from a CUDA sampler gives different values on different NVIDIA GPU models once the tensor exceeds a threshold determined by the launch geometry," with a reported concrete transition point between Tesla T4 and NVIDIA L4 at 40,960 vs. 40,961 elements. — [pytorch/pytorch issue #194676, "CUDA RNG is not reproducible across GPU models above a launch-geometry threshold"](https://github.com/pytorch/pytorch/issues/194676) (accessed 2026-10-14) — see cuRAND section below for the full mechanism.
- The NVIDIA/Duncan-Riach `framework-reproducibility` project exists specifically to document and patch this class of problem across deep learning frameworks on GPUs, per its stated scope: "provide documentation, status, patches, and tools related to determinism (bit-accurate, run-to-run reproducibility) in deep learning frameworks, with a focus on determinism when running on GPUs." — [github.com/NVIDIA/framework-reproducibility](https://github.com/NVIDIA/framework-reproducibility) (accessed 2026-10-14)

### Inferences
- "Same architecture, same SM count" (cuBLAS) is a strictly narrower condition than "same architecture" alone (cuDNN's stated boundary) — meaning a blog claim of "reproducible across GPUs of the same generation" is already too strong for cuBLAS-backed ops (e.g., an RTX 4090 vs. RTX 4060, both Ada, have different SM counts and are not covered by cuBLAS's own guarantee).
- None of the three libraries examined (cuBLAS, cuDNN, and PyTorch's CUDA RNG) make any reproducibility claim across hardware generations at all; the most any of them promises is same-architecture-same-SM-count-same-library-version, which in practice usually means "the exact same physical GPU model and driver/toolkit stack."

### Gaps
- I could not locate an explicit NVIDIA statement about reproducibility **across cuBLAS/cuDNN versions** beyond the implicit scoping phrase "from a given toolkit version" / "from a given version" (i.e., the guarantee is stated as applying within one version, with no explicit statement of what, if anything, is expected to change across versions, such as a list of algorithm changes between cuDNN releases).
- Could not access Duncan Riach's original GTC talk slides/transcript directly in this session (only the project README top-level description was retrievable); any specific quotes attributed to the GTC talks would need separate verification.

## cuRAND: bit-reproducibility for a fixed seed, across GPU models, and the thread/block-configuration relationship

### Takeaway
cuRAND (e.g., the Philox4x32-10 generator used by PyTorch's CUDA RNG) is deterministic and repeatable **for a fixed seed on a fixed thread/block launch configuration**, but PyTorch's own engineering team has documented and reproduced a concrete failure of this guarantee **across different GPU models**: because `curand_init(seed, idx, offset, state)` seeds the generator with the **thread index**, not the **tensor-element index**, and the CUDA kernel's launch grid size is itself a function of the GPU's SM count, the element-to-thread (and hence element-to-random-value) mapping silently changes between GPU models once a tensor is larger than one "wave" of the launch grid.

### Cited Findings
- Core seeding/reproducibility guarantee (same GPU, same configuration): "If curand() is called with the same initial state each time, and the state is not modified between the calls to curand(), the same sequence is always generated." — [NVIDIA cuRAND Device API Overview](https://docs.nvidia.com/cuda/curand/device-api-overview.html) (accessed 2026-10-14)
- Seed/subsequence/offset semantics: "Following a call to curand_init(), curand() returns a sequence of pseudorandom numbers with a period 2^128." "Different seed is guaranteed to produce different starting states and different sequences. Subsequence and offset together define offset in a sequence with period 2^128." "Within an experiment, each thread of computation should be assigned a unique sequence number." The state after initialization "will be the state after 2^67 · sequence + offset calls to curand() from the seed state." — same source
- Common DL usage pattern that ties the RNG stream to the *thread*, not the *element*: `curand_init(seed, idx, offset, &state)` where `idx = threadIdx.x + blockIdx.x * blockDim.x` — i.e., "curand_init(seed, idx, offset, &state) seeds Philox with the thread index." — [aggregated from NVIDIA cuRAND programming guide usage pattern, via pytorch/pytorch issue #194676 discussion](https://github.com/pytorch/pytorch/issues/194676)
- The cross-GPU-model failure, documented by PyTorch engineers investigating this exact issue: "Seeding a CUDA generator makes device-side sampling reproducible on the same GPU model, not across GPU models. ... the random stream is attached to a thread, not to an element, so the element-to-thread mapping is a function of the device's SM count." The grid-size computation that causes this is `grid.x = min(SMs × (maxThreadsPerSM / 256), ceil(numel / (256 × VEC)))`, giving a concrete reproducibility threshold `T = SMs × (maxThreadsPerSM ÷ 256) × 256` elements, below which all GPUs agree and above which the mapping diverges because smaller devices must wrap more than one element per thread. Reported concrete thresholds: Tesla T4 (40 SMs, 1024 threads/SM) → T = 40,960 elements; NVIDIA L4 (58 SMs, 1536 threads/SM) → T = 89,088 elements. — [pytorch/pytorch issue #194676, "CUDA RNG is not reproducible across GPU models above a launch-geometry threshold"](https://github.com/pytorch/pytorch/issues/194676) (accessed 2026-10-14)
- Explicit statement that this is **not fixed** by PyTorch's determinism flag: "`torch.use_deterministic_algorithms(True)` provides no protection" against this particular RNG-launch-geometry effect, because the divergence happens in the random-number generation step itself, before any floating-point accumulation occurs. — same source
- As of this research date, a documentation PR to add this caveat to PyTorch's own Reproducibility notes and seeding docstrings (PR #196733, "[docs] CUDA generator output depends on the device's SM count") had been reviewed and approved by PyTorch maintainers (eqy, kurtamohler, ngimel) but was still shown as **open, not yet merged**, as of 2026-10-14 — i.e., **this caveat is not yet present in the officially published PyTorch documentation** (confirmed absent from the live PyTorch 2.14 `randomness.html` and `torch.manual_seed` pages fetched in this research). — [pytorch/pytorch PR #196733](https://github.com/pytorch/pytorch/pull/196733) (accessed 2026-10-14)

### Inferences
- This is a stronger and more specific claim than the general "no cross-architecture reproducibility" statements from cuBLAS/cuDNN: the cuRAND/PyTorch case shows the divergence is a *deterministic function of SM count* with a *computable threshold*, not merely an unspecified "may differ" — useful for a blog wanting a concrete, reproducible-itself demonstration of cross-GPU nondeterminism.
- Because the threshold scales with `SMs × maxThreadsPerSM`, larger/newer GPUs (more SMs) have a *higher* safe-element threshold before divergence — meaning a script that "worked identically" on two different cards for small tensors can start disagreeing only once inputs grow past a size that depends on exact chip specs, making this bug class easy to miss in small-scale testing.

### Gaps
- I could not confirm from NVIDIA's own cuRAND documentation (as opposed to the PyTorch issue discussion) an explicit, named statement that "cuRAND results are not reproducible across different GPU models" — the NVIDIA docs I accessed describe the seeding/sequence/subsequence contract in the abstract (same state ⇒ same output) but do not themselves discuss SM-count-dependent launch geometry; that specific causal chain is documented by PyTorch engineers reasoning about cuRAND's primitives, not by NVIDIA's cuRAND guide directly.
- Could not verify whether this same launch-geometry/thread-indexing caveat is mentioned anywhere in NVIDIA's own cuRAND "Host API" or "Device API" overview pages (only PyTorch's issue tracker was confirmed to state it explicitly) — worth flagging in the blog as "documented by PyTorch's engineering team, not (yet, as far as I could verify) by NVIDIA's own cuRAND docs."

## `torch.manual_seed`: which generators it seeds, and DataLoader worker behavior

### Takeaway
`torch.manual_seed(seed)` seeds **every** device's default RNG in one call — both the CPU default generator and the default generator on all CUDA devices — but it does not automatically propagate to separate worker processes spawned by `DataLoader(num_workers>0)`, nor to other libraries (NumPy, Python's `random`); those require explicit, separate seeding per PyTorch's documented pattern.

### Cited Findings
- "Sets the seed for generating random numbers on all devices. Returns a torch.Generator object." — [torch.manual_seed, PyTorch 2.14](https://docs.pytorch.org/docs/2.14/generated/torch.manual_seed.html) (accessed 2026-10-14). Signature: `torch.manual_seed(seed)`, where "the seed parameter accepts an integer within the range [-0x8000_0000_0000_0000, 0xffff_ffff_ffff_ffff]. Negative values are converted using the formula 0xffff_ffff_ffff_ffff + seed." — same source
- Explicit confirmation on the Reproducibility page that "all devices" means both CPU and CUDA: "You can use torch.manual_seed() to seed the RNG for all devices (both CPU and CUDA)." — [PyTorch Reproducibility notes, PyTorch 2.14](https://docs.pytorch.org/docs/2.14/notes/randomness.html)
- What it does **not** cover, per the same page: (1) other libraries — "If you or any of the libraries you are using rely on NumPy, you can seed the global NumPy RNG with np.random.seed(0) ... However, some applications and libraries may use NumPy Random Generator objects, not the global RNG, and those will need to be seeded consistently as well... If you are using any other libraries that use random number generators, refer to the documentation for those libraries..."; (2) custom/Python-level randomness — "For custom operators, you might need to set python seed as well: random.seed(0)"; (3) DataLoader worker processes — "DataLoader will reseed workers following the Randomness in multi-process data loading algorithm. Use worker_init_fn() and generator to preserve reproducibility," with the documented canonical pattern being a `seed_worker(worker_id)` callback (reading `torch.initial_seed() % 2**32` inside each worker and reseeding NumPy and Python's `random` module there) plus passing a separately-seeded `torch.Generator` as the `generator=` argument to `DataLoader`. — same source

### Inferences
- The "reseed workers following the Randomness in multi-process data loading algorithm" phrasing implies DataLoader workers get *some* automatically-derived seed (deterministically derived from the main process's base seed, per PyTorch's internal algorithm) even with no user action — but that per-worker seed is *not* simply "the same as `torch.manual_seed`'s seed," which is exactly why NumPy/`random` inside a worker still need the explicit `seed_worker` callback: libraries other than `torch` itself are not covered by whatever implicit per-worker torch-level reseeding occurs.
- Combined with the cuRAND finding above, "seeds the RNG for all [CUDA] devices" should be read as "initializes the same logical seed value across every GPU's local generator state," which is necessary but — per the SM-count/launch-geometry finding — not sufficient for identical sampled values across GPU models with different hardware specs.

### Gaps
- I could not find, on the current `torch.manual_seed` or Reproducibility pages, a description of the exact internal algorithm PyTorch's DataLoader uses to derive each worker's default seed from the main-process seed (the page references "the Randomness in multi-process data loading algorithm" by name/link but the fetched content did not include that linked page's own detailed text).
- Could not independently verify whether `torch.manual_seed`'s CUDA-seeding step itself is affected by the "SM-count-dependent" PR #196733 caveat for multi-GPU setups beyond what's already captured in the cuRAND section — i.e., whether seeding behavior differs for `torch.cuda.manual_seed(seed)` (single current device) vs. `torch.cuda.manual_seed_all(seed)` (all devices) in any way relevant to reproducibility; this distinction exists in the API (confirmed by PyTorch's `torch.cuda` seeding function names surfaced during research) but its docstring content was not directly fetched in this session.
